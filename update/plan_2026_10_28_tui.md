## Landed

### Status row visibility and activity markers

The inline working row now follows Rust's bottom-pane state machine.

- `tui/tea/model.go`: `statusIndicatorHidden` mirrors
  `bottom_pane::hide_status_indicator` / `ensure_status_indicator`.
  `appendAssistantDelta`/`mergeAssistantFinal` hide the row
  (`chatwidget/streaming.rs` `sync_active_stream_tail`), committed commentary
  and partial answers restore it, and an in-flight command, MCP call, web
  search or tool call restores it. A fresh turn always starts visible.
- Unified-exec commands with no parsed actions no longer create a transcript
  cell (`chatwidget/exec_state.rs` `is_standard_tool_call` /
  `is_unified_exec_source`); the status row plus the shared footer summary is
  the only live surface (`bottom_pane/unified_exec_footer.rs` `summary_text`).
- `tui/status_indicator.go`: `DETAILS_PREFIX` is `  └ ` and the inline context
  separator is ` · `, matching `status_indicator_widget.rs`.
- `tui/motion.go`: `ActivityIndicatorStyled` adds `shimmer.rs` styling for the
  status row; the row uses `ReducedMotionIndicator::Hidden`, exec cells keep the
  reduced-motion static bullet.
- `tui/exec_cell/*`: an in-flight call renders `activity_marker` (blinking or
  shimmering marker) and a finished call freezes its outcome glyph.

### Exec command actions and the unified-exec source

Rust's TUI renders the `commandActions` the executor parsed and decides whether
a command is a standard tool call from its source; Go was re-parsing the raw
command and dropping the source on the executor path.

- `protocol/exec_events.go`: `ThreadItem.CommandActions` carries the app
  server's parsed actions in-process (`json:"-"`); `nil` means the payload
  omitted them, while a present-but-empty slice keeps Rust's "no standard
  action" result.
- `app/remote_tui.go`: `remoteProtocolCommandActions` decodes the
  `commandActions` array from a `commandExecution` payload.
- `tui/tea/model.go`: `parsedCommandsForExecCellItem` prefers the supplied
  actions and only falls back to `parsedCommandsForExecCell` when they are
  absent, so a shell alias such as `ls` stays `Unknown` instead of being
  re-labelled as a list action.
- `exec/exec.go`: items for the `exec_command` tool carry
  `source = unifiedExecStartup` (Rust's `ExecCommandSource`), so the TUI tracks
  the live process for the background-terminal footer and skips the duplicate
  cell for non-standard commands; the plain `shell` tool keeps the agent
  source.
- Tests: `app/remote_tui_command_test.go`
  (`TestRemoteProtocolCommandExecutionCarriesCommandActions`) pins decoding and
  the absent-field fallback; `tui/tea/unified_exec_command_actions_like_rust_test.go`
  (`TestUnifiedExecUnknownActionsMatchRustCommandCell`) pins that an Unknown
  unified-exec command paints no live Exploring cell and completes as
  `Ran <cmd>`.

### `fab1a57545` - Preserve rich composer content in Vim registers (`#57564`)

The composer now has Rust's single-entry rich register: one text, linewise
flag, structured elements and local-image paths shared by editor kills, Vim
yanks and Ctrl-Y.

- `tui/tea/composer_register.go`: `composerRegisterSpan` resolves the atomic
  payloads of a register text (element ranges validated against the text,
  image paths kept), `storeComposerRegister` writes the Vim and Ctrl-Y views
  together, and `insertComposerRegisterText` inserts text while re-registering
  mention/element ranges and re-attaching images under fresh `[Image #N]`
  labels (`chat_composer/vim_register.rs` `register::copy` / `paste`).
- `tui/tea/vim_mode.go`: yanks, deletes (`x`, `s`, `dw`, `D`, `dd`, `d`/`c`
  operators, line motions, `yy`/`Y`) capture the rich register; `p` pastes it
  characterwise or linewise, keeps the cursor on the leading pasted element
  for linewise paste, avoids the extra newline when the register already ends
  with one, and records the paste for `.` repeat. Undo/redo snapshots now carry
  elements and attachments.
- Vim edits transform the tracked element ranges (`x`, `D`, `dd`, operators,
  replace mode, prompt-prefix absorption) so placeholders deleted or shifted
  by a command no longer leave stale `text_elements`.
- `tui/tea/editor_kill_yank.go`: kills store the same register (whole-line
  kills as linewise), and Ctrl-Y rehydrates rich payloads instead of inserting
  placeholder text; in Replace mode a rich yank resets the per-character
  recovery so Backspace cannot corrupt the pasted elements.
- Tests: `tui/tea/vim_register_like_rust_test.go` covers repeated rich pastes
  and `.` (fresh labels), rich register across draft clear/composer handoff,
  linewise paste, plain deletes replacing the register, Ctrl-Y, Replace-mode
  recovery, and rich undo/redo. `tui/tea/editor_kill_yank_test.go` flips the
  #57502 plain-text guard to the #57564 rich restore.

Declared deviations from Rust:

- Go has no collapsed-paste placeholders (`pending_pastes`); pasted text stays
  inline, so the register carries elements and image paths only.
- Elements carry their placeholder text rather than a stable binding id, so
  rich undo/redo restores the exact ranges and mention text but not a separate
  binding identity.
- Go's Vim dot-repeat records normal-mode changes (find, Replace-mode
  overwrite, paste, delete); replaying an insert session, including its Ctrl-Y
  register generation, is not implemented.
- Deleting a placeholder does not prune every orphaned attachment in Go (a
  pre-existing gap); the tests clear the draft explicitly, as submission does.
- Characterwise `p` inserts at the caret in Go, without advancing past the
  caret grapheme/atom; Rust inserts at `next_atomic_boundary`. This placement
  gap predates the rich register and is unchanged here, so the `xp` test
  asserts the Go caret position.
