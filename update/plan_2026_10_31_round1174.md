# Round 1174 audit plan (2026-10-31)

Target: Rust `main` at `cbe16d525c2d7362fc3d4726143288e932905daa`.

This round aligns the shell-snapshot transport split: the session file snapshot
serves local launches only, and a remote executor is reached exclusively through
the capability-gated `shell_snapshot_v2` request.

## Rust behaviour

- `core/src/tools/runtimes/unified_exec.rs:284-306`: the session snapshot is
  `None` when `environment_is_remote` (and when a credential broker is active
  with escalated permissions); a local launch replays the file.
- `core/src/unified_exec/shell_snapshot.rs:169-196`: `shell_snapshot_request`
  attaches the executor request for both local and remote environments, but only
  when the environment reports `shell_snapshot_v2_supported`.

So a remote executor never sees the file snapshot, and receives a request only
after advertising the capability.

## Go gap

`appserver.shellSnapshotV1ProviderForTurn` returned a
`ShellSnapshotRequest` for `request.Remote` whenever the `shell_snapshot`
feature was on, without any capability check. That sent Go's default
(`shell_snapshot` stable/on, `shell_snapshot_v2` off) remote launches down a
path Rust never takes, and could ask an executor without v2 support to capture.

## Change

- The v1 provider answers remote launches with no snapshot.
- The only producer of `SnapshotProviderResult.Remote` is now
  `shellSnapshotV2ProviderForTurn`, which already requires the executor's cached
  `shellSnapshotV2` capability and scopes the request to `thread:environment`.
- `TestShellSnapshotProviderFollowsTheFeatureAndLaunchShapeLikeRust` now asserts
  a remote launch gets neither a path nor an executor request; the v2 provider
  test keeps covering the capability-gated remote request.
