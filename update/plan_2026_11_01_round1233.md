## Context

Both commits were recorded as `not_applicable` because the audit that produced
those entries predates the Go port of `windows-sandbox-service`. The service now
exists, its stop path and its package-registration failure path are instrumented,
so this round audits them against the Rust sources and certifies them.

## #50507 service stop diagnostics

- `provisionservice/service_diagnostics_windows.go` stores
  `(reason<<32)|hresult` as `CodexLastStop` in the existing SCM service key and
  never recreates the key, because Windows removes it during uninstall.
- `RecordServiceStopped` emits `codex.windows_sandbox.service_stopped` only
  when the re-queried service state, both SCM exit codes and the registry record
  still match, which keeps a concurrent restart from pairing inconsistent
  evidence; `serviceStopReasonLabel` maps all seven reasons.
- The service records `Starting` before the broker, the fatal reason in
  `serviceMainProcedure` and the final reason in `runServiceMain`
  (`OwnerRemoved`, `StopRequested`, `Shutdown`); `ReportStatus` caches the
  status only after `SetServiceStatus` succeeds.

The one gap this round closes is the fatal-reason mapping: `fatalStopReason`
now reports `ServiceStopReasonRegistrationInterrupted` for
`ErrRuntimeSetupInterrupted`, which `serviceMainProcedure` used to report as a
startup or broker failure. `service_fatal_reason_like_rust_test.go` covers an
interrupted registration during startup and while running, plus the startup and
broker failures.

## #53426 registration failure diagnostics

`registration_result.rs` is carried by `readRegistrationResult` and
`registrationResult.check` in
`windowsandboxservice/registered_packages_register_windows.go`: the async
status and `ErrorCode` stay separate from a `GetResults` failure,
`IDeploymentResult`'s `ExtendedErrorCode` and `ActivityId` each keep their own
error slot, and the summary keeps the same phase tags without free-form Windows
`ErrorText`.
