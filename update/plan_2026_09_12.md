## Non-TUI core: MCP OAuth cross-process credential lock (`RefreshCredentialLock`)

Go's MCP OAuth credential store had no cross-process serialization, so two
processes (or two goroutines) could replay the same rotating refresh token or
observe a partially persisted transaction. Rust guards this with
`rmcp-client/src/oauth/refresh_lock.rs`, which `save_oauth_tokens`,
`delete_oauth_tokens`, and `refresh_transaction` all hold. This pass ports it:

- `mcp/oauth_credential_lock.go` mirrors Rust `RefreshCredentialLock`: an
  exclusive `flock` at `$CODEX_HOME/mcp-oauth-locks/<sha256(store_key)>.lock`
  with a 60s acquire bound and 50ms retry, never stealing a held lock, and the
  Rust timeout message (`timed out after 50ms waiting for OAuth refresh lock ...`).
- `OAuthStore.Save`/`Delete` now acquire the lock and delegate to new
  `saveWithLockHeld`/`deleteWithLockHeld` writers, mirroring Rust's
  `save_oauth_tokens_with_lock_held` / `delete_oauth_tokens_with_lock_held`.
- `httpClient.refreshOAuthTokenForRequest` holds the lock across the whole
  transaction: it re-reads the authoritative credential after acquiring it, and
  when the pre-lock snapshot needed refreshing but the locked reread no longer
  does, it adopts the winner from another process without contacting the
  provider (checking that refresh credentials stay bound to the validated
  issuer), then refreshes and persists with the locked writer. The forced-401
  path still refreshes. Provider failure adoption and permanent-error deletion
  use the locked writer, so no nested acquisition can deadlock.
- Tests: the Rust lock-contention vector (timeout without stealing, then

## Non-TUI recovery: attachment-owned permissions for MCP servers (`batch-mcp-oauth-identity`, #40728)

`4213b38f3c` #40728 makes MCP servers attached to executor environments retain
their owner's permission profile instead of inheriting the thread-wide sandbox
authority. Go previously had one thread-wide profile and no per-server
authority, so attached servers inherited the thread's permissions and every
server stayed callable even when its authority was unresolved.

- `mcp/config.go` + `mcp/permission_authority.go`: `RuntimeConfig` gains
  `PermissionProfile` and `ServerPermissionProfiles` (Rust `McpConfig`), plus

  resolution rules: the controller-owned Apps server uses the thread authority,
  an attached environment uses its own published authority, local and
  selected-plugin servers use the thread authority, and anything else gets no

  restrictive default so discovery/resource reads never inherit execution

## #44341 residual re-assessment (evidence-based)

The earlier residual note ("same-owner refreshes should preserve the live relay;
replacement sessions need fresh replay state") no longer describes a real gap:
- `RemoteControlWebsocketLoop.runConnection` ends only on shutdown, disabled, or
  a stopped connection worker; it does not watch the auth revision, so a
  same-owner token refresh keeps the live relay connection (only the reconnect
  backoff/reset path consumes `AuthRevision`). `RetireForAuthChange` is invoked
  only for logout/account-switch (owner changes) and disables the session.
- `NewRemoteControlWebsocketLoop` is created only by `ServeRemoteControlOnly`
  (`app/remote_control_state_db.go`), one per process; a retirement disables the
  session and ends that loop, so there is no in-process "replacement session"
  that could inherit a stale replay cursor or client tracker.
- Stale-message/queued-RPC rejection and drained persistence permits are part of
  Rust's async transport-layer rework; Go tears the connection down on owner
  change and uses synchronous persistence, so those mechanisms have no Go
  counterpart (architecture-different).
