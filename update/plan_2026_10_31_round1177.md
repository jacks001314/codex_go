## Gap

Two app-server parity tests were red on `main`:

- `TestRuntimeRouterExecutorCatalogUsesExtensionByteBudgetWithoutCoreWarningLikeRust`
  turned the turn's `model_context_window` into the skill catalog budget. Rust
  resolves the budget from the captured step model, whose `ModelInfoOverrides`
  come from the session configuration captured when the thread is created
  (`core/src/session/mod.rs`: `model_info_overrides:
  config.to_models_manager_config()`; `StepSettings::apply_update` re-resolves
  only from those overrides). A turn-local override therefore tightens that
  turn's context management without re-budgeting the catalogs, so every executor
  skill was dropped in Go while Rust keeps them.
- `TestRuntimeRouterFileChangeEmitsAnalyticsLikeRust`,
  `TestRuntimeRouterFileChangeAnalyticsIncludesUserReviewSummaryLikeRust` and
  `TestRuntimeRouterTurnCompletedEmitsAcceptedLineFingerprintsLikeRust` wrote
  `model = "gpt-5"` into the test config. Neither this repo's bundled catalog
  nor `codex-rs/models-manager/models.json` lists `gpt-5`, so
  `model_info_from_slug` supplies `apply_patch_tool_type: None` and Rust's
  `spec_plan.rs` (`if context.model_info.apply_patch_tool_type.is_some()`)
  never registers `ApplyPatchHandler`. The dispatcher answered
  `tool not found: apply_patch`, so the file-change item, turn diff, review
  analytics and accepted-line fingerprints were never exercised.

`go test ./...` surfaced two more `./app` failures that reproduce on a clean
checkout:

## Follow-up: concurrent executor refresh guard

`TestExecServerRegistryAuthConcurrentRefreshesShareOneRefreshLikeRust` failed
whenever the whole `./app` package ran (never alone): a registration that
resolved the credential while another exchange was still in flight read the
unsettled generation and `checkExecutorCredential` answered the transient
"executor refresh outcome is unknown" error, so `RefreshAfterUnauthorized`
returned false. Rust joins the refresh guard before that check
(`AuthManager::refresh_token_if_unchanged`), so the queued caller reuses the
completed refresh. `app/exec_server_auth.go` now waits on the same guard once
for a transient resolution error and re-resolves.

`TestExecServerRegistryAuthRaceWithInFlightRefreshJoinsTheGuardLikeRust` pins
the race deterministically by holding the refresh exchange open until the
racing caller has resolved the unsettled generation; it fails without the fix
and passes with it (verified in a clean worktree).

Verification: `go test ./app -run 'ExecServerRegistryAuth|ExecServerAuth|RemoteExecServerRefreshes' -count=3`
and two consecutive `go test ./app -count=1` runs (30s each, ok).
