## Goal

Stop preparing a filesystem sandbox from doing redundant path-alias resolution
and repeated permission-entry filtering on the executor runtime thread.

## Findings

- Rust's fix is local to `FileSystemSandboxPolicy::effective_writable_roots`
  (resolve precedence and filesystem aliases once per effective entry, reuse the
  cached paths for writable roots and read-only carveouts, return early when no
  entry is writable) and to exec-server `fs_sandbox.rs` (only non-Linux hosts
  normalize permission-root aliases; Linux leaves it to the sandbox helper).
- Go has no `FileSystemSandboxPolicy` entry/carveout pipeline. Writable roots
  are derived once from the legacy `SandboxPolicy` by
  `GetWritableRootsWithCWD` and `sandboxpath.WritableRootsWithProtectedSubpaths`,
  which clean, de-duplicate and then add Git-dir carveouts in a single pass.
  There is no per-writable-root loop that re-resolves permission entries, and
  `HasFullDiskWriteAccess`/empty policy short-circuits return early.
- Go's exec-server does not run the `FileSystemSandboxRunner` preparation that
  `fs_sandbox.rs` optimizes; it delegates sandboxed command execution to the
  `sandbox` package (bwrap/seatbelt/Windows sandbox), so there is no
  permission-root alias normalization on the executor runtime thread to remove.

## Implementation

- None required. Both halves of the upstream change optimize code paths Go does
  not have; the observable writable-root result is unchanged, which the existing
  `sandbox` tests already assert.
