## Landed this round

### `#55587` - caller-controlled prompt cache keys

Ported semantics:

- `model.PromptCacheKey` is the policy for the Responses `prompt_cache_key`
  request-body field with the three Rust modes: the default session-derived
  key, a caller key (`CustomPromptCacheKey`), and omission
  (`OmitPromptCacheKey`). Its zero value is the default policy.
- `exec.Request.PromptCacheKey` is the Go host surface corresponding to Rust's
  `StartThreadOptions.prompt_cache_key`. `exec` resolves the policy against the
  run's session-derived identity, so the default run keeps sending the thread
  id and `Omit` leaves the body field out.
- Child agent runs inherit the policy because subagent requests clone the root
  `exec.Request`, matching Rust's `inherited_child_settings`.
- Session/thread identity headers stay independent of the policy. Go already
  derives `session-id`, `thread-id`, and `x-client-request-id` from the session
  identity rather than from the prompt cache key, which is the Rust #55587
  requirement.

Files:

- `model/prompt_cache_key.go`
- `exec/exec.go`

Tests:

- `model/prompt_cache_key_like_rust_test.go` (three policies, zero value,
  accessors, unchanged session identity headers)
- `exec/prompt_cache_key_like_rust_test.go` (policy reaches the model request;
  subagent requests inherit the policy)

Deliberate deviations / N/A:

- Go has no embedded `codex_core::StartThreadOptions`; `exec.Request` is the
  host-facing equivalent (CLI, embedded TUI, goal runtime, subagents).
- The app-server wire protocol matches Rust and therefore does not expose a
  prompt cache key parameter; Go's app-server thread starts remain
  session-derived exactly like Rust's app-server.
- Guardian review sessions already send the parent-scoped
  `guardian:<thread>` key (`appserver/guardian_session.go`), which is the
  `PromptCacheKey::Custom` behavior from Rust.
- Go's Responses payload elides empty strings, so an empty custom key degrades
  to omission; Rust would serialize an empty value.
