## Advanced this round

Covering the gRPC host with Rust's
`server_output_budgets_follow_exec_wait_and_terminate_over_grpc` scenario showed
that Go's second observation repeated the first one: a script that writes
`partial`, yields, then throws produced `partial` in the yielded observation
**and** `partial\nScript error: …` in the wait observation, so the model saw the
pre-yield text twice and the wait header reported 9 tokens instead of Rust's 24.

The cause is that the two views of a cell's output advance on different
schedules: `cellDelta` moves a cursor over `cell.texts`, while
`cellContentDelta` clears `cell.items`. The yielded observation only read the
text view, leaving the item view to be replayed by the next wait. Rust takes the
whole collector at every observation, so both views must be consumed together.

## What changed

- `tool/code_mode_exec.go`: the exec yield observation and the wait
  `runningOutput` now publish `content_items` from `cellContentDelta` alongside
  the body from `cellDelta`, so the next observation starts empty.
- `codemode/grpc_stdio_host_failure_like_rust_test.go` drives the real
  `RunGrpcStdioHost` over gRPC: the failure branch asserts Rust's exact
  `Script error:` bytes and the exec→wait flow asserts that the yielded
  observation carries `partial` once and the wait observes only
  `Warning: truncated output (original token count: 24)\nTotal output lines: 2\n\nScript error:\n…17 tokens truncated…67890123456789`
  with `error_text` set to the 80-byte thrown string.
