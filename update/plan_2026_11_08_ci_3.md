### 3.2 Go 侧锚点

| 事实 | 证据 |
| --- | --- |
| Go 的发布是**单步**完成建 release + 上传资产 | 【F:.github/workflows/release.yml†L140-L147】`uses: softprops/action-gh-release@v2`，`files: dist/**`、`prerelease: ${{ contains(needs.build.outputs.version, '-') }}` |
| 没有"先建后传、失败按 ID 删"的分阶段控制 | 同文件 147 行内没有 `id:` 捕获、没有 `trap`、没有 `gh api .../releases` 调用 |
| 与 Rust 修前完全同构的失败模式 | prerelease 是**非 draft** 直接创建（`prerelease: true`），资产随后上传；上传失败即留下"公开但不完整"的 prerelease，且公开 release 已存在 → 重跑不会再触发 `prereleased` |

### 3.3 判定：`partial`；**第二处消费点：有（同一工作流内不可分）**

Rust 把"建 release"与"上传资产"拆成两段才能做 ID 级清理。Go 侧用 `softprops/action-gh-release` 一步做完，两件事绑在同一步里——这就是"第二处消费点"：**不是缺一个参数，而是缺一个阶段边界**。落地必须换实现（`gh api` 建 + 上传 + trap 清理），不能只加个输入。

### 3.4 落地切入点

1. 新增 `.github/scripts/publish-github-release.sh`（等价 Rust 版本）：GraphQL 查 tag（含 draft）→ 不存在则校验 tag ref → stable 用 `draft: true`、prerelease 直接建 → 记录 `release_id` → `trap 'delete $release_id' ERR` → 上传 `dist/**` → 成功后 `trap -` 并更新元数据。
2. `release.yml:140-147` 换成调用该脚本，删除 `softprops/action-gh-release`。
3. 测试：可移植 Rust 的 `.github/scripts/test_releases.py` 思路（stub `gh`），覆盖上传失败清理、重跑成功、既有 prerelease 保留、上传后元数据失败不删。
