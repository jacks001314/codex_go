### sync135: executed tool call metadata survives recorder capacity pressure (#46712)

Go's recorder refused a registration once the group or mapping budget was full,
so orphaned evidence from finished cells could permanently block fresh Code Mode
calls from reporting their executed calls, cell id and completion marker.

Rust now reclaims and evicts instead:

- under **mapping** pressure it drops output mappings whose cell is gone
  ("Ended empty cells can leave mappings without any records to attach"), and
- under **cell or pending-call** pressure it evicts finished (or already
  revoked) cells that no output mapping can reach any more, revoking their
  completeness and releasing the pending calls they held - never the cell whose
  output is about to make its own late records attachable again.

`ExecutedToolCallRecorder.registerGroup` gained the same two steps
(`reclaimOrphanedOutputs`, `capacityPressure`, `evictFinishedGroup`), with the
eviction picking the lowest group id when several qualify so the choice does not
depend on Go's map iteration order.

Evidence: `turn.TestExecutedToolCallRecorderReclaimsOrphanedMappingsLikeRust`
(the orphaned mappings no longer consume the budget, and the fresh call attaches
`cell_id`/`tool_calls_complete`/the recorded call) and
`turn.TestExecutedToolCallRecorderEvictsUnreachableFinishedGroupsLikeRust` (the
whole pending budget is held by finished cells with no output mapping; the fresh
cell registers, the lowest unreachable cell is evicted and revoked, and the
mapped cell keeps its own complete inventory). Both are verified to fail with
the reclamation, respectively the eviction, removed.

Recorded nuance: Go's lifecycle deletes a mapping together with its group, so
Rust's orphaning cause - `finish_cell_recording` dropping a cell whose
completion is still `Unobserved`/`Incomplete` - has no Go counterpart, because
Go models `Complete` (the closed dispatch gate) with a single `finished` flag
and never drops a registered group at finish. The reclamation is therefore the
guard Rust needs, and Go's own orphan state can only be built directly (which is
what the test does).

### sync136: the persisted transcript retains the summary with the raw reasoning (#46711)

Rust's persisted-transcript reasoning arm (`thread_transcript.rs`) now keeps the
split summary and appends the enabled raw chain-of-thought after a blank line
instead of replacing the summary - so the projected cell equals the live replay,
which has always chained summary + raw parts. Go's thread-transcript projection
(`app.reasoningProjectionText`) and its Markdown export
(`app.transcriptExportReasoningText`) still replaced it.

Both now build the summary first and append the raw content when
`show_raw_agent_reasoning` is enabled and the item carries content; an empty
summary leaves the raw content alone, mirroring Rust's conditional separator.

Evidence: `app.TestReasoningRawVisibilityGatesRawContent` is re-pinned
(`Summary body.\n\nRaw chain of thought.` for both the export body and the pager
entry) and now also pins Rust's
`snapshot_formatter_reasoning_matches_compact_and_detailed_replay` - the
persisted cell's text equals the chatwidget's raw variant.

### sync137: MCP diagnostics stay in the retained warnings entry after the turn starts (#46751)

Rust's `ChatWidget::add_mcp_startup_warning` no longer branches on
`warning_display_state.startup_complete`: MCP startup diagnostics join the
retained `StartupWarningsCell` (with the failed servers and their sign-in

live conversation. Go still routed those later diagnostics through the inline

config-warning paths, exactly as Rust still branches on them.

(re-pinned from the old inline-path test): after a turn starts, a late MCP
failure shows the retained `1 MCP startup issue` summary, adds no inline row, and
keeps the diagnostic in the transcript entry.
