### `1715e55076` #45185 - direct tool-call metadata (port)

Rust attaches a recorded direct call to the invocation's own output before it
enters history (`prepare_direct_call` + `attach_direct_call_to_output`), marks
`tool_calls_complete` when the arguments were fully recorded, bounds retained
direct metadata (1 MiB) with a clear order (tool-result metadata first, then the
executed calls), ties prepared records to a recorder-lifetime token so disabling
capture invalidates them, strips direct metadata from prompt/compaction inputs
when capture is disabled, and records call IDs that bypass local dispatch so
their reuse cannot establish Code Mode completeness. Go still uses the older
pending-then-attach-at-prompt model (`AttachPendingToPrompt` +
`CommitAttachment`), has no `tool_calls_complete` for direct outputs, no retained
budget, and no non-dispatched observation.

Go-side surface: `turn/executed_tool_calls.go` (recorder),
`turn/tool_dispatcher.go` (dispatch/attach), `turn/agent_loop.go` and
`turn/runtime.go` (prompt attach/strip), `turn/compaction` (history strip).

### `e61f381900` #45182 - N/A

Rust hand-walks the TOKEN_GROUPS buffer and copies SIDs into owned values, so it
now validates the layout, SID bounds, revision, and length with a shared
size-limited helper. Go delegates to `golang.org/x/sys/windows`
(`Token.GetTokenGroups()`) and only reads the returned `SIDAndAttributes`
(`sandbox/windowssandbox/token_windows.go` `scanTokenGroupsForLogonSID`), so
there is no raw buffer walk to harden and no owned group list to build. No Go
change; the equivalent robustness comes from x/sys's own sizing/validation.

### `cfde11a24c` #45180 - N/A

The commit extracts `PreparedNetworkConfig` from the loader
(`build_network_proxy_spec`) preserving behavior, and adds helpers for
*per-environment* network policy (`project_environment_profile_network`,

## Newly discovered gap (evidence): the TUI model/reasoning picker is not applied or persisted

While auditing the last banner residual (`update_luna_reserve_reasoning`) the
underlying mechanism turned out to be missing rather than merely nuanced:

- Rust's picker actions dispatch `AppEvent::UpdateModel` /
  `UpdateReasoningEffort` / `PersistModelSelection` (and
  `UpdateLunaReserveReasoning` for the temporary Reserve model). The app then
  (a) sends a `thread/settings/update` for the active thread
  (`app/thread_settings.rs` `active_thread_model_setting_update_params` -
  including the cyber-model workspace-permission/reviewer override - and
  `sync_active_thread_reasoning_setting`), and (b) writes `model` /
  `model_reasoning_effort` through config persistence
  (`app/config_persistence.rs` `persist_model_selection`). The Reserve model is
  the exception: it updates the active task's effort without persisting a model
  default (`app/backend_banner_fallback.rs::update_luna_reserve_reasoning`).
- Go has the picker UI and the plan-mode-scope prompt, and
  `tui/tea/model.go::resolveModelPickerModal` updates `m.State` as well as
  returning a `PickerDecision`; but no production code consumes
  `ModalResponse.Picker` (both `OnModalResponse` handlers only forward to the
  approval/elicitation/user-input brokers), no code writes a `model` /
  `model_reasoning_effort` config key (the settings writers cover theme, pet,
  service tier, experimental features, and memories), and no callback updates
  the server thread's settings for a picked model/effort.

Consequences: a picked model/effort only affects the local session's subsequent
turns; it does not persist across restarts and does not update the remote
thread's stored settings, where Rust does both. The Reserve exception therefore
has no Go counterpart to fix until the base application path exists - so the
recorded `update_luna_reserve_reasoning` residual is folded into this lane.

This is the next TUI/core item, with the Rust references above pinned.

### `36f0dbe796` - revoke_ace hardening (port)

Rust's `acl.rs::revoke_ace` now returns a `Result`, no-ops when the target has a
null DACL ("replacing it with an empty ACL would deny access"), and skips the
write when `REVOKE_ACCESS` removed nothing (an unchanged ACL must not propagate
inheritance). Go's `RevokeACE`
(`sandbox/windowssandbox/deny_read_acl_windows.go`) always rebuilt and wrote the
DACL, so a path with a null DACL panicked inside `windows.ACLFromEntries` (a real
crash: the guard was verified by reverting it and reproducing the panic).

- `RevokeACE` returns early when `fileDACL` reports no DACL, and skips
  `SetNamedSecurityInfo` when the rebuilt ACL's `AceCount` is unchanged.
- Tests: `TestRevokeACEKeepsANullDACL` (a null DACL survives) and
  `TestRevokeACEPreservesChildNullDACLLikeRust` (Rust's
  `revoking_absent_sid_preserves_child_null_dacl`: revoking an absent SID from a
  parent does not rewrite a child that permits inheritance).
