# Round 1220: Retained-handle setup launch (2026-11-01)

Target: Rust main at 67f0994b532b8740f14b5b738af7b7b2a915b1d6 (#42342,
`provisioning.rs`'s legacy arm and `windows-sandbox-rs/setup_launch.rs`).

## Context

Rounds 1215-1219 served provisioning requests but had to answer
`ServiceUnavailable` whenever setup was needed, because the service could not
start the packaged helper with the client's pinned directories still held.

## Launch with retained handles

`sandbox/windowssandbox/setup_launch_windows.go` ports
`setup_launch::spawn_with_retained_handles`: the helper starts with
`CREATE_NO_WINDOW|CREATE_SUSPENDED` and discarded standard handles, every
retained directory handle is duplicated into the child's handle table, and only
then is the process resumed through `NtResumeProcess` (failures translated with
`RtlNtStatusToDosError`). A partially initialized helper is killed and reaped so
it can never run after the parent drops the protections.

`setup_windows.go` threads the retained handles through `runSetupExe` and
`runSetupExeNonElevated`; a launch with pins bypasses the plain
`cmd.Run()` path and waits on the started process instead.

## Service-side provisioning

`RunElevatedProvisioningSetupWithRetainedHandles` ports
`run_elevated_provisioning_setup_with_retained_handles`: the CODEX_HOME must be
an absolute local disk path (no UNC or device prefix), the sandbox directory is
created, the service must already be elevated, and the helper receives a
provision-only payload with the requested proxy settings, setup runtime and real
user.

`windowsandboxservice.RunPackagedSetup` is the production `SetupRunner`: it
refuses a missing packaged helper next to the service image and launches the
helper with the authenticated client's home, account, settings, runtime and
retained directory handles. The service entry point now passes it to the broker,
so a legacy request that needs setup runs the helper instead of falling back.

## Known gaps

Registered-Core provisioning (`provisioning/registered.rs`), native packaged
cleanup, uninstall observation, registered-runtime transactions,
`ServiceStopReason` recording, the cleanup journal and installer/MSIX wiring for
the service binary remain open.
