# Round 1179: the app-server project-config startup warning (2026-10-31)

Target: Rust `main` at `cbe16d525c2d7362fc3d4726143288e932905daa`.

## Gap

The ledger held #42609 (`32c303c197`, "Condense TUI startup warnings") at
`audit_pending` with the note `Partial symbol coverage 3/4; needs review:
project_config_warning`. The TUI half is already in place
(`tui/history_cell/startup_warnings.go`, `tui/chatwidget/warnings.go`,
`tui/chatwidget/mcp_startup.go`, `tui/app.BuildProjectConfigWarningMessages`),
but the Go config loader never marked a project layer as disabled, so nothing
ever produced the message Rust derives from `config.config_layer_stack`.

Rust emits it twice from the same walk: `project_config_warning` in
`codex-rs/app-server/src/lib.rs` (startup `configWarning`) and in
`codex-rs/tui/src/app/startup_prompts.rs`. Both list every
`ConfigLayerSource::Project` layer whose `disabled_reason` is set, in
`all_layers_low_to_high` order, as:

```
Project-local config, hooks, and exec policies are disabled in the following folders until the project is trusted, but skills still load.
    1. <dot-codex folder>
       <reason>
```

and `disabled_reason` comes from
`TrustContext::disabled_reason_for_decision`
(`codex-rs/config/src/loader/mod.rs:1128`): no reason when the folder is
trusted, the stable `<key> is marked as untrusted in the effective
configuration...` prefix for an explicit untrusted decision, and
`To load <gated features>, add <key> as a trusted project in <user config>.`
otherwise, where `<key>` is the folder's own saved key, else the project-root
key, else the repository-root key.

## Evidence

- `config/project_config_warning.go` ports that decision:
  `newProjectTrustContext` builds the project-root and repository lookups plus
  the merged (packaged defaults, user, managed) `projects` table;
  `decisionForDir` walks folder key, project root, repository root and falls
  back to the repository/project root as the message key;
  `disabledReasonForDir` renders the two reason strings byte-for-byte;
  `ProjectConfigWarning` renders the condensed message with Rust's trailing
  newline per entry. `ConfigService.ProjectConfigWarningForCWD` discovers the
  project layers for a cwd with the same `.gcode` folder and
  `project_root_markers` rules the loader uses, skips CODEX_HOME itself, and
  returns "" when nothing is disabled or the startup configuration is
  unreadable.
- `appserver/runtime_router.go`: `configWarningsForInitialize` appends the
  message as one `configWarning`, placed with the other startup warnings before
  the bubblewrap warning, matching the order in `codex-rs/app-server/src/lib.rs`.
  `rememberEmittedConfigWarnings` keeps the thread-scoped path from repeating it.
- Tests: `config/project_config_warning_test.go` pins the undecided message
  the undecided fallback quotes the normalized project-root key, the explicit-untrusted
  prefix, the trusted no-op, and nested folders listed low-to-high;
  `appserver/project_config_warning_test.go` pins the initialize delivery and
  that a later thread start does not repeat it.

## Note

Two pieces of the same upstream behaviour stay with their owning streams:

- `config/read` layers still do not carry `disabledReason` for an untrusted
  project, because `readLayersForCWDOptions` omits project layers entirely when
  the project is untrusted and `config/ignored_settings.go` /
  `config/permissions.go` are being edited by another agent. `app/remote_trust.go`
  and `app/daemon_compatibility.go` already handle a non-nil `DisabledReason`,
  so the layer-stack half can land once those files are free.
- The TUI keeps its own `BuildProjectConfigWarningMessages` formatter; wiring it
  to local config is part of the TUI stream, which is off-limits here.
