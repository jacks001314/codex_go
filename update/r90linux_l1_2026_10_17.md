### 3.1 `sandbox/integrity` 真红的根因（已定位到 file:line）

失败的三条子例有一个共同点：**可写根是一个普通文件**（`narrow_write_grant`、`overlapping_write_grant`、`link_is_the_writable_root`）；而根是目录的三条（`write_grant`/`read_carveout`/`deny_carveout`）全过。

独立探针（`/tmp/_l90_probe4`，用自己的 module + `replace` 指向 worktree，未碰产品码）：

```
PreparePolicy err=<nil>
  root[0].Root="/tmp/l90p4864546325/sandbox-helper"
  root[0].ReadOnlySubpaths=["/tmp/…/sandbox-helper/.git" "/.agents" "/.gcode" "/.aws"]
  root[0].ProtectedMetadataNames=[".git" ".agents" ".gcode" ".aws"]
    EvalSymlinks("/tmp/…/sandbox-helper/.git")    -> "" err=not a directory os.IsNotExist=false
    EvalSymlinks("/tmp/…/sandbox-helper/.agents") -> "" err=not a directory os.IsNotExist=false
    EvalSymlinks("/tmp/…/sandbox-helper/.gcode")  -> "" err=not a directory os.IsNotExist=false
    EvalSymlinks("/tmp/…/sandbox-helper/.aws")    -> "" err=not a directory os.IsNotExist=false
NewFileContentsChecker err=not a directory
```

因果链（全部可引用）：
1. `sandbox/sandboxpath/sandboxpath.go:103-117` `WritableRootsWithProtectedSubpaths` 给**每个**可写根无条件塞入 `ProtectedSubpaths(root)`；
2. `sandbox/sandboxpath/sandboxpath.go:83-90` `ProtectedSubpaths` = `{root/.git, root/.agents, root/.gcode, root/.aws}` —— **不检查 root 是不是目录**；
3. `sandbox/integrity/contents.go:52-55` 确实对"根不是目录"做了处理，但它只把 `ProtectedMetadataNames` 置 nil，**`ReadOnlySubpaths` 未清**；
4. `sandbox/integrity/contents.go:60-66` 于是对 `<文件>/.git` 这类路径调用 `resolveExistingOrKeep`；
5. `sandbox/integrity/contents.go:124-133` `resolveExistingPath` 里 **只有 `os.IsNotExist` 被当作"缺失"**，而 Linux 上 `EvalSymlinks("<file>/.git")` 返回的是 **ENOTDIR（"not a directory"）**，`os.IsNotExist=false` → 直接 `return "", false, err` → 错误上抛。

→ **这是我的探针在 Linux 上独立复现的**（`probe[2]`：`EvalSymlinks(file+"/.gcode") = "not a directory", isNotExist=false`；对照组 `[3]`：真正缺失的路径 `isNotExist=true` 且被正确当作"缺失"）。

**Windows 为什么看不到**：Windows 上按同路径取 `EvalSymlinks("<file>\\.gcode")` 走的是 `GetFinalPathNameByHandle` 语义，失败码落进 `IsNotExist` 分支 → 被当作"缺失"→ 保留原路径 → 不报错。（此条**我无法在 Windows 上实测，标 unverified**；但"Linux 上 ENOTDIR 未被覆盖"是 verified。）

## 6. 深挖：`TestPluginContentHashMatchesRustBundleFingerprintLikeRust` 为什么 Linux 红、Windows 绿

硬编码向量（`appserver/plugin_hook_trust_test.go:20`）：`pluginBundleFingerprintVector = "sha256:1b30ece2…c44b"`，注释说明它由"独立实现"按 Rust 配方算出；而 Linux 上 Go 算出 `sha256:ffb9a8b9…08b0`。

我按 `plugin_hook_fingerprint.go:44-185` 的编码规则（域标签 `codex-plugin-bundle-v1`、长度前缀相对路径、`directory`/`file` 判别串、小端 u64 长度、内容；
跳过 `__pycache__`/`.venv`/`*.pyc`/`*.egg-info`；LIFO 升序访问）用 Python 独立实现了两遍，只改**相对路径分隔符**：

```
$ python3 /tmp/_l90_py/fp.py
sep='/'(unix)   = sha256:ffb9a8b9cd4906e02e5a1641c5d1736ce99c9f88abf96cb1ddd378f2948f08b0
sep='\\'(win)   = sha256:1b30ece2fc8dd5840ddd43127d3e0931034d3e3679e06fe398bbe82769d2c44b
```

**两个哈希都被精确复现**——用反斜杠 = 测试里那个"期望值"，用斜杠 = Go 在 Linux 上算出的值。结论：

1. **`pluginBundleFingerprintVector` 是把 Windows 路径分隔符烘进了向量**（`hooks\hooks.json` 而不是 `hooks/hooks.json`）。当时那份"独立实现"应该是在 Windows 上跑的。
2. Go 侧的 `pluginContentHash` 用的是 `filepath.Rel`/`filepath.Join`（`plugin_hook_fingerprint.go:79,115`），在 Linux 上给出 `/` 分隔——**这正是上游 Rust walker 在 Unix 上也会产出的形式**。所以**很可能是"测试向量不具备跨平台性"，而不是 Go 实现错**（此判断基于我复现的两个哈希 + 上游语义，标 `likely`，需要队长/上游确认）。
3. **但它同时暴露一个真问题**：这个"插件内容指纹"是**平台相关**的（同一 bundle 在 Windows 与 Linux 上指纹不同）。若上游 Rust 也是这样（`strip_prefix` + `to_string_lossy`），那 Go 是忠实移植；若上游用 `to_slash`/`/` 归一化，那 Go 侧就有移植偏差。**建议队长让 Windows 车道核一下上游 `plugin_fingerprint.rs` 的相对路径写法**——这条已超出我本单的只读边界。
