## `16537b20a5` #45248 - captured step settings for metadata and tool hooks

Rust now builds the Responses/MCP/extension request metadata and the pre/post
tool-use and permission-request hook payloads from the *issuing step's* captured
settings (`ExecutionMetadata::from_settings(step_context.settings)`) instead of
the turn context's initial settings, and it takes the Responses tool inventory
from the step's finalized tool router instead of a turn-scoped
`TurnMetadataState::tool_namespaces_info` write.

### What Go already has

- `turn.BuildResponsesClientMetadata` carries the lineage, sandbox, analytics,
  auto-review and Node REPL flags, and the app-server builds it per turn
  (`buildAppTurnRunConfig`), re-derives it for steer-issued requests
  (`steerClientMetadata`), and the standalone web-search and exec paths build
  their own copies.
- The hook runner serializes Rust's request shapes (`model`, `permission_mode`,
  `tool_use_id`, matcher aliases, ...).

### Divergences found in the same path (evidence)

1. **Tool-use hooks report no model.** `RuntimeRouter.turnHookAdapter` builds
   the adapter without `Model`, so `ToolHookAdapter.RunPreToolUse` /
   `RunPostToolUse` send `model: ""` in the hook input, and
   `PermissionMode` is the literal `"default"` instead of Rust's
   `hook_permission_mode(approval_policy)` (`Never` -> `bypassPermissions`).
   Rust has sent the turn's effective model here since before this commit.
2. **The turn metadata has no `model` / `reasoning_effort`.** Rust inserts both
   into the request metadata extra (`ExecutionMetadata::apply_to`); Go's
   `codexapi.ClientMetadata` has no such fields, so neither the Responses turn
   metadata nor the MCP/extension metadata carries them.
3. **The MCP/extension request metadata has no `x-codex-turn-metadata`.**
   Rust's `build_mcp_tool_call_request_meta` inserts the whole turn-metadata
   document; Go's `_meta` carries only `_codex_apps`, the plugin id, and the
   confirmation policies.
4. **PermissionRequest hooks are never invoked.** `HookRunner.RunPermissionRequest`
   and its parsing/analytics have no production caller, so Rust's
   `run_permission_request_hooks` step in the approval flow (`tools/approvals.rs`)
   has no Go counterpart.
5. **No step settings lane.** `step_model_switching` is registered in
   `features/features.go` but unimplemented: the agent loop copies the turn's
   model/effort once (`AgentLoopRequest`), so a mid-turn `turn/settings/update`
   never reaches a later sampling step. Rust's per-step capture
   (`session/step_settings.rs`, `session/step_context.rs`) is the prerequisite
   for the *step-scoped* half of #45248, and for the tool inventory
   (`tool_namespaces_info`) Go has no equivalent type at all.

### Landed in this pass

- `codexapi`: `ClientMetadata.Model` / `.ReasoningEffort` are emitted as the
  `model` and `reasoning_effort` turn-metadata keys when set (Rust's
  `ExecutionMetadata::apply_to` extra entries), and the captured pair overrides
  client-provided `responsesapi_client_metadata` / `responses_api_metadata`
  entries for those keys - Rust inserts them into the extra map after the client
  entries, and removes the effort key when the step has none. `turn.
  ResponsesClientMetadataOptions` forwards both.
- `appserver` / `exec`: the turn-config, steer, standalone web-search, and exec
  metadata sites now carry the model (and effort where the turn resolves one),
  so the request metadata describes the settings that issued the request.
- `appserver`: `turnHookAdapter` resolves the turn's effective model and
  Rust's `hook_permission_mode` mapping for the approval policy, so pre/post
  tool-use hooks report the issuing model and the correct permission mode; the
  interrupt hook uses the same mapping instead of `fmt.Sprint` of the raw
  policy.

Recorded divergence (step-scoped half): Go's metadata/hook attribution is
turn-scoped until the step-settings lane exists; a mid-turn
`turn/settings/update` is reflected in the next turn and in steer-issued
requests, not in the metadata of an already-running step.

## Permission-request hooks: the folded verdict (queue 10, first slice)

Rust's approval order is hooks -> Guardian -> user
(`Session::request_approval`): `run_permission_request_hooks` folds the matched
handlers' verdicts ("any deny wins, otherwise the last allow wins, otherwise
no verdict"), and only a decision lets the call skip the later approval stages.
Go already discovered, matched, ran, and parsed PermissionRequest handlers -
`RunPermissionRequest` existed with no production caller - but a deny only
surfaced as `HookRunResult.Blocked` and an allow was dropped, so no caller could
distinguish "hooks decided" from "hooks declined to decide".

- `appserver/hooks_runner.go`: `hookRunEffectResult` now carries a per-handler
  verdict (allow, or deny with its message, including Rust's exit-code-2 +
  stderr deny), and `mergeHookRunEffect` folds it into the new
  `HookRunResult.PermissionRequestDecision`: the first deny is final and no
  later allow can overrule it, otherwise the last allow wins, otherwise nil.
  A handler that cannot apply control effects (`hookTrustAllowsExecution` is
  false) contributes no verdict, matching Rust's `can_apply_control_effects`
  gate, while its run and output are still reported. An invalid or unparsable
  output stays a failure with no verdict, as in Rust.
- Test: `TestHookRunnerFoldsPermissionRequestDecisionLikeRust` covers
  allow+allow, allow->deny->allow, the no-handler case, the untrusted handler,
  and the exit-code-2 deny.

### The approval path is the next slice, and it is larger than the queue said

Wiring the verdict into approvals needs the approval precedence to exist first,
and an audit of the current tree shows Go's auto-review lane is incomplete:

- The Guardian reviewer has exactly three production call sites
  (`appserver/network_approval.go`, `appserver/mcp_elicitation.go`, and
  `request_permissions`' reviewer in `appserver/runtime_router.go`).
  `state.Action` values of type `command` / `execve` / `apply_patch` are only
  built in tests, so command-execution and file-change approvals never reach
  the Guardian review at all: `shellApprovalForTurn` and
  `applyPatchApprovalForTurn` send the user approval request directly (with
  `recordCommandExecutionApprovalReview` recording the user source).
- Rust instead runs hooks, then Guardian (`request_reviewer_approval`), then the
  user for every `ApprovalAction`.

So the lane is: (a) build the permission-request payload for exec / apply-patch
(tool name + matcher aliases + tool input from the invocation, run id from the
action, model and permission mode from the existing `hookTurnAttribution`),
(b) run `RunPermissionRequest` through the turn's hook metadata and apply the
verdict (allow -> approved with source hook; deny -> denied with the message),
(c) route the undecided case through the Guardian reviewer for `command` /
`execve` / `apply_patch` before the user request, then (d) the user request.
Steps (a) and (c) are recorded here as the remaining work for queue item 10
rather than left implicit.

## The account-change telemetry reload (`app-server/src/otel_reloader.rs`)

Rust watches the auth-change receiver and, after an account change, rebuilds the
OTEL provider from the latest config, reloads the log export layer, swaps the
provider, and shuts the previous one down on a blocking task - logging the
`codex.app_server.otel_reloaded` event. The tracing and metrics pipelines follow
the process-global provider the rebuild installs.

- `appserver/runtime_router.go`: `configureOtelMetrics` now splits into
  `buildOtelProvider` (resolve the latest config -> `otel_init::build_provider`)
  and `installOtelProvider` (publish the task-metrics exporter, the exported log
  handler, and the request tracer), then always starts the reloader - Rust
  spawns it next to the initial provider, including when no exporter is
  configured yet. `startOtelReloader` waits out the account handlers that
  install the new cloud loader (Rust's 50 ms sleep) before re-reading the
  config, and `reloadOtelProvider` installs the rebuilt provider and shuts the
  previous one down on its own goroutine. `Router.Close` stops the reloader
  before shutting the current provider down, and the provider field is now read
  under a lock because request spans resolve their tracer concurrently.
- Behavior note: Rust's tracing layer is permanent and only re-points when the
  rebuilt provider has a tracer provider, so a reload to a config without a
  trace exporter leaves the previous (already shut down) global provider behind.
  Go clears the installed tracer in that case; both stop exporting spans, which
  is the observable contract.
- Tests: an account change made after the config moves to a second collector
  sends the later metric to the new endpoint while the earlier metric still
  reaches the first one (the old provider's shutdown flush), and closing the
  router stops the reloader.

## Session telemetry records: the emitters that feed the log and trace pipelines

Every `SessionTelemetry` metric has a matching diagnostic record, produced by
Rust's `log_event!` / `trace_event!` / `log_and_trace_event!` macros: the
log-only half carries the event fields plus the session identity to the
`codex_otel.log_only` target, and the trace-safe half becomes an event on the
`codex_otel.trace_safe` target, which `tracing_opentelemetry` records on the
span the caller is running inside (an event with no enclosing span is dropped).
Go emitted the metric halves but none of the records, so the log pipeline had
almost no producers and the trace pipeline had no span events at all.

- `telemetry/session_telemetry.go` (new): `SessionTelemetry` with Rust's
  metadata (conversation id, agent name, auth mode, account id/email,
  originator, model/slug, app version, terminal type, log-user-prompts) and
  `LogEvent` / `TraceEvent` / `LogAndTraceEvent`. The log record keeps Rust's
  common fields (event.timestamp as RFC 3339 millis, conversation.id,
  app.version, auth_mode, originator, user.account_id, user.email,
  terminal.type, model, slug), carries no body (Rust's events set no `message`
  field), and omits the optional identity fields the session does not have
  (tracing records nothing for an absent `Option`). The trace record is
  recorded through `WithSpan` / `SpanFromContext`, and is dropped outside a
  span with Rust's `on_event` semantics. The log half is handed to the logs
  client directly rather than through the process logger: Rust routes these
  records to the OTEL log layer only, its log DB turns both targets off, and its
  stderr layer is filtered by `RUST_LOG` (default ERROR), so a per-tool-call
  record must not reach Go's terminal handler.
- `telemetry/traces_client.go` / `traces_otlp.go`: `Span.AddEvent` plus the
  OTLP `events` encoding (JSON and protobuf) so a span exports the records
  emitted inside it; a non-recording span keeps no events.
- `telemetry/logs_client.go` / `logs_otlp.go`: log records now carry their
  tracing target and the batch groups them into one scope per target, the way
  the appender bridge reports `InstrumentationScope` names; a record with no
  body omits the OTLP body instead of sending an empty string.
- `telemetry/tool_result.go`: `EmitToolResult` mirrors codex-otel's
  `emit_tool_result` - the process-global result sequence, the
  `telemetry_preview` truncation for the log record, the common fields
  (`tool_result_seq`, `tool_name`, `tool_namespace`, `call_id`, `duration_ms`,
  `success`, `output_truncated`), the log-only fields (`agent_name`,
  `arguments`, `output`, `mcp_server`, `mcp_server_origin`), and the trace-only
  fields (`arguments_length`, `output_length`, `output_line_count`,
  `tool_origin`, `mcp_tool`). `protocol.DefaultFunctionNamespace` mirrors
  `DEFAULT_FUNCTION_NAMESPACE` for the default tool namespace.
- `appserver/session_telemetry.go` (new): the per-session metadata builder (the
  active turn's model/originator and connection client name, the thread record
  as a fallback, the agent path, the account identity) and
  `emitToolResultRecords`, called by the tool-completion notifier beside the
  metrics; the arguments follow codex-tools' `ToolPayload::log_payload`
  (including core's `[plaintext arguments]` for direct plaintext calls) and the
  output is the tool body, or the failure message.
- `exec/otel_metrics.go`: the exec runtime emits the same record pair for its
  completed calls with the originator and the resolved `otel.tool_result` byte
  budget from its config.

Recorded divergences:

1. Go's tool outputs have no per-tool `log_output()` (for example the MCP
   "Wall time: X seconds\nOutput:" header), so the record's `output` is the
   tool body or the failure message.

## Step settings: the per-step tool inventory (queue 9, remaining slice)

Rust attaches `tool_namespaces_info` to the Responses metadata when
`turn_metadata_includes_tool_info && model_info.use_responses_lite`, built by
`collect_tool_namespaces_info(registry, code_mode_tool_names, model_visible_specs)`
(`core/src/tools/tool_namespaces_info.rs`) and carried on the step's finalized
router (`tools/router.rs::tool_namespaces_info`). The algorithm, so the Go port
is mechanical next time:

- direct functions come from the model-visible specs: function/freeform specs
  under `DEFAULT_FUNCTION_NAMESPACE`, namespace specs under their own namespace,
  and native tool search as `(TOOL_SEARCH_TOOL_NAME, "tool_search_tool")`.
- every non-hidden registry entry becomes one `(namespace, function)` pair - the
  tool's name with its default namespace, with tool search remapped to the
  tool-search namespace/function.
- `direct` = the pair is in the model-visible set; `code_mode_name` = the reverse
  of the code-mode name map; `deferred` = the entry is deferred **and** native
  tool search is visible **and** it has an immutable spec or search info;
  `source` = `mcp{server_name}` when the runtime reports an MCP server, else
  `harness`. Entries with none of direct/code-mode name/deferred are dropped.
- the document is `ToolNamespacesInfo = map[namespace]{name, functions:
  map[function]{name, direct, code_mode_name?, deferred, source}}` under the
  reserved `tool_namespaces_info` key.

Go's plumbing today: `turn.newCodeModeClientMetadataTransform` writes the legacy
`code_mode_tool_names` (code-mode name -> `{name, namespace}`) into a
responses-lite request's turn metadata using `router.CodeModeToolNames()`, and
`codexapi` reserves that legacy key; there is no `tool_namespaces_info` key and
no per-step inventory. Rust has removed the legacy inventory (the key stays
reserved "so callers cannot reintroduce oversized metadata") and emits
`tool_namespaces_info` instead. The Go port therefore is:

1. `codexapi`: add and reserve `ToolNamespacesInfoKey`, keep the legacy key
   reserved.
2. `tool`: expose what the collector needs (name -> spec with exposure/search/
   freeform, the model-visible spec set, the code-mode name map, and per-entry
   MCP server attribution).
3. `turn`: build the inventory from the step's router and emit it in place of
   the legacy key (the transform already runs per request, so it is the
   issuing step's router).
4. Update the tests that assert the legacy key (`turn/runtime` metadata tests,

## OTEL lead: the runtime-metrics snapshot (next OTEL slice)

Rust's `runtime_metrics` feature does **not** add CPU/memory gauges: it installs a
manual reader over the metrics already recorded, and
`SessionTelemetry::runtime_metrics_summary()` projects those records into a
`RuntimeMetricsSummary` (tool calls, api calls, streaming events, websocket
calls/events, the responses-api timings, and turn ttft/ttfm). The TUI's
chatwidget consumes that summary (`turn_runtime_metrics`,
`has_websocket_timing_metrics`), and `codex_init` gates the reader on
`features.runtime_metrics`.

Go already has the mirror type (`historycell.RuntimeMetricsSummary` with
`ApplyRuntimeMetricsDelta` in `tui/chatwidget/turn_runtime.go`), but nothing in
production feeds it, and `telemetry.OtelSettings.RuntimeMetrics` is carried
without a reader. So the Go slice is: record the in-memory totals beside the
existing metric emission (or read `state.TaskMetrics`' records), add the
summary projection, and feed the chatwidget the same way the app server reports
turn metrics.

### Landed: the runtime-metrics summary and its deltas (`telemetry`)

- `telemetry/runtime_summary.go` (new): `RuntimeMetricsSummary` mirrors Rust's
  otel type (the tool/api/streaming/websocket count+duration totals, the
  responses-api overhead/inference/iapi+service ttft/tbt fields, and the turn
  ttft/ttfm), with `IsEmpty`, `Merge` (totals add, a later non-zero timing
  replaces the earlier one) and `Subtract` (clamping at zero).
  `RuntimeMetricsSummaryFromRecords` projects `state.TaskMetrics.Records()` the
  way Rust's `from_snapshot` reads the manual reader: counters sum their
  increments, durations/histograms sum their values, matched by metric name.
- Tests: the projection matrix over every metric (plus an unrelated record and a
  nil entry), the empty cases, and the delta/merge semantics.

Still missing to finish the item: a producer that feeds the TUI. Rust's
chatwidget owns the session telemetry and calls `collect_runtime_metrics_delta()`
at turn completion, then reports the merged totals in the completion separator;
Go's `tui/chatwidget/turn_runtime.go` already accumulates deltas
(`ApplyRuntimeMetricsDelta`) and renders them, and
`historycell.RuntimeMetricsSummary` mirrors the TUI-side shape, but nothing
feeds it. The remaining wiring is: a source callback on `TurnRuntimeState`
consulted by the completion path (Rust's call site), a conversion from the
telemetry summary to the history-cell summary, and a producer on the local
session path (which owns the `state.TaskMetrics` records - `appserver`,
`model/agent_metrics.go`, and `state/runtime.go` are the current owners) that
returns the delta taken since the previous turn completion.

### Landed: the chatwidget's metrics source seam, and why the consumer side is not portable

- `tui/chatwidget/turn_runtime.go`: `TurnRuntimeState.RuntimeMetricsSource` drains
  the runtime-metrics delta since the previous call, mirroring Rust's
  `SessionTelemetry::runtime_metrics_summary` (which reads and resets the metrics
  manual reader): `OnTaskStarted` drains and discards (Rust's
  `reset_runtime_metrics`), and `OnTaskComplete` applies the delta before the
  completion separator reads the accumulated totals (Rust's
  `collect_runtime_metrics_delta`). Test:
  `TestTurnRuntimeDrainsRuntimeMetricsSourceLikeRust`.

Recorded architectural divergence for the consumer side (evidence):

1. Rust's chatwidget can drain the reader because its core session runs in the
   TUI process (`ChatWidget::session_telemetry`). Go's TUI never runs the model
   client in-process: `app/` contains no `turn.NewRuntime(...)` or
   `ResponsesAgentRunner(...)` construction (the only in-process routers there
   serve auxiliary operations such as guardian approvals), so the TUI has no
   metric records to project.
2. Rust's protocol carries no runtime-metrics field either, so delivering the
   summary from the app server would require inventing a Go-only field;
   `TurnCompletedNotification` is `threadId` + `turn` in both implementations.
   Rust's own remote-TUI mode consequently has the same gap, and Go's TUI is
   always a client of the app server.
3. The projection therefore lands where Go does hold the records (`telemetry`,
   over `state.TaskMetrics`), and the TUI-side seam is in place for an
   in-process consumer; nothing sets it in production today.

## Next OTEL slice: the logging pipeline (scoped from the current tree)

Rust's `OtelProvider` builds three pipelines from one exporter config
(`codex-rs/otel/src/provider.rs`): metrics (landed in Go), **logs**
(`build_logger` -> `SdkLoggerProvider` with the same `resolve_exporter`
resolution, OTLP gRPC endpoint/headers/TLS, and a `log_export_filter` that the
app-server's reloadable layer also uses), and traces
(`build_tracer_provider` with the span attributes and tracestate).

Go's `telemetry` package already has the metrics transports a logging pipeline
can reuse (`metrics_otlp.go` for OTLP/HTTP JSON + binary, `metrics_grpc.go` for
OTLP gRPC with the same TLS/header handling), and the process actually emits log
records: `log/slog` is used in 33 files with 137 call sites, so a `slog.Handler`
that converts records into OTLP log rows is a real wire rather than a dead seam.
The slice is therefore: (a) an OTLP log-record encoder over the existing
transports, (b) a batching `slog.Handler` with Rust's export filter (level and
target rules), (c) the provider building it from `OtelSettings.LogExporter`
(today carried but unused) and shutting it down with the metrics client, and
(d) tests over a loopback endpoint like the metrics ones. The tracing pipeline
(`build_tracer_provider`, span records from the session telemetry) is the
remaining piece after that, and the account-change reload
(`app-server/src/otel_reloader.rs`) depends on both.

## OTEL logging pipeline (the first pipeline after metrics)

Rust's `OtelProvider` builds the log pipeline from the general `otel.exporter`
setting (`provider.rs::try_new` -> `build_logger(&settings.exporter)`), with the
same exporter resolution, OTLP gRPC/HTTP transports, TLS and headers as metrics,
and exports only records whose tracing target passes
`targets::is_log_export_target` (targets starting with `codex_otel` that are not
`codex_otel.trace_safe`). Go carried the setting and had no pipeline.

- `telemetry/logs_otlp.go` (new): the OTLP logs request shape with the JSON
  encoding (`resourceLogs`/`scopeLogs`/`logRecords`, string-encoded
  `timeUnixNano`, `body.stringValue`) and the protobuf conversion built from the
  official `collector/logs/v1` definitions, plus `OTLPLogsExporter` (OTLP/HTTP
  JSON and binary) and `OTLPGRPCLogsExporter` (OTLP gRPC) reusing the metrics
  transports' TLS/header handling and per-signal timeout resolution
  (`OTEL_EXPORTER_OTLP_LOGS_TIMEOUT` over the generic variable).
- `telemetry/logs_client.go` (new): `LogsClient` with Rust's batch-processor
  shape - a bounded queue (2048, dropping with a counter), a periodic export
  loop, `Flush`, and a `Shutdown` that stops the loop and flushes - plus the
  resource attributes (`service.name`/`service.version`/`env`) the metrics
  client reports. `LogsSlogHandler` forwards exported records to the client and
  delegates every record to the wrapped handler, mapping the slog level onto the
  OTLP severity and using the record's target as the scope while dropping the
  `target` attribute; `IsLogExportTarget` mirrors `targets.rs`.
- `telemetry/otel_provider.go`: `NewOtelProvider` now builds the log client from
  `settings.Exporter` (a logs-only configuration yields a provider with
  `Logs()` set and `Metrics()` nil, as Rust does), `LogsHandler(next)` returns
  the slog handler for an enabled pipeline, and `Shutdown` flushes the log
  client before the metrics client.
- `otelinit`: the package comment and `BuildProvider` docs now describe the two
  pipelines (the log exporter is not gated on analytics, matching
  `otel_init.rs`).
- `appserver/runtime_router.go`: `configureOtelMetrics` installs the provider's
  log handler around the process logger (Rust installs the reloadable OTEL log
  layer on the app-server's tracing subscriber) and no longer returns early when
  only logs are configured; `state.SlogTerminalHandler` factors out the guard
  that keeps slog's private default handler from recursing through the standard
  log package.
- Tests: the target-filter matrix, the handler's export/delegation and batch
  shape over a loopback endpoint (resource, scope, severity, body, attributes,
  timestamp), the binary protocol round trip through the official protobuf
  types, the bounded queue's drop counter, a logs-only provider, and an
  app-server end-to-end test where a `codex_otel.log_only` record reaches a
  configured OTLP logs endpoint on shutdown.

Remaining in the OTEL lane: the session-telemetry span records that feed the
tracing pipeline (`tracing::info_span!` sites plus the `trace_event!` events
that become span events, which need the log/trace event emitters Go has not
ported yet) and the propagation of a span's trace context into the outgoing
model requests (`client.rs`'s `current_span_w3c_trace_context`).

## OTEL tracing pipeline and W3C trace context (the second pipeline)

Rust's `OtelProvider::try_new` builds three pipelines from three settings:
logs from the general `otel.exporter`, traces from `otel.trace_exporter`
(`provider.rs::build_tracer_provider`), and metrics from
`otel.metrics_exporter`. Go had the metrics and logging pipelines; the trace
settings were carried but never built.

- `telemetry/traces_otlp.go` (new): the OTLP trace request shape with the JSON
  encoding (`resourceSpans`/`scopeSpans`/`spans`, string-encoded
  `timeUnixNano`, `traceState`, `parentSpanId`) and the protobuf conversion
  built from the official `collector/trace/v1` definitions, plus
  `OTLPTracesExporter` (OTLP/HTTP JSON and binary) and
  `OTLPGRPCTracesExporter` (OTLP gRPC) reusing the metrics and logs transports'
  TLS/header handling and per-signal timeout resolution
  (`OTEL_EXPORTER_OTLP_TRACES_TIMEOUT` over the generic variable).
- `telemetry/traces_client.go` (new): `TracesClient` with the batch span
  processor's shape - a bounded queue (2048, dropping with a counter), a
  periodic export loop, `Flush`, and a `Shutdown` that stops the loop and
  flushes - plus the trace resource (`service.name`, `service.version`, `env`),
  the configured span attributes applied to every exported span, and
  `Tracer`/`Span` with parent links, kinds, status, tracestate, and the
  parent-based sampling decision (a span continuing a non-sampled remote trace
  is not exported). The instrumentation scope is the service name, because Rust
  builds its tracer with `provider.tracer(settings.service_name)`.
- `telemetry/trace_context.go` (new): `trace_context.rs` - the configured
  `otel.tracestate` members are validated (`validate_tracestate_entries` /
  `validate_tracestate_member` with the field grammar), installed
  process-globally, and merged field-by-field into a propagated tracestate
  (`merge_tracestate_entries` upserts the configured fields of an existing
  member and leaves unrelated members in place); W3C `traceparent` parsing
  follows the propagator's grammar and the `TRACEPARENT`/`TRACESTATE`
  environment pair is read once per process; spans expose
  `TraceContext`/`InjectTraceHeaders`/`SetParentContext` so a request can
  continue an inbound trace.
- `telemetry/otel_provider.go`: `NewOtelProvider` validates the trace metadata
  before building any pipeline (span attribute keys when traces are exported,
  the tracestate entries always, as `try_new` does), clears the process-global
  tracestate when no exporter is enabled, builds the trace client from
  `TraceExporter`, installs the tracestate entries, and shuts the tracer
  provider down before metrics and logs.
- `appserver`: `Request` carries the optional W3C `trace` object
  (`app-server-protocol/rpc.rs::JSONRPCRequest::trace`), the
  `app_server.request` span copies `app_server_tracing.rs`'
  `app_server_request_span_template` (the RPC method becomes the span name via
  Rust's `otel.name`, the kind is `server`, and `rpc.system`, `rpc.method`,
  `rpc.transport`, `rpc.request_id`, `app_server.connection_id`, and
  `app_server.api_version=v2` are recorded), and the inbound request trace -
  otherwise `TRACEPARENT` - becomes the span's parent, with an unusable carrier
  logged and ignored. The stdio, unix-socket, and websocket servers stamp their
  transport name; a router used in process keeps Rust's `"in-process"`.
- `otelinit`: the package docs now describe the three pipelines.
