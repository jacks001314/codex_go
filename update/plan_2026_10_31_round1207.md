# Round 1207: service-owned runtime ownership and provisioning policy (2026-10-31)

Target: Rust main at 67f0994b532b8740f14b5b738af7b7b2a915b1d6 (#42342,
#42375, #45550, #46239 residuals).

## Context

Round 1206 added the provisioning-service client, so Go can reach an installed
packaged service, but the service-owned state that client depends on had no Go
carrier: the installation record that proves sandbox ownership across package
updates, the registered-Core refresh decision, and the provisioning policy
checks. The readiness path also still answered without refreshing a registered
Core whose receipt names an older package.

## 42342 / 42375: installation record and ownership

`sandbox/windowssandbox/installation_record.go` ports the Rust record:

- `SOFTWARE\OpenAI\Codex\WindowsSandboxService` with the bounded
  `ProvisionedInstallation` `REG_SZ` value, plus the package-update-safe
  `RegisteredCore` subkey the service keeps when an old service deletes the
  parent key on uninstall.
- `InstallationRecord` (owner SID, Codex home, session, desktop installation,
  runtime registration) with the legacy `cleanup` alias still decoding into
  `cleanup_logon_pending` and a non-null journal refused, so an older record
  cannot smuggle a pre-provisioning journal into the current shape.
- `AdmitOwner` keeps the first owner and refuses a different one,
  `ReadyForPackage` compares the committed receipt with the running package,
  `CanResumeRegistration` only resumes a registration that already targeted the
  current package, and `RuntimeRegistration` returns nil without a receipt.
- `RuntimeAccountRegistration` carries the per-account receipt
  (`cleanup_logon_pending`, `account`, `user_sid`, `alias_path`), and
  `SandboxRuntimeAccount` names the managed offline/online accounts and the
  `codex-core-command-runner.exe` execution alias.

`installation_record_registry_windows.go` performs the registry read/write
through `x/sys/windows/registry` and flushes with `RegFlushKey` (the registry
package does not expose it, so `advapi32.dll` is resolved directly);
`installation_record_registry_other.go` keeps the same seams inert off Windows.

## 42375: uninstall policy

`sandbox/windowssandbox/uninstall_policy.go` ports `clean_uninstall_enabled`:
`desktop.uninstall_codex_home` in `config.toml` decides whether the service may
delete the sandbox home, a missing file keeps the OEM preinstall default, and an
unreadable or unparsable file refuses deletion.

## 46239 residual: registered-Core readiness refresh

`sandbox/windowssandbox/registered_refresh_windows.go` ports
`registered_core_needs_refresh`: the service receipt is loaded, its Codex home
must match the canonicalized home, and a `ready_package` that still satisfies
its own receipt but names a different package means the packaged Core must be
re-registered.

`appserver/windows_sandbox_runtime.go` now runs that refresh from the readiness
handler when registered Core is requested, the legacy elevated level is
effective, and no workload identity is selected. It coalesces through a
per-router `sync.Once` (Rust's `registration_refresh` OnceCell), derives
settings and listeners from the effective permission profile, refreshes through
the service, and keeps manual setup available when the refresh fails. Rust
answers readiness after the spawned refresh; Go's router has no deferred
response channel, so the refresh runs inline before the readiness snapshot is
taken.

## Provisioning policy

`sandbox/windowssandbox/servicepolicy` ports `machine_policy::validate_requirements`:
the elevated implementation must remain allowed by managed requirements, a
disabled network policy rejects local binding and proxy ports, a single managed
HTTP/SOCKS port rejects any other classified listener, and an unclassified proxy
port is rejected when the policy pins either port.

## Known gaps, deliberately not faked

Go ships no `windows-sandbox-service` server binary, so the installation record
writer, the uninstall policy and the machine-policy check have no production
caller yet: they are the pieces the future service carrier will run under its
setup lock. Package-family revalidation of an existing receipt
(`is_current_package_family`) and the staged-alias image verification remain
service-owned. Go still has no structured `NetworkProxySpec`, so readiness and
setup listeners always come from the proxy environment.
