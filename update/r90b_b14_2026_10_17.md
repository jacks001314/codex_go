## 7. 未覆盖项 / 语义差异申报（不做「已对齐」表述）

1. **中途取消**：Rust 在 `spawn_blocking` 里用 oneshot 接收端 `stop.is_closed()` 可中途放弃扫描
   （`rollout_input.rs:37-38, :55`）。Go 侧是同步调用，没有 async executor / 任务被 drop 的概念，取消只体现为
   调用方不再使用结果；扫描本身不可中断。已写进 `readRecentRolloutItems` 的 doc 注释，属结构性差异（同 #51499 先例）。
2. **计数口径**：Rust 计费的是 `serde_json::to_vec(&RolloutItem)`（带 `type` 标签的枚举序列化）长度
   （`rollout_input.rs:74`），Go 计费的是清洗后记录的 JSON 字节（`len(line.Item)` / `len(line.Payload)`）。
   两者同量级同语义（都正比于记录 JSON 体积），但没有逐字节同值保证；测试只断言可判定的不变式
   「总量 ≤ 8 MiB 且与最旧一条相加 > 8 MiB」（对齐 Rust `rollout_input_tests.rs:49-55`）。
3. **头部校验的严格度**：Rust 的 `SessionMeta` 反序列化会校验其必填字段与严格枚举（`history_mode`，
   `protocol.rs:885-889`）。Go 的 `rollout.SessionMeta` 是宽松的（`omitempty` 字符串），因此本路径只强制
   `type == "session_meta"` + `payload` 为对象 + `history_mode ∈ {空, legacy, paginated}`，**不**复刻
   serde 的必填字段校验。Rust 侧该分支同样没有独立用例（只有 `rollout_input_tests.rs:57-60` 一条 history_mode 反例），
   Go 侧把它拆成 3 条子用例。
4. **`should_persist_response_item_for_memories` 等价物**：Go 复用既有 `sanitizeMemoryResponseItem`
   （`memories/pipeline.go:587-622`），未新增第二套筛选函数；因此「丢弃哪些记录」与改动前完全一致（由 ④ 的
   逐字节 golden 兜住）。Rust 的 `clear_encrypted_content` 在 Go 侧历史上就没有对应实现，本批不变、不复刻。
5. **Windows 上的验证面**：本项不涉及平台专属行为，无「未验证 + 原因」条目；压缩路径（⑤）与 45 MB 级大文件（①）
   均在 Windows 本机真跑通过。
