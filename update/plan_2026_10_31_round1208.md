# Round 1208: registered Core launch consumes the service receipt (2026-10-31)

Target: Rust main at 67f0994b532b8740f14b5b738af7b7b2a915b1d6 (#45550).

## Context

Round 1207 taught Go to read the service installation record and refreshed a
stale registered Core before answering readiness, but the launch path still ran
the app-contained runner it inferred from the current executable. Rust never
infers that path: `spawn_runner_transport` asks
`app_package::registered_runner_alias` for the alias the service wrote into the
receipt, and fails the launch when the receipt is missing or stale. Go also
reported registered-Core setup as complete whenever the process carried any OS
package identity.

## Registered runner alias

`sandbox/windowssandbox/registered_alias.go` carries the receipt logic:

- `SandboxRuntimeAccountForUsername` maps only the two managed accounts
  (case-insensitively) to their runtime account.
- `AuthorizeRunnerReceipt` refuses a receipt owned by another SID, another Codex
  home, a retiring registration or a different package version; the messages
  match Rust's `authorize_runner_receipt`.
- `RunnerAliasForAccount` requires the account entry, the live account SID, an
  absolute `alias_path` whose file name is `codex-core-command-runner.exe`.
- `installationHomeMatches` accepts the recorded home or its symlink-resolved
  form, since the service stores the path the client sent.

`registered_alias_windows.go` adds `RegisteredRunnerAlias(codexHome, account)`:
it loads the record, requires an installed package, resolves the requesting
user's SID from the process token, authorizes the receipt and returns the alias.
The `!windows` build returns the package's unsupported error.

Wiring:

- `elevated.SpawnRequest.RegisteredAlias` carries the alias from the parent
  process; it is excluded from the runner wire payload because Rust keeps it in
  `spawn_runner_transport` too.
- `spawnRunnerTransport` runs the alias instead of the materialized or
  app-contained runner when the parent supplied one.
- `elevated_impl.go` resolves the alias for every spawn attempt (including the
  credential-refresh retry) through `registeredRunnerAliasForSpawn`; legacy
  runtimes stay on the helper and a registered Core without a receipt fails
  loudly instead of silently falling back.

## Registered setup readiness

`identity.go` replaces the "process has a package identity" shortcut with
Rust's `registered_setup_is_ready`: both managed accounts must exist and not be
disabled (UF_ACCOUNTDISABLE), the process must run from an installed package,
and the committed receipt must name that package and this Codex home.
`CurrentProcessPackageFullName` supplies the package on Windows and reports
none elsewhere.

## Known gaps, deliberately not faked

The service binary still issues the alias, staged runner image verification
(authorize_runner_receipt only checks the receipt, not the image bytes) and
service-side proxy reconciliation. Desktop uninstall registration and the
package-lifecycle uninstall path remain service-owned as well.
