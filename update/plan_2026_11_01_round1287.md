# Round 1287 — measure result buffering only for an already-buffered Result

Rust target: `67f0994b532b8740f14b5b738af7b7b2a915b1d6` (anchor worktree
`D:\qax\reagent\dev\git\codex-anchor-67f0994b`, hash `67f0994b`).

## Advanced this round

Rust #55653 attaches `result_buffered_for` to a `RuntimeResponse::Result`, and
`code-mode-runtime/src/cell_actor/types.rs` only fills it for a cell whose
completion had already been buffered when the observation arrived:

```rust
CellPhase::Completed { completed_at, .. } => Some(buffered_completion(event, completed_at)),
...
fn buffered_completion(mut event: CellEvent, completed_at: Instant) -> CellEvent {
    *result_buffered_for = completed_at.elapsed();
}
```

A completion observed live keeps `Duration::ZERO`. Go measured
`time.Since(completedAt)` unconditionally, so:

- an exec call whose script finished inside its own yield window reported a
  few hundred nanoseconds as "buffered" (Rust reports zero);
- a wait that blocked until the script completed reported the time between the
  completion and the response instead of zero;
- the in-process stdio host forwarded that spurious measurement on the wire
  (`codemode/stdio_host.go` copies `result_buffered_for_ns` from the
  observation).

## What changed

- `codemode/session_runtime.go`: `responseForCell` takes the observation's start
  time and only fills `ResultBufferedForNS` when `CompletedAt` is not after it;
  all four call sites pass their own `startedAt`.
- `tool/code_mode_exec.go`: `consumeCell` takes the observation start
  (`cell.startedAt` for exec, the wait's own entry time) and writes zero for a
  live completion while still measuring a genuinely buffered result.
- Tests: `codemode/session_live_completion_buffer_like_rust_test.go` and
  `tool/code_mode_live_completion_buffer_like_rust_test.go` assert the zero for
  live completions on both engines; the existing buffered-result tests still
  cover the non-zero case for a result that waited for retrieval.
- `parity/commits.json`: #55653 carries the new evidence.
