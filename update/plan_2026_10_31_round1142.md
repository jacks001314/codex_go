## Findings

- #47709 returns a completed resume warmup's client session to the model client
  cache, then re-checks that socket before scheduling again. The handle owns a
  single task, in-flight warmups are shared with later resumes, and the separate
  `is_websocket_prewarmed` short-circuits are gone. #47745 (also in the
  baseline) keeps the readiness check inside the warmup task: a socket that
  already carries a request and is not closed skips preparation.
- Go scheduled resume prewarms through `appserver/session_startup_prewarm.go`,
  but three things diverged: a completed same-key history prewarm short-circuited
  the next resume without re-checking the socket, base prewarms overwrote an
  in-flight warmup, and `model.ResponsesAgentRunner.Prewarm` treated any cached
  connection as warm (`conn != nil`) and therefore never repaired a socket the
  peer had closed.

## Changes

- `model/responses_agent.go`: `responsesWebsocketSession` records `requestSent`
  and an atomic `connClosed` (set by the session reader when the connection
  ends). `websocketSessionPrewarmed` mirrors Rust's
  `WebsocketSession::is_prewarmed`: cached connection, a request already sent,
  and not known closed. `Prewarm` skips preparation only for such a socket,
  otherwise drops the stale connection and redials `generate=false` with the
  full prepared input and no `previous_response_id`, and keeps the session's
  single reader running so a later resume observes the peer's close.
- `appserver/session_startup_prewarm.go`: both schedulers only share an
  in-flight warmup (`finished == false`). A completed warmup is retried so the
  socket is re-checked; when the model skipped preparation the retained response
  baseline stays in state, while a repaired socket installs the new response id.
