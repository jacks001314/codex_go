# Round 1168 audit plan (2026-10-31)

Target: Rust `main` at `cbe16d525c2d7362fc3d4726143288e932905daa`.

This round closes the last piece of `#44242`: a sampling step that switches
models is now planned from that step's captured settings, for both the tool list
the model is offered and the router its calls dispatch through.

## Rust behaviour

`codex-rs/core/src/session/mod.rs` calls
`codex-rs/core/src/session/turn.rs::built_tools` for every sampling step with
that step's `model_info`:

```rust
let tool_router = turn::built_tools(
    &sess,
    &turn_context,
    &model_info,
    &turn_environments,
    &mcp,
    &step_store,
    prepared_recommendations,
    dynamic_tools,
).await?;
```

`built_tools` re-plans `spec_plan.rs::build_tool_router` from the step's
`ModelInfo`, so `apply_patch_tool_type`, `effective_tool_mode`,
`experimental_supported_tools` (clock, `request_user_input_async`,
`send_message_to_user_async`), the catalog's confirmation policies and
description prefixes, `supports_search_tool`/`web_search_tool_type`, and image
support all follow the step. Everything else (MCP tools, sandbox, skills,
environments) is the turn's.

## Go gap

`appserver.toolRouterForTurnContext` assembles `turn.ToolRegistryOptions` once
per turn, so the model-visible tool list kept the turn-start model's
apply_patch, tool mode and catalog entries, and the dispatcher kept dispatching
through the turn-start router.

## Change

- `appserver/step_tool_plan.go` keeps the turn's assembled options together
  with `params`, `cfg` and `cwd` (newest turn per thread), and re-derives the
  model-dependent half for a later step: model, `model.ResolveToolMode`,
  `apply_patch_tool_type`, `decideClockToolEnablement`, the catalog's
  confirmation policies/description prefixes/`MCPResources`/`CodeMode`/
  `ContextManagement` entries, the catalog-declared async tools, and standalone
  web search/image generation plus the hosted tool declarations.
  `turn.BuildToolRouter` then builds the step's router; the turn's template is
  never mutated.
- `turn.RuntimeOptions.StepToolPlan` + `turn.StepToolPlan` let the runtime swap
  the router and hosted tools for the step, replay the turn's dynamic tool
  catalog on the new registry, and keep the previous plan when a rebuild fails.
- `(*ToolDispatcher).SetRouter` moves dispatch (and the executed-call tool mode)
  onto the step's router after the previous step's batch drained.
- The runtime starts on the turn's own plan and rebuilds only when the step's
  model differs from the plan currently installed, so repeated steps of one
  model never rebuild; a step that switches back to the turn's model restores
  the turn's plan instead of keeping the previous step's.
