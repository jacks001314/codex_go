## Advanced this round

`codex-rs/core/src/tools/code_mode/wait_handler.rs` parses
`ExecWaitArgs.max_tokens` as `Option<usize>` and forwards it unchanged to
`code_mode_service.wait` / `.terminate`. Only the final observation goes
through `resolve_max_tokens` (`core/src/unified_exec/mod.rs:215`), which is
`max_tokens.unwrap_or(DEFAULT_MAX_OUTPUT_TOKENS)` with
`DEFAULT_MAX_OUTPUT_TOKENS == 10_000`. An explicit `max_tokens: 0` is
therefore a real zero-token budget: it truncates the observation instead of
silently restoring the default, and it reaches the host as a zero budget.

Go collapsed both cases into an `int`:

- `tool/codeModeWaitParams.MaxTokens` was `int`, so `0` and "absent" were
  indistinguishable after decoding;
- `codeModeWaitRemoteBudget` turned every `value <= 0` into `nil` before
  calling `Wait`/`Terminate`, so a requested zero budget became "no budget";
- `codeModeWaitTokenLimit` mapped `0` back to `10000` for the local and
  client truncation paths.

A negative budget was also forwarded to the host, while Rust rejects it during
deserialization (`usize`).

## What changed

- `tool/code_mode_exec.go`: `codeModeWaitParams.MaxTokens` is now `*int`;
  the wait/terminate budget is forwarded verbatim (both the server-truncation
  host path and the local path); `codeModeWaitRemoteBudget` and
  `codeModeWaitTokenLimit` are gone in favour of the existing
  `codeModeTokenLimit` (`nil -> 10_000`, otherwise the value itself, matching
  `resolve_max_tokens`); a negative `max_tokens` is rejected with
  `max_tokens must be non-negative` before it reaches the host.
- Tests: `tool/code_mode_wait_budget_like_rust_test.go` records the budget a
  remote session receives (`0` forwarded for wait and for terminate, `nil`
  when absent, error for `-1`) and checks that a zero client budget truncates
  the observation instead of restoring the default.
