### 2. `codex tcp-tunnel` (the hidden HTTP/3 CONNECT tunnel, #45900)

Rust added `codex-rs/tcp-tunnel` plus the hidden `codex tcp-tunnel` subcommand:
a loopback TCP listener forwarded through an HTTP/3 (MASQUE-style) CONNECT
proxy, with the bearer and optional extension headers supplied only on stdin,
`LISTENING <addr>` readiness on stdout, `AUTH_UPDATED` acknowledgements, and a
listener that survives transport loss without replaying TCP streams.

Go now implements the same surface in the new `tcptunnel` package:

- `args.go`: clap-shaped argument parsing and the policy surface -
  `ParseTrustedOrigins` (exact HTTPS origins only) and `ParseProxyTarget`
  (trusted origin, credential-free authority, nonzero port), mirroring Rust's
  `parse_trusted_origins` / `ProxyTarget::parse` rules and error texts.
- `control.go`: the bounded stdin protocol (`ReadConnectHeaders` /
  `ReadAuthToken`) with Rust's limits (64 KiB tokens, 16 KiB metadata, 16
  headers, 4 KiB values), the `x-` non-forwarding header rule, duplicate
  rejection, and failures that never echo a secret.
- `tunnel.go`: the transport - a cached QUIC connection to the proxy, one
  authenticated CONNECT per local connection, `LISTENING`/`AUTH_UPDATED`
  readiness, the draining/reconnect loop with Rust's 1s->15s backoff while
  dropping (never queueing) local connections, and stream bridging with
  half-close on local EOF.
- `cli`/`app` wiring: `codex tcp-tunnel ...` reaches `tcptunnel.Run`.

Tests: the policy/admission matrix and the clap requirement matrix mirror
Rust's `proxy_policy_and_target_admission`; the control-input tests mirror
`control_input_acknowledges_bearer_renewal_with_or_without_metadata`,
`closed_parent_pipe_finishes_even_before_proxy_readiness` and
`invalid_control_input_stops_credentials_without_exposing_secrets`; and two
end-to-end tests run against a local HTTP/3 CONNECT proxy built with
`quic-go` + `http3` in the test itself - one drives the full transport
(authenticated CONNECT, bearer renewal, transport loss, reconnect, no replay)
and one drives `Run`'s whole command surface (stdin control, `LISTENING`,
`AUTH_UPDATED`, per-connection CONNECT headers).

This is the first new third-party dependency in a while
(`github.com/quic-go/quic-go` + `qpack`); it is pure Go, so the cgo-free release
path is unaffected (`go build ./...` and the existing cross-build script).

### 4. Experimental `rollout/compress` RPC (#46020)

Rust added `rollout/compress`: no parameters, requires the `experimentalApi`
capability, rejects non-local thread stores, immediately acknowledges the
trigger with `{}`, and schedules a best-effort background pass that compresses
cold local rollouts even when `features.local_thread_store_compression` is off.

- `rollout/compression.go`: `SpawnRolloutCompressionWorker` /
  `RunRolloutCompression` mirror Rust's worker - the process-scoped rollout
  maintenance lock (skip when another maintenance job holds it), the
  `rollout-compression.lock` run marker under `.tmp` with its 6-hour stale
  window, the 7-day cold-file age gate, the archived-then-active scan order, the
  sibling temp file + zstd encode + decode verification, the source-state
  recheck before publishing, the no-clobber publish that keeps the source's
  mtime, and removal of the plain file only after the compressed copy is
  published.
- `appserver`: `MethodRolloutCompress` is a top-level experimental method
  (dispatch + result type + schema signature), and the runtime router forwards
  it to the thread router's handler, so the capability gate
  (`rollout/compress requires experimentalApi capability`) and the response
  shape match.
- `appserver/rollout_migration_startup.go` +
  `RuntimeRouter` startup: `MaybeSpawnRolloutCompressionOnStartup` starts the
  startup-triggered pass when `local_thread_store_compression` is enabled,
  mirroring `thread_manager.rs`.

Tests: `rollout.TestRolloutCompressionWorker*` (cold compression + lossless
readback + mtime preservation, run-marker skip, already-compressed no-clobber),
`appserver.TestRuntimeRouterRolloutCompressSchedulesBackgroundPass` (the RPC
acknowledges and the background pass compresses a cold rollout), and
`appserver.TestRolloutCompressRequiresExperimentalCapability`.

Recorded nuance: Go has no per-rollout writer lock
(`WriterLockCoordinator`), so the worker's "skipped busy" branch has no Go
caller; the maintenance lock still excludes compression from migration and
other compression runs. Go also has no non-local thread store, so Rust's
`unsupported_thread_store_operation("rollout/compress")` rejection has no Go
counterpart (`experimental_thread_store` is not modelled at all).

### `thread/start.daybreakEnabled` (#45513)

The initial Daybreak choice for a persistent thread is now accepted by

record's metadata, rejected for ephemeral threads on both the runtime and base

`appserver.TestRuntimeRouterThreadStartRejectsDaybreakForEphemeralThreads`.

### Effective collaboration mode on resume (#45519)

Rust resumed a thread with `Default`, losing a saved Plan mode, and had no
server-reported mode for reconnecting clients. Go now:

- records the collaboration mode on the persisted thread-settings snapshot
  (`rollout.AppendThreadSettingsAppliedWithSnapshot` writes
  `thread_settings.collaboration_mode`, and the runtime router passes the
  thread's saved mode when it persists a settings update),
- restores it the way Rust does: the latest thread-owned snapshot first
  (fork-copied snapshots owned by another thread are skipped), then the legacy
  `TurnContext.collaboration_mode`, then Go's compact world-state section
  (`rollout.LatestPersistedCollaborationMode`,
  `Router.latestPersistedCollaborationMode`),
- reports it as `thread/resume.collaborationMode` (absent when nothing was
  saved), and
- seeds the resumed session's settings from the restored mode so the first turn
  after a cold resume keeps using the saved Plan mode
  (`RuntimeRouter.applyThreadResumeCollaborationMode`).

Evidence: `rollout.TestLatestPersistedCollaborationModeRestoresSavedMode` (owner
matching plus the fork-copy skip),
`rollout.TestLatestPersistedCollaborationModeFallsBackToTurnContext`,
`appserver.TestThreadResumeReportsLiveCollaborationMode` (including the
serialized `collaborationMode` document),
`appserver.TestThreadResumeRestoresPersistedCollaborationMode`, and
`appserver.TestLatestPersistedCollaborationModeReadsWorldState`.

### An accepted exec-server replacement retries the attach (found while running the suite)

Running `go test ./...` twice surfaced a real, load-sensitive failure that is
not part of the upstream range but is a Go/Rust behaviour gap:
`execserver.TestConnectAcceptedClientInitializesAndReplacesLikeRust` failed with
`accepted exec-server replacement failed: exec-server initialize failed
(-32010): session <id> is already attached to another connection` (reproduced
on demand by running six concurrent copies of the package under load).

Rust classifies `SESSION_ALREADY_ATTACHED_ERROR_CODE` as a *retryable* recovery
error (`exec-server/src/client_recovery.rs::is_retryable_recovery_error`)
because retiring a transport is asynchronous on the server, and its accepted
replacement returns after handing the socket to the recovery task, which
re-dials/re-handshakes. Go's `ReplaceAcceptedConnection` closed the old transport
and then ran a single initialize, so the handshake could race the server's
detach and fail the host's handoff (losing the host-supplied socket).

Go now mirrors the classification: `execserver.rpcServerError` carries the
JSON-RPC code (text unchanged), `isSessionAlreadyAttachedError` matches -32010,
and `attachAcceptedReplacement` retries the handshake on the same socket for
that code only, bounded by a 2 s window with 10 ms steps, while every other
failure still releases the socket. Evidence:
`execserver.TestAcceptedReplacementRetriesAlreadyAttachedLikeRust` (a scripted
first attach rejected with -32010, then a successful resume, socket kept) and
`execserver.TestAcceptedReplacementSurfacesNonRetryableAttachErrorsLikeRust`
(another code still fails the handoff and closes), plus 330 clean runs of the
previously failing test under the six-job stress harness that reproduced it.

### The catalog follows the current credentials before turns and wakeups (#46508)

Rust refreshes a catalog that belongs to other credentials before a user turn and
before a mailbox-triggered wakeup, then rechecks the active turn after discovery;
static catalogs need no refresh, and a failure or the five-second deadline leaves
the existing cache or bundled fallback.

- `model.ModelsManager` gained `RefreshAfterAuthChange` and `CatalogIdentity`
  (Rust's endpoint-client identity): the static manager is a no-op with an empty
  identity, the lazy manager forwards both, and `RemoteModelsManager` compares
  the identity the in-memory catalog was fetched under (`fetchedIdentity`, now
  recorded on fetch and cache load) with the configured identity and refreshes
  with `OnlineIfUncached` under the same five-second deadline when they differ.
  `shouldRefreshModels` mirrors Rust's gate (Codex-backend catalog, command auth,
  or API-key discovery).
- `RuntimeRouter.refreshModelCatalogAfterAuthChange` resolves the identity the
  running configuration would use (`accountScopedCatalogIdentity`, extracted
  with `resolveAccountScopedCatalogProvider` so the manager build and the
  identity cannot drift) and, when it differs from the running catalog's, rebuilds
  the account-scoped manager and claims the new catalog before use. Go's manager
  captures its identity and endpoint auth when built while Rust's endpoint client
  reads the live auth manager, so rebuilding under the current credentials is Go's
  equivalent of Rust's in-place refresh; an unresolvable identity on either side
  leaves the running manager to its own claim check, and a failed rebuild keeps
  the current catalog.

  queued-submission wakeup (`maybeDispatchQueuedSubmissionIfIdle`), where the
  wakeup rechecks the active turn before dispatching, matching Rust's ordering.

Evidence: `model.TestRemoteModelsManagerRefreshAfterAuthChangeMatchesRust` (an

## sync46 continuation: the shared OAuth protocol layer (#46318, piece 2)

`codex exec` path leaves the provider untouched, and only app-server-hosted
turns (which install the resolver) rewrite it. The app-server
`responsesAgentForTurn` wiring is the correct site.

### Landed: connection-initialized routing notification

- `RuntimeRouter.notifyWorkspaceRoutingToConnection` mirrors Rust
  `AccountRequestProcessor::notify_workspace_routing_to_connection`: once a
  connection initializes, discovery runs off the request path (spawned like
  Rust's `tokio::spawn`), and when it resolved and the credential owner
  generation is unchanged, the connection receives `account/updated`. Both
  transports call it where they already send the initialize notifications
  (`stdio` and `websocket`), since Go drops the client `initialized`
  notification before it reaches the router.

Evidence: the `appserver.TestResolveWorkspaceRoutingLikeRust`
"connection initialize notifies account updated" and "no chatgpt credential
stays silent" subtests.

### Landed: discovery consistency checks

- `workspaceRoutingConfigIdentity` captures the routing scope (effective
  `chatgpt_base_url`, `model_provider`, and the managed `chatgpt_base_url`
  requirement) before discovery. After discovery the resolver re-reads it and
  refuses the result when the credential owner generation moved or the resolved
  routing names another account (`ErrWorkspaceRoutingAccountChanged`), when the
  reload fails (`ErrWorkspaceRoutingRequirementsReload`), or when the scope
  changed (`ErrWorkspaceRoutingConfigurationChanged`) — mirroring Rust
  `AuthManager::workspace_routing` plus `read_account`'s reload guard.

Evidence: `appserver.TestRuntimeRouterWorkspaceRoutingRejectsCredentialChangeLikeRust`
(an owner switch during the request surfaces the exact Rust message) and
`appserver.TestRuntimeRouterWorkspaceRoutingRejectsConfigChangeLikeRust` (a
`model_provider` change during discovery refuses the routing).

### Landed: 401 recovery-and-retry for discovery

- `discoverWorkspaceRouting` mirrors Rust `read_account`'s recovery loop: a 401
  from accounts/check refreshes the credential owner
  (`refreshManagedAuthForStatus`) and retries discovery with the refreshed
  credential, bounded to the recovery plan's steps (3) so a persistently
  rejecting backend cannot spin; a failed refresh maps to
  `DiscoveryUnauthorized`.
- The owner-generation baseline is seeded with the resolved credential
  (`AuthChangeTracker.SeedLastAuth`), matching Rust's manager (which records its
  initial credential before observing changes), so a same-owner refresh is not
  misread as an ownership change.

Evidence: `appserver.TestRuntimeRouterWorkspaceRoutingRecoversFromUnauthorizedLikeRust`
(the stub accounts/check rejects the first credential, the token endpoint
rotates it, and discovery then succeeds with exactly one unauthorized attempt).

### Remaining nuances in this lane

Still missing versus Rust: the per-session
`WorkspaceRoutingContext.previously_routed` / session-backend bound checks
(`SessionBackendChanged`) — Go applies routing once per turn provider rather
than per request, so there is no per-session latch to consult. Rust's
`ResponsesConnectionKey` socket-reuse key is effectively satisfied in Go by
construction: the provider (origin plus routing header) is fixed for a runner,
and the websocket session cache is keyed per thread+turn, so a pooled socket
can never serve a different route.

## sync58: application network policy primitives (#45503)

The sync49 triage marked #45503 N/A; re-checking the commit showed it adds an
exported `http-client` API surface (`NetworkPolicy`, `NetworkPolicyController`,
`NetworkPolicyRevision`, `NetworkPermit`, `DestinationPolicy`,
`NetworkPolicyDenied`) with **no production caller** in Rust yet, so Go was
missing the surface rather than an integrated behaviour. Go now mirrors it in
`network/network_policy.go`:

- `DestinationPolicy` (unrestricted or restricted) permits only `https`/`wss`
  requests to exact normalized hosts, ignoring one trailing dot
  (`DestinationPolicy::allows`).
- `NetworkPolicyController` publishes an already-composed policy for the current
  revision, rejects stale publications, clears the policy on a failed load
  (`Unavailable`), and revokes permits the new policy no longer allows.
- `NetworkPolicy` is the read side transports bind to: `ForCurrentAccount` (an
  account-bound handle cannot regain access after an invalidation),
  `Changes`/`Revision`, `Invalidate`, `Acquire`, and
  `AcquireForUnsupportedSDK` (denied once any endpoint scoping or restriction
  applies).
- `NetworkPermit` retains authorization for the whole operation with a latched
  `Check`/`Revoked` and `RunWithNetworkPermit` (revocation wins over the running
  operation).

Go adaptation recorded in the code: Go has no weak references, so a transport
that abandons a permit calls `Release()` to keep the controller's tracking list
bounded (Rust relies on `Drop`); the observable revocation behaviour is
unchanged.

Evidence: `network.TestRestrictedDestinationPolicyMatchesExactSecureHosts`,
`TestNetworkPolicyInvalidationRevokesPermitsAndRejectsStalePublication`,
`TestNetworkPolicyLoadFailureRecoversCurrentAccountButNotPrevious`, and
`TestNetworkPolicyUnsupportedSDKWorkIsDeniedAndCancelled` — the four Rust
`network_policy_tests.rs` cases.

Also re-verified in this pass: #46331 (defer environment network policy
validation until after composition) is already Go's shape — Go captures the
portable policy in `EnvironmentNetworkPolicyFromConfig` and validates only the

## sync59: Code Mode tool metadata in compaction prompts (#46044)

The sync49 triage queued this item. Go implemented the *old* Rust behaviour

  flag (`compactRunnerForRecord` resolves the feature for the compaction turn's

Evidence: `turn.TestExecutedToolCallRecorderAttachesCodeModeMetadataToCompactionPromptLikeRust`

compaction request's `InputItems` carry `executed_tool_calls` / `mcp__echo`).

Remaining nuances from Rust's version: the independent `MetadataBudgetScope`

## sync61: keep remote workspace roots under server control (#46494)

Upstream was re-checked (`git fetch origin main`) and is unchanged at
`78245b47af`. This pass lands the queued #46494 item, which had two portable
halves: rejecting client-host workspace-root overrides with `--remote`, and
preserving the active session's server-resolved roots when a Session-sourced
fork happens.

### Re-checked: the remote lifecycle already omits client roots

Rust #46494 makes remote `thread/start`, `thread/resume`, and `thread/fork`
requests omit client-configured `runtimeWorkspaceRoots` (client config paths
belong to the client host) and adopt the roots the server reports instead. Go
already has that shape:

- `app.remoteThreadStartParams` / `app.remoteSideThreadForkParams` never send
  `RuntimeWorkspaceRoots` (the remote requests carry only the shared CLI
  settings), so the server resolves its defaults.
- `app.remoteTUISettingsFromResume` / `remoteTUISettingsFromStartedThread` adopt
  the response's `RuntimeWorkspaceRoots` into the TUI settings, and
  `app.dynamic_tools` seeds a resumed thread's start params from the resumed
  roots.

The picker fork (`app.remoteSessionActionHandler`'s `SessionSelectionFork`) also
omits the roots; Go's server restores the parent record's saved roots in that
case (`appserver.threadRecordRuntimeWorkspaceRoots(record, cwd, nil)`), which is
at least as strong as Rust's server default.

### Landed: `--add-dir` / `writable_roots` are rejected with `--remote`

Rust rejects client workspace-root overrides before connecting, with distinct
texts. Go now mirrors it in `app.interactiveRemoteWorkspaceRootError`, called
from `runInteractive` before the remote endpoint is resolved/connected:

- `--add-dir` + `--remote` ->
  `--add-dir is not supported with --remote. Configure additional workspace roots on the server.`
- an override for `sandbox_workspace_write.writable_roots` (either the dotted key
  or an inline `sandbox_workspace_write={writable_roots=...}` table) + `--remote`
  -> `sandbox_workspace_write.writable_roots overrides are not supported with --remote. Configure additional workspace roots on the server.`
- every other sandbox override (for example
  `sandbox_workspace_write.network_access`) still proceeds, matching Rust's
  `remote_start_allows_network_access_overrides_before_requiring_terminal`.
- Embedded launches keep explicit roots (the check only fires when `--remote` is
  set), matching Rust's `Embedded => Some(config.workspace_roots)`.
- The `codex resume|fork|archive|unarchive|delete|queue --remote` surface runs
  the same check (`sessionRemoteWorkspaceRootError`, called from
  `resolveSessionRemoteEndpoint`), since Rust validates the merged TUI CLI for
  every interactive command.

The override scan reuses `config.ParseOverrides`, the same parser the existing
legacy-sandbox-mode check uses, so it understands both `key=value` spellings.
A malformed override is left to the normal config load rather than reported here.

Evidence: `app.TestInteractiveRemoteWorkspaceRootRejectionsLikeRust` (all six
cases above, including the two network-access spellings), the fatal-exit surface
`app.TestInteractiveRemoteAddDirFailsFatalLikeRust`, and
`app.TestInteractiveRemoteNetworkAccessOverrideProceedsPastRootCheck` (the
ordering Rust pins), plus `app.TestSessionRemoteWorkspaceRootRejectionsLikeRust`
for the session commands.

### Landed: Session-sourced forks forward the active session's roots

Rust's `ForkConfigSource::Session` (the side-conversation and active-session
forks) explicitly sets `runtime_workspace_roots` because "fork does not restore
saved roots when omitted" and the fork's CWD override would otherwise drop the
server-resolved selection. Go now does the same:

- the TUI tracks the active thread's server-resolved roots
  (`tea.Model.sessionWorkspaceRoots`, populated in
  `applyThreadSettingsValues` from `appserver.Settings.RuntimeWorkspaceRoots`,
  the same settings snapshot the server sends for resume/switch and settings
  updates);
- `SideStartParams` gained `RuntimeWorkspaceRoots`, and
  `startSideConversation` forwards the tracked roots;
- `app.remoteSideThreadForkParams` and the local
  `interactiveLocalSideCoordinator.Start` set
  `ThreadForkParams.RuntimeWorkspaceRoots` from them; the local coordinator
  falls back to the parent record's saved `runtime_workspace_roots` when the TUI
  has not reported any, so an embedded side conversation with a CWD override no
  longer drops the parent's extra roots.

Evidence: `app.TestInteractiveRemoteStartSideForksAndInjectsBoundary` now asserts
the fork request carries the session's two roots alongside the CWD override;
`app.TestInteractiveLocalSideCoordinatorForksInjectsAndDeletes` asserts the
embedded side record keeps the parent's roots; and
`tea.TestSideCommandForwardsSessionWorkspaceRootsLikeRust` pins the TUI
forwarding.

### Recorded remainder

Seeding the TUI's tracked roots from the embedded `thread/start` response:
`app.interactiveStartLocalTUIThread` ignores the start response's
`RuntimeWorkspaceRoots`, so the embedded TUI only tracks roots once a settings
update arrives. The local side-coordinator fallback above already keeps the
behavior correct; seeding the model directly would remove the fallback's
dependency on stored record metadata.
