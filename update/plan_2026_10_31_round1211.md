# Round 1211: Windows sandbox service request surface (2026-10-31)

Target: Rust main at 67f0994b532b8740f14b5b738af7b7b2a915b1d6 (#42342,
service crate windows-sandbox-service).

## Context

Go ships the provisioning client but not the machine-wide service, so the
client can only reach an installed packaged service. Rust splits the service
into request validation, authenticated IPC, provisioning under an impersonated
owner and package lifecycle; this round lands the first two service-side
primitives in a new `windowsandboxservice` package.

## Request validation

`windowsandboxservice/request.go` ports Rust `ipc::request::validate_request`:

- one frame no larger than `MaxRequestBytes` (4096) and nothing after it;
- an empty frame is the dedicated "provisioning client sent an empty request"
  refusal, and a second frame is refused instead of being ignored;
- the frame must carry `PROVISIONING_PROTOCOL_VERSION`;
- `register_installation_request` only validates its home;
  `provision_sandbox_response` is refused as "expected a service request";
- homes may not be empty or contain NUL/CR/LF;
- a registration refresh requires `registered_core`;
- proxy port 0 is refused, settings and listener ports are sorted and
  deduplicated, and every listener port must appear in the proxy settings.

## Codex home pinning

`windowsandboxservice/home_windows.go` ports Rust `ipc::home::prepare_codex_home`:

- the requested path must pass `ValidateLocalDirectoryPath` and sit on a fixed
  local drive (`GetDriveTypeW`), otherwise the request is `ServiceUnavailable`
  so the client falls back to its elevated helper;
- every existing ancestor is opened through `OpenDirectoryNoReparse` with
  `FILE_TRAVERSE` so a junction cannot redirect the pinning walk;
- the home is canonicalized, revalidated and re-pinned when the canonical path
  differs from the request;
- the sandbox leaves (`.sandbox`, `.sandbox-secrets` and, for the legacy
  runtime, `.sandbox-bin`) are opened with add-file/add-subdirectory access and
  `WRITE_DAC`, receive a `CreateDirectoryGuard` that keeps them nonempty, and
  are rescanned so an existing reparse point is refused;
- `WRITE_DAC` denial on `.sandbox-bin` surfaces as
  "sandbox binary directory needs elevated repair", matching Rust's fallback for
  older elevated installs;
- registered Core pins three directories because the service owns
  `.sandbox-bin`.

`windowsandboxservice/home_other.go` keeps `ServiceUnavailable` and
`IsServiceUnavailable` buildable off Windows.

## Known gaps

The authenticated pipe listener (security descriptor, impersonation, caller
package-image authorization), the request dispatcher, the SCM service host and
package lifecycle cleanup are still missing, so no Go process serves the pipe
yet and #42342/#42375 keep their service-side residuals.

## Coverage

`request_test.go` (oversized, empty, two frames, version, control-character
home, response message, refresh without registered Core, port 0, listener
absent from settings, sorted/deduplicated normalization, register request) and
`home_windows_test.go` (legacy pinning creates and guards the three sandbox
leaves, registered Core pins three directories without `.sandbox-bin`, and
relative or UNC homes are refused).

Verified with `go build ./...`, `go test ./windowsandboxservice -count=1` and
`go test ./sandbox/windowssandbox -count=1`.
