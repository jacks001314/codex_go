## Findings

- Rust #42373 attributes exec-server process lifecycle and network-policy
  telemetry to the launch without logging argv, paths, environment values,
  output, or error text. The optional `ExecMetadata` wire type and the unified
  exec thread/tool-call propagation already existed in Go; the missing piece
  was the bounded lifecycle events and their attribution.
- Rust captures registry-issued executor identity from the authenticated
  executor connection, stores it with each process at launch, and does not
  refresh it from later process operations or reconnects. Go needs the same
  launch-time snapshot so network-policy logs and lifecycle events agree.
- Rust emits one start event after a successful spawn, one spawn-failed event
  when the spawn returns an error, and one sandbox-denied plus one exit event
  when the process finishes. Exit events carry the code and whether a
  termination was requested.
- Rust attaches launch trace/span, thread, tool-call, and executor identity to
  executor-local network-policy audit events. The controller-forwarded audit
  event uses the controller's launch metadata and `executionId`, not the
  executor process id.

## Changes

- `execserver/process_telemetry.go`: capture bounded launch attribution once
  (`trace`, `span`, thread, tool call, executor environment/registration) and
  emit `codex.exec_server.process_start`, `process_spawn_failed`,
  `sandbox_denied`, and `process_exit` with Rust Debug sandbox spellings.
- `execserver/server.go`: store the identity on the server, propagate it to
  session servers, snapshot it into `processState` at reservation, emit the
  lifecycle events for sandbox, TTY, and piped launches, and emit denial/exit
  once from `finishWithCode`. `terminate` records that termination was
  requested. Managed network proxy launches receive the same process-log
  metadata.
- `execserver/remote.go`, `execserver/remote_direct.go`: record the
  registration identity returned by Noise and direct registration, including
  the direct 409 re-registration path.
- `execserver/client.go`: retain the launch audit metadata and execution id on
  the process session and use them for controller-forwarded policy decisions.
- `execserver/trace_context.go`: parse a W3C `traceparent` into the
  exec-server request trace, rejecting malformed and all-zero identifiers.
- `tool/unified_exec.go`: carry the tool-call W3C trace into the bounded remote
  process-start context so lifecycle events inherit the launch trace.
- `network/proxy_policy.go`, `network/proxy_policy_audit.go`,
  `network/proxy_server.go`: add process-log attribution to proxy audit
  metadata, emit the executor-local policy decision even without an audit
  sink, prefer the process thread id over the conversation id, and keep the
  Rust `codex_otel.network_proxy` target.
- Tests: `execserver/process_telemetry_like_rust_test.go` covers lifecycle,
  spawn failure, sandbox denial/termination, and bounded metadata;
  `execserver/trace_context_test.go` covers W3C parsing; the client network
  policy test covers controller metadata/execution id; the network policy audit
  test covers executor identity, trace, tool-call, and conversation fallback.

## Residual

- Go emits these bounded events as `slog` records with OTEL log-export targets
  (`codex_otel.log_only` for process lifecycle and
  `codex_otel.network_proxy` for executor-local policy decisions) rather than
  exporting a dedicated OpenTelemetry span per process. The launch trace/span
  identifiers are still attached, and the existing OTEL log exporter consumes
  the records.
- Go records the process exit code as `-1` when the wait path cannot produce a
  code; Rust receives an explicit `i32` from its spawned-process result.
