## Goal

Let the synchronous Guardian reviewer consume a usable parent compaction
checkpoint across differing or unknown `comp_hash` values. Only checkpoint
usability matters; review and backend payload errors still fail closed.

## Findings

- Go carried the pre-#47272 rule in `guardianParentCompactionSeedAllowed`: a
  checkpoint was reusable only when both the producer and the reviewer model
  declared the same nonempty compatibility hash (Rust #42588).
- Go seeds review continuity with the checkpoint response ID rather than the
  checkpoint payload, and `guardianParentCompactionResponseID` already enforces
  the Rust #38980/#53691 usability and token/wire budget bounds.
- The producer hash is still recorded in compaction rollout metadata by
  `turn_runtime.go`; only the synchronous reviewer gate had to change.

## Implementation

- `appserver/guardian_reviewer.go`: `resetGuardianAfterParentCompaction` now
  drops the seed only when no usable checkpoint exists or when
  `guardian_reuse_parent_compaction` (Go thread-owned policy) is disabled;
  differing, unknown and empty producer hashes no longer prevent reuse.
  Removed `guardianParentCompactionSeedAllowed` and the reviewer-hash lookup
  from this path.
- `appserver/guardian_compaction_reuse_test.go`: replaced the
  matching-provenance unit test with a router-level test that runs
  `resetGuardianAfterParentCompaction` with a different, matching and unknown
  hash and asserts the checkpoint is seeded in every case.

## Residuals

- `guardianReviewModelHashForTurn` remains as the review-model catalog hash
  accessor used by the review-model selection contract; it no longer gates
  checkpoint reuse.
- Go has no checkpoint payload in its reviewer history, so an absent or
  oversized checkpoint preserves the existing reviewer context instead of
  failing the thread-owned review as Rust does. That fallback is the documented
  Go session model and predates #47272.
