### 3-A8.6 N-A 说明：Unix 臂 `readlink == protected_socket_path` 半无 Go 载体（正向证据）

Rust Unix 臂的**第一道**闸门是 `read_link(advertised) == protected_socket_path(advertised)`（`unix_socket.rs:306-309`），而 `protected_socket_path` 是 `sha2` 派生的受保护路径（同文件 `:329-333` 起），只有 daemon 通过 rendezvous 符号链接暴露控制 socket 时才成立。Go 侧正向证据（`grep`，在本 worktree 执行）：

```
> Select-String -Path ./**/*.go -Pattern 'protectedSocketPath|ProtectedSocket|protected_socket_path'
appserver\unix_socket_unix.go:43  // protected_socket_path), which is what rejects an SSH/socat forward bound   <- 仅本项注释
appserver\unix_socket_unix.go:45  // socket directly and Go has no protected-path derivation (no protectedSocketPath
```

即 Go 侧**没有** `protectedSocketPath` / `protected_socket_path` 派生或 rendezvous→受保护路径的等价载体；Go daemon 直接把控制 socket bind 在 advertised 路径上（`codexuds/platform_other.go` 的 `validatePrivateSocketPath` 只做 `filepath.Abs`，见下），因此不存在「advertised 是符号链接、目标是受保护路径」这一状态，`readlink` 断言在 Go 上恒不成立/无对象可判。

```
> Select-String -Path ./codexuds/platform_other.go -Pattern 'func validatePrivateSocketPath' -Context 0,7
func validatePrivateSocketPath(socketPath string) (string, *os.File, error) {
	absolute, err := filepath.Abs(strings.TrimSpace(socketPath))
	if err != nil {
		return "", nil, err
	}
	return absolute, nil, nil
}
```

`codexuds` 里唯一的符号链接逻辑是长路径 `EINVAL` 重试（`platform_other.go:77-91` 注释 + `filepath.EvalSymlinks`，配套 `uds_unix_test.go:15-48`），与「受保护路径派生」无关。

**因此 A8 在 Go 侧的落点取 Rust 用例真正能在本平台成立的两条语义**：(1) 显式默认 socket 必须存在，否则报 Rust 原文 `"the requested app-server socket is not available"`；(2) 只有**校验通过**的默认 daemon socket 才算本地（Windows 走 `ValidatePrivateSocketPath` 目录 DACL，Unix 走目录 uid/0700 契约），路径本身不再是「本地」的充分条件。Rust 用例里 `UnixListener::bind` 同一路径⇒`None`（`unix_socket_tests.rs:434-439`）对应到 Go 的等价负例是「目录未通过私有化校验⇒不 verified」（`daemon_socket_locality_like_rust_test.go:42` 与 RC-B 原文），已在测试里显式断言。

### 9.6 必须申报的机制差异（诚实版：上游形态不能逐字复刻）

上游那条测试的严格形态是「**永不发 `process/closed`**」（`:511-520` 只在 `output_stays_open == false` 时才发 closed）。Go 里做不到等价断言，原因是两处实现差异（都给 file:line）：

1. **远端退出的认定点不同** ⇒ PROBE-1 实证：我把 fixture 退回上游严格形态（去掉尾部 `process/closed`，其余不变），Go 的末轮询**返回的是存活会话而不是退出码**：

```
PROBE-1 FAIL 原文（fixture 去掉 process/closed，产品代码未改）：
    unified_exec_test.go:867: final poll = exit=false code=0 session=1 stdout="pushed remote output\n", want exit code 0 and the delayed output of the open stream
```

   机理：Go 只在 `process/closed`（或 `sandboxDenied`/`failure`）上调用 `finishWithExit` 认定退出（`tool/unified_exec.go:1571-1582`，即 `case execserver.ProcessEventClosed:`），而 Rust 在 `process/exited` 通知上就置 `state.exited(exit_code)`（`core/src/unified_exec/process.rs:570-584`），随后由 `POST_EXIT_CLOSE_WAIT_CAP = 50ms` 收尾（`process_manager.rs:1626-1633`）。所以在 Go 里「输出流仍打开」= 「`closed` 尚未到达」，即使已收到 exit 通知也算「还在跑」。
   因此落地的等价场景把 `closed` 放在**延迟输出之后**，保留上游要表达的关键时序：**exit 通知（seq2）先于末轮询、延迟输出（seq3）在末轮询期间到达**，并断言可见契约（退出码 0 = seq2 的退出码、延迟输出不丢、会话被移除、完成事件已发、无兼容读）。
   （PROBE-1 之后再跑测试会挂在 teardown：进程仍存活时 `manager.Close()` 会尝试 terminate 一个假 exec-server 不认识的远端进程。这是探针现场的现象，不留在交付物里；探针改动只存在于 `%TEMP%` 的临时副本，已还原。）

2. **Go 会对「静默 ≥1s 的事件流」补发一次 `process/read`**：`tool/unified_exec.go:1515-1532`（`events.Next` 超时 `context.DeadlineExceeded` ⇒ `reconcileRemote` ⇒ `remote.Read`）。Rust 只在 lag、seq 缺口、或缺 `sandboxDenied` 字段时读（`core/src/unified_exec/process.rs:478-488`），静默不读。所以上游的 `process_read_requests == 0`（`:1616-1622`）在 Go 侧不能逐字成立：stage-1 的静默窗口（Windows 初始 yield 下限 10s）**必然**产生 1 次 reconcile 读——注意 `reconcileRemote` 是同步的，故该窗口内只会挂起 1 个读，计数是确定的。fixture 对这一读的应答是「活动态 + `nextSeq: 0`」（`:791-803`），双重作用：(a) 不推进重放游标，避免跳掉 seq1/seq2（我在调试中实测过 `nextSeq: 3` 会把 seq1/seq2 当已读丢掉）；(b) 让**退出码与会话移除只可能来自推送的事件**——这正是本场景真正守住的东西，断言写成 `wantReads: 1`（`:648`）显式记录「这 1 次读是 Go 的静默补读，不是完成路径需要的兼容读」。

**这条差异要不要落地到产品，请队长立项判定（我不擅自改）**：要真把 (1) 搬进 Go，就得拆开「标记退出」与「拆传输」两件事（现在 `finishWithExit` 会同时关掉事件流/客户端，而延迟输出还要进 transcript，语义上与 Rust 的 `BoundedAfterExit` 冲突），影响面覆盖 `hasExited()` / `allocateProcessID` 剪枝 / `WriteStdin` 写路径 / `ListProcesses` / 事件收尾，跨 `tool`、`appserver`、`turn` 多条既有断言。按本单「小项、测试补回归、不要为它多开一轮」的定位，我把它记为**待立项候选**，正向证据（PROBE-1 原文 + Rust file:line + Go file:line）已给全。
