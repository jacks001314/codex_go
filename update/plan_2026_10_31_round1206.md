# Round 1206: provisioning service client and service-first setup (2026-10-31)

Target: Rust main at 67f0994b532b8740f14b5b738af7b7b2a915b1d6 (#46239,
Rust commit 32b54cffdd3bfa6bc018b67886a3be575afb9533).

## 46239

Rust prefers the installed Windows sandbox provisioning service during
automatic setup:

- `run_automatic_setup` filters proxy listener ports to the effective (possibly
  saved) proxy ports, asks the authenticated service to provision, and falls
  back to the UAC helper only on `Unavailable`. Service errors propagate.
- `provision_windows_sandbox_via_service` selects the helper fallback when
  workload-identity environment variables are present, because the IPC request
  cannot carry them; registered Core still refuses helper fallback.
- The app-server setup RPC runs the same service-first block when registered Core
  or the `windows_sandbox_service` feature is selected.

Go already repaired missing/disabled/password-expired accounts and removed stale
`sandbox_users.json` (Round 1189), but had no provisioning-service carrier, so
automatic setup always required the elevated helper.

Round 1206 adds `sandbox/windowssandbox/provisionservice`:

- `protocol.go`: versioned, internally tagged frames with the flattened
  `type` tag (`register_installation_request`, `provision_sandbox_request`,
  `provision_sandbox_response`), `deny_unknown_fields` provisioning payloads,
  status-tagged responses (`ok`, `unavailable`, `error`), the
  `sandbox group changed before authentication` refusal and the 1/8 MiB
  protocol/frame bounds.
- `framing.go`: little-endian length-prefixed JSON with Rust's EOF semantics.
- `identity.go`: package-family hint validation and the qualifed
  `CodexSandboxService[.Name]` / `\\.\pipe\OpenAI.CodexSandbox[.family]`
  routing.
- `client.go`: grouped provisioning/registration/deadlines, workload-identity
  routing, registered-Core no-fallback refusal, unavailable classification for
  closed or timed-out replies, the one-shot group-change reconnect, and the
  two-restart registration-refresh resume (only reply-side disconnects count).
- `transport_windows.go`: SCM status/pipe-server authentication, impersonation
  pipe open, `WaitNamedPipe` busy handling, `PeekNamedPipe` complete-frame
  polling, and restart-aware reconnection plus `StartServiceForSetup`.

Wiring:

- `windowssandbox.runAutomaticSetupForCredentials` is now the default
  `runElevatedSetupForCredentials`: it filters listeners to the desired saved
  ports, provisions through the service and falls back to the elevated helper
  only on `Unavailable`.
- `appserver/windows_sandbox_runtime.go` resolves the workspace policy first,
  starts the service for registered Core, and provisions through the service
  when registered Core or the `windows_sandbox_service` feature is selected and
  no workload identity is present.

Known gaps, deliberately not faked: Go ships no `windows-sandbox-service`
server binary, so the client only reaches an installed packaged service; the
readiness-path coalesced refresh needs `registered_core_needs_refresh` and the
service installation record (runtime ownership), which Go does not carry; Go has
no structured `NetworkProxySpec`, so listeners always come from the proxy
environment.

Coverage: `sandbox/windowssandbox/provisionservice/*_test.go` (wire shapes,
strict decoding, framing bounds, identity validation, listeners/settings
derivation, unavailable/error/group-change/restart/workload-identity state
machine, real SCM lookup without a running service) and
`sandbox/windowssandbox/provisioning_*_test.go` (saved-port filtering,
service-first automatic setup, fallback-only-on-unavailable, propagated errors).

Verified with `go build ./...`, `go test ./sandbox/... -count=1`,
`go test ./execserver -count=1` and
`go test ./appserver -run 'WindowsSandbox|WindowsSetup' -count=1`.
