# Round 1165 audit plan (2026-10-31)

Target: Rust `main` at `cbe16d525c2d7362fc3d4726143288e932905daa`.

This round closes the registration half of the `#44242` residual: Go gated
`view_image` on the turn model's input modalities, while Rust registers the
handler under `features.view_image` alone and decides at call time whether the
step's model can accept images.

## view_image is feature-gated, not model-gated

Rust `spec_plan.rs` adds `ViewImageHandler` whenever `Feature::ViewImage` is
enabled (`view_image` is a stable, default-on feature), and
`handlers/view_image.rs` rejects a call from a step whose captured model does not
list `InputModality::Image`:

```
view_image is not allowed because you do not support image inputs
```

Go previously returned nil `ViewImageOptions` for a text-only turn model in both
`appserver.viewImageOptionsForTurn` and `exec.execViewImageOptions`, which hid
the tool from the request entirely. That diverges in the direction #44242
covers: a turn that starts on a text-only model and switches to an
image-capable model never exposed `view_image`, even though the step's captured
settings allow it.

`viewImageOptionsForTurn` now keeps only the feature gate. The registered
handler's `StepSettings` resolver still reports the issuing step's modalities and
original-detail support, so a text-only step is rejected with Rust's message and
an image-capable step can request `detail: original`. An unresolvable step model
now reports text-only capabilities instead of falling back to the turn-start
assumption.

`exec.execViewImageOptions` keeps the model gate for now (its caller is a
linear `codex exec` run without a step-model switch); that file is shared with
another in-flight change, so the exec half stays recorded as residual.

## Per-step tool schema refresh

Rust rebuilds the whole registry for every step from the step's `model_info`,
so a step model with `supports_image_detail_original` advertises the `detail`
argument even when the turn's first model did not. Go finalizes the registry
once per turn. `turn.RuntimeOptions.StepToolSurface` now lets the host refresh
the model-dependent part of that registry before a later step's tool list is
built (the same hook point that already rebuilds code-mode messages and
multi-agent overrides), and `appserver.stepToolSurfaceRefresher` uses it to
re-register `view_image`'s spec snapshot from the step model.

## Tests

- `turn/step_tool_surface_like_rust_test.go`: the runtime invokes the step tool
  surface for the second sampling step with that step's model.
- `appserver/view_image_step_surface_like_rust_test.go`: a text-only model still
  advertises `view_image` and its call returns Rust's unsupported message; after
  a mid-turn switch to a model with original-detail support the step's schema
  gains `detail` and the call succeeds with `detail: original`.
- Verified with `go test ./turn ./tool -count=1`,
  `go test ./appserver -run 'ViewImage|StepToolSurface' -count=1` and
  `go test ./appserver -run 'ToolRouter|ToolSpec|Tools|Environment|ViewImage|PermissionProfile' -count=1`.

## Residual

`#44242` stays `partial`: Go still finalizes the registry once per turn, so a
step model that changes `apply_patch_tool_type`, the resolved tool mode,
clock/sleep support, or the web-search image content types keeps the turn-start
surface. `exec.execViewImageOptions` still hides `view_image` for a text-only
model until that file's in-flight change lands. Artifact-operation metrics still
lack the step model tag (emission lives in `appserver/turn_runtime.go`).
