## 7.2 B2 #54475 —— Use a synchronous mutex for remote metadata request tracking（N-A + 正向证据）

上游 `e790ce2717`：把 `RemoteFileSystem::metadata_requests` 的 **`tokio::sync::Mutex` 换成 `std::sync::Mutex`**，并集中到
`fn lock_metadata_requests(&self) -> MutexGuard<...>`（`remote_file_system.rs:76-84`，用
`unwrap_or_else(std::sync::PoisonError::into_inner)` 恢复中毒锁），同时把测试改为调用该 helper。

**判定：N-A。** 依据（正向证据）：

1. **Go 侧不存在「异步锁 → 同步锁」的迁移对象**。Rust 该 PR 改的是 Tokio 异步互斥量的**类型**；Go 的标准库互斥量 `sync.Mutex` 本来就是同步的，没有异步/中毒两种形态：
   ```
   $ git grep -c -i 'metadata_requests' -- '*.go'      # ⇒ 0 个文件命中
   $ git grep -c -i 'metadataRequests'   -- '*.go'     # ⇒ 0 个文件命中
   $ git grep -c -E 'lock_metadata_requests' -- '*.go' # ⇒ 0 个文件命中
   ```
   ⇒ Rust 的 `metadata_requests` 字段、`lock_metadata_requests()` helper 在 Go 中没有同名载体（也无需有）。
2. **Go 的等价载体一开始就是同步互斥量**，且**元数据 I/O 在锁外**（正是该 PR 用注释点明的目标语义）：
   - `execserver/client.go:42` `metadataMu sync.Mutex`；`:43` `metadata map[string]*inFlightMetadataRequest`；`:58-63` `inFlightMetadataRequest`
   - `execserver/client.go:1531-1541` `fsGetMetadataCoalesced`：只在「判归属/登记 in-flight」时持锁，`:1541` 立即 `Unlock`
   - `execserver/client.go:1543-1544` **在无锁状态下**发 `fsGetMetadataUncoalesced`
   - `execserver/client.go:1545-1557` 回填结果时才重新持锁
   - `execserver/client.go:1584-1591` `clearInFlightMetadataRequests()`（等价 Rust 的 `lock_metadata_requests().clear()` 全部 6 处调用点）
3. **Go 无锁中毒概念**：`sync.Mutex` 不会 poison，`PoisonError::into_inner` 的恢复逻辑在 Go 中无对应物，强行引入反而是无意义代码。
