# Round 1219: Service entry point and packaged binary (2026-11-01)

Target: Rust main at 67f0994b532b8740f14b5b738af7b7b2a915b1d6 (#42342, crate
windows-sandbox-service; `main.rs` and `lib::run`).

## Context

Rounds 1214-1218 built the SCM host, pipe carrier and broker, but nothing called
`RunService` in production and no service binary existed, so the crate entry
point was still missing.

## Entry point

`windowsandboxservice/run.go` adds `Run(mode)` (Rust `lib::run`) with
per-platform dispatch: the Windows arm hosts the SCM service with
`NewProvisioningBroker(NewLifecycle(), nil)`, refuses an unknown run mode, and
the other-platform arm refuses to host the service at all.
`cmd/codex-windows-sandbox-service/main.go` parses the arguments with
`ParseRunMode` and exits non-zero with the message on stderr, mirroring the Rust
binary's `main`.

`NewProvisioningBroker` now closes the lifecycle when the broker returns, so the
retained owner token and directory pins are released at service stop (Rust
`PackageLifecycle::drop`).

## Packaging

The new binary is built beside the existing Windows helpers by
`scripts/build.ps1`, `scripts/build.sh` and `npm/scripts/build-packages.mjs`,
and `scripts/windows_helpers_test.go` now asserts that packaging wiring.

## Known gaps

The installer's required-resource list and MSIX packaging do not reference the
service binary yet, and the packaged setup runner passed to the broker is still
nil until `run_elevated_provisioning_setup_with_retained_handles` is ported, so a
legacy request that needs setup still answers `ServiceUnavailable` and falls back
to the interactive helper. Native packaged cleanup, uninstall observation,
registered-runtime transactions and `provisioning/registered.rs` refresh remain
open.

## Coverage

`run_windows_test.go` covers the unknown run mode refusal; `go build` covers both
entry-point arms and `scripts` covers the packaging assertions.
