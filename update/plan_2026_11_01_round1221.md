# Round 1221: Service stop diagnostics (2026-11-01)

Target: Rust main at 67f0994b532b8740f14b5b738af7b7b2a915b1d6 (#42342,
`windows-sandbox-rs/src/service_diagnostics.rs`).

## Context

Neither the service nor the provisioning client recorded why the sandbox
service stopped, so `CodexLastStop` and the
`codex.windows_sandbox.service_stopped` telemetry were missing from Go.

## Recording

`sandbox/windowssandbox/provisionservice/service_diagnostics_windows.go` adds
`ServiceStopReason` (starting, stop-requested, shutdown, owner-removed,
startup-failed, broker-failed, registration-interrupted) and `Record`, which
writes `(reason<<32)|hresult` as the `CodexLastStop` REG_QWORD in
`HKLM\\SYSTEM\\CurrentControlSet\\Services\\<service>`. The key must already
exist — Windows removes it while uninstalling, and the record must never
recreate it — and every failure is ignored so the service lifecycle is
unaffected.

`windowsandboxservice` records `Starting` before the SCM run, `StartupFailed`
when the service never left start-pending, `BrokerFailed` otherwise, and
`StopRequested`/`Shutdown` when the broker returns normally.

## Client observation

`RecordServiceStopped` ports `service_diagnostics::record_stopped`: after the
client observes a stopped service it re-queries the SCM and re-reads the
advisory record, and only reports `codex.windows_sandbox.service_stopped` when
the stopped state, both exit codes and the record still match, so a concurrent
restart cannot be mispaired. The recorded reason and HRESULT, Win32 exit code
and service exit code are attached as attributes.
`provisionservice.queryServiceStatus` calls it whenever the service is stopped.

## Known gaps

`OwnerRemoved` stays unused until owner-aware cleanup lands, and
`RegistrationInterrupted` until the registered-runtime transaction is ported.
Native packaged cleanup, uninstall observation and `provisioning/registered.rs`
remain open.

labels, service key path, a written `CodexLastStop`, a missing service key
