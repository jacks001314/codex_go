## 4. T6 第 3 项：我独立构造的秒/ms 配对清单（不采信车道自述）

### 4.1 ★ 新发现：analytics 缺省回退把**秒**写进 `*MS` 字段（5 处，probe 可复现）

- 站点（`completedAtMS = uint64(item.CreatedAt)`）：`appserver/command_execution_analytics.go:42-43`、`appserver/file_change_analytics.go:41-42`、`appserver/mcp_dynamic_tool_analytics.go:42-43` 与 `:132-133`、`appserver/remaining_tool_item_analytics.go:129-130`；随后 `durationMS = completedAtMS - startedAtMS`（`command_execution_analytics.go:45` 等）。
- 单位证据（同一个 Go 字段有两种生产者）：
  - `appserver/protocol.go:3953` `CreatedAt: unixOrZero(item.CreatedAt)`，`unixOrZero` = `value.UTC().Unix()`（`protocol.go:6463-6469`）⇒ **秒**（BuildThreadItem / 会话条目路径）；
  - `appserver/turn_runtime.go:3385`、`:3423`（`:3383`/`:3421` 为 commandExecution）与 `:11739`（mcpToolCall）用 `...UnixMilli()` ⇒ **毫秒**（引擎内部构造路径）；
  - 另一处把该字段当 ms 消费：`appserver/turn_runtime.go:6546` `time.UnixMilli(item.CreatedAt)`。
- probe 原文（临时 `appserver/zzz_v8_probe_test.go`，复用既有 harness `newModelAttributionRouter`，**已删**）：

```
=== RUN   TestZzProbeCommandExecutionAnalyticsCreatedAtFallbackUnit
    zzz_v8_probe_test.go:33: PROBE completedAtMS=1700000000 startedAtMS=0 durationMS=(*uint64)(...)   # 输入 CreatedAt=1700000000（秒）
--- PASS: TestZzProbeCommandExecutionAnalyticsCreatedAtFallbackUnit (0.01s)
```
即 `CompletedAtMS` 收到 1.7e9（秒）而不是 1.7e12（ms），`DurationMS` 随之整体错 1000 倍。
- 上游对照：Rust reducer **没有**这个回退——`analytics/src/reducer.rs:2079-2093` 用「ItemStarted 通知里记下的 `started_at_ms`」+「ItemCompleted 通知的 `completed_at_ms`」，两者都是事件自带的 ms（`turn.rs:1822-1827` 明确 doc「Unix timestamp (milliseconds)」）。
- 可达性（如实标注）：`BuildThreadItem` 会把 `session.Item.Metadata` 合并进 `Data`（`protocol.go:3914-3920`），而 `appTimingMetadata`（`turn_runtime.go:11611-11631`）写的正是 **ms**；因此**主流已完成路径不缺 key、不走该回退**。回退只在「Data 与 Metadata 都没有开始/完成时间键但 `CreatedAt>0`」时命中（例如旧 rollout/无 metadata 的条目、`unifiedExecSessionItem` 中 `event.StartedAt` 为零的情形）。⇒ 我把它判为**可达但低频的单位错配**，建议按「telemetry-only 缺陷」登记并单独派单，**不**并入 T6 的修复范围（T6 两行修改本身 verified）。
