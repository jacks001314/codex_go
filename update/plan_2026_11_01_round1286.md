## Advanced this round

`codex-rs/code-mode-runtime/src/service.rs` resolves every in-process
observation timeout with one function:

```rust
fn resolve_yield_timeout(&self, yield_time_ms: u64) -> Duration {
    let yield_time = Duration::from_millis(yield_time_ms);
    let timeout = if yield_time >= MIN_YIELD_TIME_FOR_GRACE /* 10s */ {
        yield_time.saturating_add(YIELD_GRACE_PERIOD /* 1s */)
    } else {
        yield_time
    };
    self.options
        .cell_execution_limits
        .max_yield_time_ms
        .map(Duration::from_millis)
        .map_or(timeout, |limit| timeout.min(limit))
}
```

Both `execute` and `wait` call it, so a script that publishes output just
after a ten-second yield still lands in that observation, and
`max_yield_time_ms` caps the **graced** value.

Go only modelled the cap, and it applied it as a request-time clamp in
`SessionHost` before the runtime saw the value:

- no grace anywhere in the runtime, so - in host mode - the observation closed
  exactly at the requested yield time instead of a second later (the remote
  host already applied the grace, so the two transports disagreed);
- the tool's in-process fallback (`tool/code_mode_exec.go`) timed its exec and
  wait observations with the raw yield time as well;
- because the clamp happened before the runtime, a limit above the requested
  yield but below the graced value (e.g. yield 10000, limit 10500) produced
  11 000 ms from the clamp order Rust uses nowhere: Rust answers 10 500 ms.

## What changed

- `codemode/protocol_types.go`: `ClampYieldTimeMS` is replaced by
  `CellExecutionLimits.YieldTimeout`, mirroring `resolve_yield_timeout`
  (grace at `ProtocolMinYieldTimeForGrace` = 10 s, then the cap; a zero yield
  stays immediate, and the millisecond value is bounded so the `time.Duration`
  conversion cannot overflow).
- `codemode/session_runtime.go`: the runtime captures the session limits
  (`SetCellExecutionLimits`) and resolves both the execute and wait deadlines
  through them; the immediate-yield branch now triggers when the resolved
  timeout is zero, not only when the requested yield was zero.
- `codemode/session_host.go`: `session/open` hands the limits to the runtime
  instead of clamping each execute/wait request.
- `tool/code_mode_exec.go`: `codeModeYieldTimeout` applies the same grace to
  the in-process exec and wait timers (the remote paths keep forwarding the raw
  value, because the host applies the grace).
- Tests: `codemode/protocol_test.go` covers the resolver (grace threshold,
  cap, cap-after-grace, zero), `codemode/session_yield_grace_like_rust_test.go`
  proves the host captures the limits for its runtime and that a zero limit
  shortens a ten-second observation immediately, and
  `tool/code_mode_yield_grace_like_rust_test.go` covers the tool-side helper.
  `tool/code_mode_wait_yield_like_rust_test.go` no longer terminates a cell
  whose script awaits a bare promise (that path is the next round's gap); it
  uses a timer so the test is deterministic.
