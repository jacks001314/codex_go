## Goal

Order retained user instructions and verified answers by host acceptance order
instead of persistence order.

## Findings

- Rust reserves an acceptance sequence for user prompts and
  `request_user_input` answers, persists it as `user_input_order` metadata and on
  verified answers, and uses it for ordering, bounding, replay, and rollback;
  events without metadata keep legacy recording order.
- Go already implements the same contract:
  `retainedctx.RetainedContext.ReserveOrder` hands out the shared sequence,
  `RecordUserMessage`/`Record` consume it through `RetainedInputSource.Order`
  with a recording-order fallback, and the retained checkpoint serializes each
  ordered entry.
- Acceptance is reserved at admission time: `handleTurnSteer` appends the steer
  item immediately, the verified-answer recorder fires as soon as the host
  accepts `item/tool/requestUserInput`, and
  `annotateMissingRetainedInputOrders` assigns the shared counter to assistant
  output and calls that share it.
- `retainedctx` covers delayed queued input (`delayed old input must not evict
  newer evidence`) and `rollout/retained_context_steer_rollback_test.go` covers
  the steer-aware rollback boundary.

## Implementation

- None required. The audited Rust helper names (`AcceptedUserInputResponse`,
  `reserve_input_order`, `reserve_user_input_order`) are private plumbing whose
