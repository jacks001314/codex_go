# 2026-09-27：托管 daemon 包车道（`codex` 默认启动失败根治）

## 现象与根因

`bin/codex.exe`（以及任何 codex-go 安装）默认启动即失败：

```
ERROR: managed standalone Codex install not found at <CODEX_HOME>\packages\standalone\current\codex.exe
```

Rust #47179 把 `daemon_auto_start` 提升为 stable 且默认开启后，可用的交互式启动会
启动/复用共享后台 app-server；该 app-server 运行的是 CODEX_HOME 下**托管**的 codex
可执行文件，而不是用户敲的那个 CLI。Go 侧此前只实现了这条车道的一半：

- `install.ManagedCodexBin` 只认识 pre-dedicated 的 `packages/standalone/current/<file>`，
  且丢了 `bin/` 段，也没有 legacy 探测；对上游真正的
  `packages/app-server-daemon/current/bin/codex.exe` 视而不见；
- 完全没有 `prepare_install`：上游在启动前会把**当前 CLI 自己的包**安装进 daemon 的
  releases 目录，Go 没有这一步，因此连打包好的 CLI 也必然失败；
- 报错文案在上游全树里不存在（上游为
  `daemon executable not found at …; repair the existing installation, or run
  \`codex app-server daemon start\`…`）；
- `EnsureSupportedPlatform` 认为 Windows 不支持 daemon（上游
  `ensure_supported_platform` 在 unix|windows 均返回 Ok）；
- `daemonAutoStartFeature` 不参与本次启动的 CLI override，`-c
  features.daemon_auto_start=false` 无效（上游读的是已叠加 override 的 `Config`）。

## 记录的 Go-only 差异（必须随行测试冻结）

1. **Windows 对端 PID 校验（已修复，不再是差异）**：根因是控制码写错——
   `codexuds/platform_windows.go` 用了 `0x58000000`（只含 `IOC_OUT|IOC_VENDOR`，
   功能码为 0），而 afunix.h 的 `SIO_AF_UNIX_GETPEERPID = _WSAIOR(IOC_VENDOR, 256)`
   = `0x58000100`（与 Rust `windows_sys` 的常量 `1476395264` 一致）。功能码为 0 时
   Windows 一律返回 `WSAEOPNOTSUPP`，因此此前“Go 创建的 socket 取不到对端 PID”
   与 AFD endpoint、重叠 I/O、阻塞模式都无关（那些排除方向都是被这个错误常量误导）。
   修正后同进程/跨进程的 AF_UNIX 对端都能取到 PID。`appserverdaemon` 也随之**取消**
   对 `ErrPeerIdentityUnavailable` 的容忍，恢复 Rust 的严格语义：客户端在任何对端
   校验失败时都拒绝连接（Rust 用 `?` / `is_err()`，TUI 探针用 `.ok()?`）。
   用例：`codexuds.TestEnsureNonElevatedPeerNamesThePeerLikeRust`。
2. **AF_UNIX `sun_path` 长度**：Windows 侧路径必须小于 108 字节，否则 Winsock 在 bind
   时报 `EINVAL`。上游 `uds_windows` 会先给出 `path must be shorter than SUN_LEN`，
   Go 侧现在用同一文案拒绝（`codexuds.CheckSocketPath`）。这也意味着过长的
   `CODEX_HOME` 在两端都无法使用共享 daemon（上游同样如此）。
3. **Unix 侧仍走既有实现**：`codexuds` 的 Unix 分支只做 0700 目录与 stale 清理，
   与既有 `appserver/unix_socket_unix.go` 行为一致；上游 Unix 的
   `/tmp/codex-daemon-<uid>/<sha256>` rendezvous 方案未移植（本仓库原本就没有）。
4. **包校验按清单声明**：Rust 硬编码 `codex-resources`/`codex-path` 目录名（以及
   Linux 的 `codex-resources/bwrap`）；本地构建的 codex-go 包把这些目录放在
   entrypoint 同级的 `bin/` 下，因此校验读取清单声明的 `resourcesDir`/`pathDir`。
   其余要求与上游一致：entrypoint、同目录的 code-mode host、`pathDir` 下的 `rg`。
   **`rg` 现在随包分发**（`third_party/ripgrep` 固定版本 15.2.0 + sha256，
   `prepare_ripgrep.py` 解包到 `build/<goos>-<goarch>/bin/rg[.exe]`，`build.ps1`/
   `build.sh`/`build-packages.mjs` 再放进 `codex-path/` 并在清单里声明 `pathDir`），
   与 Rust 包一致；只有 Linux 的 `bwrap` 仍取自 PATH（`sandbox` 的系统 bwrap 检查）。
5. **`daemon update` 的两种入口都已移植**：`--from-cli`（`InstallMode::Replace`）与
   不带 `--from-cli` 的手动更新 socket（`update\n` + `Ok/Err` JSON + restore-release）。
   仍未移植的是 Rust 的 `migration.rs`（legacy pid 文件 + supported 时改走迁移程序），
   因为 Go 没有 release-installer/daemon-migration 程序（见下）。
6. **daemon 状态目录 DACL 的修复语义**：Rust 对已存在但不符合私有契约的目录**直接拒绝**
   （`prepare_private_socket_directory`）；codex-go 早期版本用默认 DACL 创建过该目录，
   因此 Go 在“属主是当前用户且不是 reparse point”时**就地套用私有 DACL**再校验，
   其余情况仍拒绝。这是为升级路径引入的差异（否则老用户的 daemon 会直接不可用）。
7. **`app-server daemon --help` 文案**：Go 侧手写近似 clap 输出（上游由 clap 生成）；
   功能上用 `pid-update-loop --help` 的成功退出即可满足上游的支持性探针。
8. **updater socket 的路径长度**：与上游一致，`<CODEX_HOME>/app-server-daemon/daemon-updater.sock`
   受 AF_UNIX `sun_path` 108 字节限制；过长的 CODEX_HOME 会让 updater 无法绑定
   （上游同样如此）。
9. **摘要算法**：包树与可执行身份用 sha256 流式摘要（上游 blake3）；两者仅本地自洽
   使用，不与 Rust 交换。
10. **entrypoint 拼写**：本地构建的包把可执行文件放在包根（WinGet 风格，由
   `install.PackageLayoutFromExe` 的包根分支识别），因此 `prepare` 接受
   `codex(.exe)` 与 `bin/codex(.exe)` 两种清单拼写。

## 本轮续做（2026-09-27 第三段：手动更新 socket 车道）

### 已落地

- **带 guard 的安装器调用**（`installer.go` + `installer_windows.go`/`installer_other.go`）：
  抓取发布安装脚本 → 断言脚本含 `CODEX_INSTALL_IF_LATEST`/`CODEX_INSTALL_IF_CURRENT`
  与（daemon 拥有的包根）`CODEX_INSTALL_DAEMON_ONLY` → 以 guard 环境变量执行
  （`CODEX_HOME`、`CODEX_RELEASE=latest`、`CODEX_NON_INTERACTIVE=1`、
  `CODEX_INSTALL_DEFER_SELECTION`）；Windows 仍走既有的 kill-on-close Job Object +
  挂起启动 + `NtResumeProcess`，脚本从 stdin 交给 PowerShell，Unix 用 `/bin/sh -s` 并
  独立进程组。原先“无 guard”的 `InstallLatestStandalone` 已删除，避免旁路。
- **触发器与选择语义**（`update_lane.go`）：`UpdateTrigger{Scheduled,Manual,RestoreProduction}`
  （含单次生效的 `--restore-release`）、`selectedRelease`、`releaseSelectionUnstable`、
  `manualUpdateSupported`（stable 发布 或 releases/ 内的完整选择 = 允许手动更新，
  后者正是“解 pin”）、`nextUpdateDelay`（读 `updater` 设置，关闭自动更新即退出）、
  以及三种结果的文案。
- **updater 提供请求 socket**（`update_loop.go`）：在 `update pid 文件`旁绑定
  `<...>.sock`（先经 `codexuds` 私有目录），只接受 `update\n`（5s 内读满 7 字节），
  回写 `{"Ok":UpdateOutput}` 或 `{"Err":...}`（对齐 Rust `Result<UpdateOutput,String>`
  的 serde 形状），并按 disposition 决定继续/退出；`--restore-release` 的授权只能用一次，
  定时器分支在授权未使用或自动更新被关闭时退出（对应 Rust 的 one-shot worker）。
- **客户端**（`manual_update.go`）：`RequestManualUpdate` 先直连；失败则在 operation lock
  下重试，然后按 `manualUpdateSupported` 决定返回 unsupported 还是停掉 updater、以
  **当前 CLI** 启动一次性 worker（带 `--restore-release <pinned>`）并等待 ≤30s 的连接，
  再走同一条 `update\n` 交换；连接后沿用 `codexuds` 对端策略。
- **重启语义**：新增 `RestartIfBinaryOrVersionChanged`（按运行实例的 executable identity
  降级为 IfVersionChanged 或升级为 Always），并在 `TryRestartIfRunning` 加上上游的
  “选中的 release 仍是 latest-channel 才允许重启”守卫；手动/恢复触发用
  `Manual`/`RestoreProduction` 的重启模式，调度触发保持原语义；`updateOnce` 现在返回
  重启结果与“需要 reexec 的托管二进制”，由调用方决定何时替换（手动应答先回包再交接）。
- **CLI/装配**：`app-server daemon update`（不带 `--from-cli`）接到手动车道；
  `pid-update-loop --restore-release <name> --check-package-ownership`；
  `app-server daemon <cmd> --help`（上游的 `pid-update-loop --help` **支持性探针**要求
  exit 0，此前直接报错会导致 updater 永不启动）。
- **状态目录的私有 DACL**：daemon 状态目录（pid/锁/设置/updater socket 同处）现在统一经
  `codexuds.PreparePrivateSocketDirectory` 创建/校验；对**旧版本用默认 DACL 创建的目录**
  做一次性修复（见差异 9）。

## 本轮识别出的重大缺口（第十三段，进行中）：控制套接字其实是 WebSocket

### 证据（Rust 侧）

对照 `codex-rs` 发现：**Rust 的 app-server 控制套接字走 WebSocket**，而 Go 侧
（`appserver/unix_socket*.go` 的 `serveUnixSocketConnection` → `serveJSONLineConnection`、
`appserverdaemon/client.go` 的 JSONL 编解码、`app/remote_tui.go` 的
`newRemoteJSONLineTransport`）走的是**按行 JSON**。两者线协议不同：

- `app-server-transport/src/transport/unix_socket.rs`：模块文档即
  “Control socket startup, guarded rendezvous paths, and WebSocket acceptance”；
  每个 accept 都 `accept_hdr_async_with_config(...)` 升级成 websocket，再
  `run_websocket_connection(...)`（与 `ws://` 传输同一个连接处理函数）。
- 同一文件里的 `run_daemon_shutdown`：当请求路径是 `/daemon/shutdown` 且该服务是
  managed daemon（`DaemonShutdownAccess::Managed`）时，读一条等于自身 PID 的文本消息、
  回写同一 PID，然后发 `TransportEvent::DaemonShutdown`。
- 客户端 `app-server-client/src/remote.rs`：`connect_unix_socket_endpoint` 先
  `UnixStream::connect`、Windows 上 `ensure_non_elevated_peer`，然后用
  `UDS_WEBSOCKET_HANDSHAKE_URL = "ws://localhost/rpc"` 做 websocket 握手。
- `app-server-daemon/src/client.rs::request_shutdown` 也走同一条 websocket 通道
  （`connect_at(socket_path, "ws://localhost/daemon/shutdown")`…回显 PID 校验）。
- `app-server-transport/src/transport/websocket.rs`：`ws://` 服务端用
  `/readyz` `/healthz` + `fallback(any(websocket_upgrade_handler))`，即**任意路径**
  都当升级处理（客户端用 `/rpc`）；Go 的 `WebSocketServer.ServeHTTP` 目前只接受
  `""`/`"/"`，其它路径 404。

### 影响

- Go 的 CLI 无法复用 **Rust 启动的共享 daemon**，反之亦然：probe/initialize 的帧格式
  不同（JSONL vs websocket）。这正好命中本车道的前提——“共享后台 app-server 可能由
  安装器换成本机（Rust）包”，以及用户最初“运行 `bin/codex.exe` 失败”的场景。
- Rust 的 managed app-server 优雅停止走 `/daemon/shutdown` 握手；Go 用的是
  `CODEX_DAEMON_SHUTDOWN_FILE`。两者是不同机制（Rust 的该文件只服务*分离的 updater*，
  且内容是**纯十进制 PID 文本**，而 Go 的 `daemonShutdownRequest` 是 JSON
  `{"pid":N}`——文件格式本身也不一致）。

- 用例：`appserverdaemon/recovery_test.go`（stop / fresh-start / restart 三种路径
  都会清掉预置的恢复快照）；`stubLifecycleManagedDaemon` 增加探针桩。
