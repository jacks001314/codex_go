# codex_go 向 Rust Codex 100% 对齐计划

> 制定日期：2026-07-31  
> Rust 冻结基线：`codex@4642370542739d5dd080b0c87a9de06a6435d3db`  
> Go 起始基线：`codex_go@70d8f0bfbd2938132c48c347643c1e3de6761c7e`  
> 计划状态：待实施  
> 目标：在冻结基线上实现可验证、无例外的外部行为与数据兼容

## 1. 结论与原则

当前 Go 版已经覆盖了相当多的 CLI、App Server、工具执行和 SDK 协议场景，现有全量 Go 测试也能通过，但仍不能称为 100% 对齐。主要原因不是零散方法缺失，而是以下系统性差异：

1. Go 版没有 Rust 的五库 `StateRuntime`，会话、线程投影、日志、目标、记忆和 agent 关系的持久化模型不同。
2. Go 的 schema 生成器只输出方法和类型名目录，不是 Rust 发布的完整 JSON Schema 与 TypeScript 绑定；现有测试无法发现这种差异。
3. code mode、realtime、memory worker、sandbox violation、remote metadata 并发合并等运行时能力仍缺失或仅有替代实现。
4. 当前对齐记录保留了 `partial` 和 `intentional_difference`，这与严格的 100% 目标不相容。
5. Go 内嵌 SQLite 是 3.50.4，低于 Rust 明确要求的 3.51.3 安全下限，是持久化对齐前必须解除的硬阻断。

本计划中的“100% 对齐”不是要求 Go 与 Rust 源代码、crate/package 划分或实现语言逐行相同，而是要求在固定 Rust SHA 上，以下维度全部一致：

- CLI 命令、参数、配置、默认值、帮助文本和退出码；
- App Server、Exec Server、MCP、SDK 和模型请求的线协议与完整 schema；
- 事件顺序、流式行为、取消、重试、并发、审批和错误语义；
- `CODEX_HOME` 下的文件布局、SQLite schema、迁移记录和跨实现读写能力；
- 崩溃恢复、损坏恢复、降级、锁竞争和旧版本打开新数据库的行为；
- Windows、Linux、macOS 支持矩阵中 Rust 支持的可观察行为；
- TUI/PTY 中用户可观察的状态、交互和渲染结果；
- 安全边界和权限收敛语义。

允许 Go 使用符合语言习惯的内部实现，但必须有差分证据证明没有外部影响。最终认证时必须满足：

- `missing = 0`；
- `partial = 0`；
- `intentional_difference = 0`；
- 行为豁免和安全豁免均为 0；
- 只允许把纯 Rust 构建系统、crate 重排等项目标记为 `N/A`，且要附带“无协议、数据、行为或平台影响”的证据。

Rust `main` 会继续变化，因此“100%”必须绑定到具体 SHA。新上游提交进入独立 intake 队列，不得在当前认证周期中悄悄移动基线。

### 2.2 对齐记录的问题

现有 `parity.json` 将以下差异视为可接受：

- exec completion 的回填架构不同；
- TUI bootstrap 使用本地状态而不是并行请求；
- realtime WebRTC crate 删除被视为结构差异；
- Go 的 Windows 取消行为强于 Rust；
- native macOS artifact 尚未纳入门禁；
- 多 SQLite、logs SQLite、memory worker 等历史上被判定为不移植。

严格认证不能继承这些结论。处理原则如下：

1. 内部架构不同可以保留，但必须通过原始事件 trace、故障注入和性能边界证明行为等价，并将项目改记为 `equivalent`，不能继续作为例外。
2. Go 更强的 Windows 取消行为不能直接计入“与 Rust 100% 相同”。优先推动 Rust 修复并在新冻结基线共同对齐；不得为了认证主动降低安全性。如果上游未解决，该项是发布阻断，目标只能标记为“小于 100%”。
3. Rust 删除 crate 属于内部结构时可标记 `N/A`，但 realtime 的实际服务、协议和传输能力仍必须逐项验证，不能借 crate 删除免除功能对齐。
4. macOS 原生验证缺失时，不得签发全平台 100% 认证。

## 5. 目标架构

### 5.1 对齐控制面

新增机器可读的对齐清单，代替只靠文档判断：

- `parity/baseline.json`：Rust/Go SHA、构建环境、SQLite 版本、schema hash；
- `parity/commits.json`：冻结区间内每个 Rust commit 的分类、影响域、Go PR、测试证据；
- `parity/domains.json`：每个能力域的 `missing/partial/equivalent/complete/N-A` 状态；
- `parity/contracts/`：CLI、config、feature、App Server、Exec Server、MCP、DB schema 的规范化快照；
- `parity/evidence/<run-id>/`：差分事件、数据库快照、SDK 结果、平台信息和失败日志。

所有 manifest 由 CI 校验：冻结范围不能漏 commit，`complete` 必须引用实际测试产物，认证分支不允许存在 waiver。

### 5.2 Go StateRuntime

在 Go 增加单一 `StateRuntime` 所有权边界，负责：

1. 定位 `CODEX_HOME`，按 Rust 文件名打开 `state_5.sqlite`、`logs_2.sqlite`、`goals_1.sqlite`、`memories_1.sqlite`，按需打开 `thread_history_1.sqlite`。
2. 统一设置 WAL、`synchronous=NORMAL`、incremental auto-vacuum、5 秒 busy timeout、最大连接数 5，并验证实际 PRAGMA。
3. 运行与 sqlx 兼容的 `_sqlx_migrations`，保留 Rust migration version、description、success、checksum、execution time 和 `ignore_missing=true` 语义。
4. 实现 Rust 对 38/39 recency migration 的修复逻辑。
5. 单库失败时隔离恢复，不连带删除或重建其他库；备份故障 DB 及 `-wal/-shm` 到 `db-backups/sqlite-<timestamp>-<seq>`。
6. 提供受控的连接/事务 API，禁止业务包自行拼接数据库路径或创建 Go 私有表。
7. 管理启动 backfill、reconcile、lease/watermark、read repair 和有序关闭。

SQLite driver 的升级必须先于任何数据库写入上线。CI 在每个目标产物启动时查询并断言版本，不能只相信 `go.mod`。

### 5.3 Rollout 与线程存储

确立和 Rust 相同的权威关系：

```text
模型/工具事件
    -> 先追加并 flush rollout JSONL（唯一权威日志）
    -> 再事务更新 SQLite 投影（允许落后，不允许领先）
    -> 查询优先投影；发现缺口时 read repair/reconcile
```

新增统一 `ThreadStore`，由 CLI、App Server、TUI、goal、agent graph、memory 和 external import 共同使用。会话落盘统一到：

```text
~/.codex/sessions/YYYY/MM/DD/rollout-<timestamp>-<thread-id>.jsonl
~/.codex/archived_sessions/...
~/.codex/session_index.jsonl
```

历史 Go `sessions/<thread-id>.json` snapshot 在至少一个稳定兼容周期内只读保留，用于迁移和回滚；不得与首个 SQLite 发布一起删除。

### 5.4 协议 oracle

Rust 冻结基线的预计算 stable/experimental schema 和 TypeScript bindings 作为协议 oracle：

1. Go 发布包携带同名、同布局的完整导出，不再用方法名目录冒充 JSON Schema。
2. 生成器输出先做 canonical JSON 结构比较，再比较压缩解包后的内容和公开文件 hash。
3. Go 运行时所有请求、响应和通知都必须能通过其对应完整 schema 校验。
4. 反向检查 schema 中每个 method/type 是否有 Go encoder/decoder 或明确的服务端方向限定，禁止“schema 有、运行时无”的空对齐。
5. TS SDK 编译测试从静态文件存在性升级为使用生成 bindings 构建并运行全场景。

### 5.5 独立运行时服务

- code mode：生产路径只使用 standalone host，完整对齐发现、版本握手、stdio/IPC、隔离、crash、重连、buffered exec、一次性 warning、optional fallback 和 `code_mode_only` fail-closed。
- realtime：实现实际 WebSocket/WebRTC/sideband 传输，禁止合成 answer 或仅以内存状态机通过测试。
- memory：按 Rust 的 job/lease/watermark 模型实现 stage1、phase2、consolidation、selection 和 retry；不允许只提供清库和 citation API。
- exec/sandbox：统一 canonical permission profile、sandbox backend 枚举和 normalized violation，所有进程创建路径只能从该边界进入。

## 6. 数据迁移方案

### 6.1 迁移前置条件

迁移代码进入可发布分支前必须满足：

- 目标平台 SQLite 均 >= 3.51.3；
- 五库完整 migration fixture 与 Rust checksum 已冻结；
- Go 在临时 `CODEX_HOME` 中创建的库可被 Rust 基线打开；
- Rust 创建和升级的库可被 Go 打开；
- 同时存在 DB、WAL、SHM、损坏文件、只读目录和阻塞同名文件的恢复测试已通过；
- 迁移不创建 Rust 未知的 Go-only table/migration。

### 6.2 分阶段切换

1. **只读盘点**：扫描旧 JSON snapshot、flat/nested rollout、`.zst`、archive、session index 和既有 Rust DB，生成可重复的 inventory，不写数据。
2. **数据库准备**：创建/升级五库，验证 migration checksum、PRAGMA 和版本；失败时保持旧读取路径。
3. **历史导入**：按 thread 和 rollout byte offset 幂等导入，记录 watermark；snapshot 仅在 rollout 不完整时作为受标记的补充源。
4. **shadow projection**：所有新事件先写 rollout，再写 SQLite，但读取仍走旧路径；后台逐 thread 比较查询结果。
5. **read preference 切换**：shadow 比较连续通过后优先读 SQLite，发现缺口自动回退 rollout 并触发 read repair。
6. **消费者迁移**：依次切 goals、agent graph、logs、external imports、remote control 和 memory，避免一次提交跨越全部所有权边界。
7. **旧 snapshot 冻结**：停止新写 `<thread-id>.json`，保留只读与显式回退一个稳定周期；确认无回退后再单独规划清理，不在本计划自动删除。

### 6.3 并发与幂等

- backfill 使用与 Rust 相同的 lease、watermark 和 30 秒启动 gate；
- 每一条 projection 以 thread、rollout identity、byte offset/end ordinal 作为幂等边界；
- flush rollout 成功前不得提交 SQLite；SQLite 提交失败可重放；
- 多 Go 进程、Go/Rust 混合进程和后台 worker 同时打开时必须依靠 WAL、busy timeout 和事务约束收敛；
- malformed/rejected line 保持 ordinal 处理规则，不因重试改变后续编号；
- 无效时间戳项目延迟处理，不能永久推进超过它的错误水位。

### 6.4 跨实现兼容矩阵

每种库和会话格式都执行以下序列：

| 序列 | 操作 |
|---|---|
| Rust -> Go | Rust 创建/写入/升级，Go 查询、追加、归档、恢复 |
| Go -> Rust | Go 创建/写入/升级，Rust 查询、追加、归档、恢复 |
| Rust -> Go -> Rust | 验证 Go 写入不破坏 Rust checksum、索引和 reducer |
| Go -> Rust -> Go | 验证 Rust 新写入可触发 Go reconcile/read repair |
| 混合并发 | 两实现并发读写不同 thread、同 thread、同 job lease |
| 版本降级 | 含未知较新 migration 的库由旧实现只读取/安全打开 |

## 8. 测试与证明体系

### 8.1 静态 contract 差分

- Rust commit range 100% 分类；
- CLI command/flag/default/help/exit code 快照；
- config key/type/default/deprecation 快照；
- feature registry 精确集合；
- App Server、Exec Server、MCP 稳定/实验 schema；
- TypeScript bindings 编译和 API surface；
- 五库 `sqlite_master`、index、trigger、migration version/checksum、PRAGMA；
- `CODEX_HOME` 文件名、目录和归档布局。

任何集合 diff 均直接失败，不允许维护 ignore list。

### 8.2 确定性协议差分

建立可脚本化的 mock Responses API 和 fake clock，Rust/Go 接收相同输入：

- 记录原始 HTTP body、headers、SSE frame、工具调用和 App Server/SDK 事件；
- 仅归一化明确非语义字段，如随机 UUID、临时绝对路径和单调时钟值；
- 比较事件类型、顺序、次数、载荷、错误、取消、重试和最终 workspace 副作用；
- 覆盖 approval、skills、MCP、code mode、image、web/realtime、compaction、review、resume/fork、multi-agent、sandbox 和 malformed input；
- 对所有 feature 分别测试默认关闭、显式开启和依赖冲突。

### 8.3 SDK 真实端到端

在既有 42 个官方 TypeScript SDK 场景上扩展：

- 完整稳定/实验方法表；
- reconnect/resume、sampling retry、取消竞态；
- permission profile 和远程审批；
- code mode standalone host crash/restart；
- realtime sideband；
- 跨实现共享 `CODEX_HOME`；
- 迁移前旧数据、迁移中断和迁移后降级。

真实模型测试受非确定性影响，只用于验证实际集成；协议精确性以 deterministic mock 差分为主。认证前真实 E2E 必须连续三次全绿并保存完整原始产物。

### 8.4 数据与故障注入

在每个 durability 边界注入崩溃：

- JSONL 写入前、部分写入、flush 后；
- SQLite begin 后、单行后、commit 前、commit 后；
- migration 中间、备份中间、WAL checkpoint 中间；
- backfill lease 获取后、续约前、watermark 更新前后；
- memory job claim、模型调用、结果提交各阶段；
- DB locked、disk full、read-only、corrupt page、坏 WAL/SHM；
- malformed JSON、非法 UTF-8、缺 ordinal、重复 ordinal、坏 timestamp。

验证不变量：rollout 从不落后于已提交 projection，重复恢复不产生重复项，单库损坏不影响其余库，旧二进制不会破坏含新迁移的数据库。

### 8.5 并发、性能与资源

- `go test -race ./...`；
- reducer、JSONL parser、schema decoder 和 protocol frame fuzz；
- remote metadata 同 key/不同 key/cancel/error 并发；
- SQLite 多进程读写和 mixed Rust/Go writer；
- streaming 大量 frame 与 invalid UTF-8 benchmark；
- 百万事件 backfill、启动 gate、history 查询和日志 retention；
- 长时间 realtime/code host 重连、goroutine/FD/连接泄漏；
- 与 Rust 基线比较 p50/p95、内存和启动时间，任何明显回退须修复或证明 Rust 同样行为。

### 8.6 平台矩阵

| 平台 | 必测 |
|---|---|
| Windows amd64/arm64 | restricted token、slash-tmp、盘符/UNC、ConPTY、cancel/kill tree、SQLite WAL |
| Linux amd64/arm64 | seccomp、PTY、signals、symlink、filesystem/network violation |
| macOS amd64/arm64 | Seatbelt、PTY、codesign/产物、SQLite WAL、权限 profile |

只有 Rust 基线明确不发布的平台/架构才能从 certification matrix 排除，且必须在 manifest 中给出上游证据。

## 9. 发布、回滚与数据安全

1. 第一个带新持久化架构的版本默认启用 inventory 和 shadow projection，但保留旧读路径。
2. 每个数据库首次 migration 前独立备份 DB、WAL、SHM；备份失败则拒绝迁移，不能“尽力而为”继续写。
3. rollout JSONL 始终是权威恢复源；数据库可删除重建，但不能以数据库覆盖较新的 rollout。
4. 同一发布中不删除旧 Go snapshot；停止写入与物理删除至少相隔一个稳定兼容周期。
5. 迁移过程写入版本、水位和错误 telemetry，但不得记录用户内容或敏感路径正文。
6. shadow compare、read repair、migration checksum 或跨实现打开出现错误时，保持/退回旧读取路径并阻止推进认证状态。
7. 不提供会把 Rust 数据库写成 Go 私有格式的回滚。降级依赖 sqlx `ignore_missing` 兼容和“不创建 Go-only migration”的约束。
8. release candidate 必须用匿名化的真实旧目录副本完成升级、运行、回滚和再次升级演练。

## 10. 100% 认证门槛

只有同时满足以下所有条件，才能宣称对冻结 Rust SHA 100% 对齐：

1. 冻结区间内 100% Rust commits 已分类并有代码或测试证据；没有 `unreviewed`。
2. domain manifest 中 `missing=0`、`partial=0`、`intentional_difference=0`、`waiver=0`。
3. stable/experimental JSON Schema 和 TypeScript bindings canonical diff 为 0。
4. feature、config、CLI、App Server、Exec Server、MCP contract 集合 diff 为 0。
5. 五库 schema、migration checksum、PRAGMA 和 Rust/Go 双向读写矩阵全部通过。
6. rollout、history、goals、agent graph、logs、memory 在崩溃和 mixed-process 场景中结果一致。
7. deterministic differential suite 连续三次全绿，除批准的非语义归一化字段外无 diff。
8. 官方 TypeScript SDK 真实 E2E 连续三次全绿，原始事件和 workspace 副作用均已归档。
9. code mode 和 realtime 使用真实服务路径，无 synthetic answer、发布态内嵌 fallback 或隐藏的 `unimplemented` handler。
10. Windows、Linux、macOS 原生 CI 和发布产物门禁通过，SQLite 运行时版本满足下限。
11. `go test ./...`、`go test -race ./...`、`go vet ./...`、fuzz seed corpus 和性能阈值全部通过。
12. 安全差异全部关闭；不得通过削弱 Go 现有安全行为获得表面一致。
13. 迁移、回滚、损坏恢复、旧版本打开新库的演练全部通过。
14. 最终报告记录 Rust/Go SHA、构建器、依赖 lock、schema hash、DB hash、平台和 evidence run ID，可由另一台干净机器复现。

如果任一项未满足，发布说明只能报告具体百分比/域状态，不能使用“100% 对齐”。

## 11. 风险登记与控制

| 风险 | 影响 | 控制措施 | 发布门槛 |
|---|---|---|---|
| SQLite 低于安全版本 | WAL reset 下潜在损坏 | 先升级 driver，运行时版本断言，多平台 fault test | P0 阻断 |
| sqlx checksum 不兼容 | Rust 拒绝打开 Go 数据库 | 直接冻结 Rust migration bytes/checksum，双向 open test | P0 阻断 |
| 多进程/混合 writer | 锁死、重复投影、数据乱序 | WAL/busy timeout、幂等 key、lease/watermark、race/load test | P0 阻断 |
| 把 schema 名称目录误当完整 schema | 测试假绿、SDK 运行失败 | 完整 oracle、运行时 payload 校验、TS 编译/E2E | P0 阻断 |
| rollout 与 SQLite 顺序错误 | 数据库领先权威日志，崩溃后无法恢复 | 强制先 append+flush 后 transaction，故障注入 | P0 阻断 |
| 上游持续变化 | 目标永远移动 | 冻结 SHA、独立 intake、下一认证周期更新 | 不在周期内移动 |
| 真实模型/外部服务非确定性 | 假失败或漏协议差异 | deterministic mock 为精确 oracle，真实 E2E 只做集成门禁 | 三次连续通过 |
| macOS/arm64 环境缺失 | 无法证明平台对齐 | 提前准备原生 runner 和产物签名流程 | 无 runner 不认证 |
| code/realtime 用替身通过 | 用户能力实质缺失 | 网络/host 真实 E2E，检查发布二进制路径 | P0 阻断 |
| 安全行为冲突 | 为相同而回退安全 | 优先修 Rust 并重冻基线，未解决则明确阻断 | 零安全 waiver |
| 一次性大迁移 | review 困难、回滚不可控 | 按 ownership 分 PR、shadow/read repair、保留旧 snapshot | 分阶段门禁 |

## 13. 首个可执行批次

实施应从以下顺序开始，不应先做表面 API 补丁：
