## Findings

- #42819 registers a dedicated `GuardianApprovalReviewer` contributor ahead of
  the async-scorer contributor so approval routing survives a scorer start
  failure, reusing cached evidence (initial computer-use allowance, serving
  assessment) and falling back to `AskUser` / a synchronous assessment. Go has
  no extension registry or async scorer: `appserver/guardian_reviewer.go` is a
  single synchronous reviewer with the same cached-evidence fast paths, and
  routing is decided beforehand by `RuntimeRouter.approvalsReviewerForTurn` and
  `state.Reviewer.RoutesToGuardian`. Certified `not_applicable`.
- #44252 is not a pure refactor: it moves the synchronous review loop and the
  reviewer session pool into `codex-guardian-reviewer`, with the pool owning
  prewarming, session reuse, concurrent forks, invalidation and shutdown. Go
  previously kept one shared `guardianSessionRunner`, so two threads reviewing
  concurrently continued the same reviewer response chain.

## Implementation

- `appserver/guardian_reviewer.go`
  - `modelGuardianReviewer` now stores the plain agent plus a per-thread
    session map (`sessionsMu`, `sessions`) and resolves sessions through
    `sessionFor(threadID)`. A reviewer built around an explicit
    `*guardianSessionRunner` (tests/embedded callers) keeps sharing it.
  - Startup prewarm uses a trunk session; the first thread-owned review adopts
    its prewarmed response (`takePrewarm`/`adoptPrewarm`), later threads start
    a fresh chain.
  - `review`, the compaction-checkpoint hook and the parent-history-reset hook
    now target the reviewed thread's session.
  - `AssessIsolated` keeps an isolated review out of the reusable session by
    falling back to a throwaway runner for plain agents.
- `appserver/guardian_isolated_assessment.go` follows the same isolation rule.
