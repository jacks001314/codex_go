## 2. `#60042` Centralize Windows sandbox filesystem override resolution

- 上游：`a90c80840869a8cfb313ef181d7721997b86c8e5`（`Centralize Windows sandbox filesystem override resolution (#60042)`）。
- 判定：**ported**（Go 侧等价集中化已落地）。
- 所属 lane：`sandbox/windowssandbox/**`（Windows lane）；跨 lane 需求：无（`execserver` 仅读校验）。
- 上游语义：把 core（`exec.rs`）、exec-server（`process_sandbox.rs`）、direct-spawn（`manager.rs`）
  三处“选 elevated 还是 restricted-token 解析器”的分支收进
  `WindowsSandboxFilesystemOverrides::resolve(sandbox, permission_profile, cwd, level, env)`；
  同时删掉导出的 `unsupported_windows_restricted_token_sandbox_reason`，测试改用本地 wrapper。

### 2.1 Go 现状（改动前）

- `sandbox/windowssandbox/lib.go`、`unified_exec/backends/legacy.go`、`unified_exec/live_windows.go`
  各自复制了一遍 restricted-token 校验（`HasFullDiskReadAccess` + deny-read 拒绝），错误文案相同；
- elevated / restricted-token 的选择分散在 `unified_exec`、`execserver.selectWindowsSandboxForExecutor`、
  `sandbox/run.go` 等多处，靠手写 `level == elevated` 比较；
- elevated 侧的 override 组装在 `elevated_impl.go` 里按字段手工搬运。

### 2.2 落地

新增 `sandbox/windowssandbox/filesystem_overrides.go`：

- `type WindowsSandboxFilesystemOverrides`（`ReadRoots/ReadRootsSet/ReadRootsIncludePlatformDefaults/
  WriteRoots/WriteRootsSet/AdditionalDenyReadPaths/AdditionalDenyWritePaths`）；
- `WindowsSandboxUsesElevatedBackend(level)`（镜像 `windows_sandbox_uses_elevated_backend`）；
- `(*WindowsSandboxFilesystemOverrides).SetupRootOverrides()` 投影到 setup 消费的
  `SetupRootOverrides`；
- `ResolveWindowsSandboxFilesystemOverrides(level, permissions, requested)`：唯一决策点，
  顺序固定为 **disabled → 无 override；elevated → elevated 解析器；其余（空/restricted-token）→
  restricted-token 解析器；未知 level → error**。
- `resolveRestrictedTokenFilesystemOverrides`：先查 split-read（`HasFullDiskReadAccess` 为假），
  再查 deny-read，两者文案与原实现逐字一致；只保留 `AdditionalDenyWritePaths`。

改造调用点（行为不变、去重）：

- `sandbox/windowssandbox/lib.go`：`RunWindowsSandboxCaptureWithFilesystemOverrides` 改用共享解析器，
  deny-write 从 overrides 取（`openLaunchDesktopForCapture` 增加 `denyWritePaths` 形参，单一调用点）；
- `sandbox/windowssandbox/unified_exec/backends/legacy.go`：PTY legacy 路径同上；
- `sandbox/windowssandbox/unified_exec/live_windows.go`：legacy live session 同上，并把
  `level == elevated` 比较换成 `WindowsSandboxLevel.usesElevatedBackend()`；
- `sandbox/windowssandbox/unified_exec/mod.go`：新增 `usesElevatedBackend()`，`SpawnWindowsSandboxSessionForLevel` 使用；
- `sandbox/windowssandbox/elevated_impl.go`：override 组装改为
  `WindowsSandboxFilesystemOverrides{...}.SetupRootOverrides()`。

测试锁顺序：`sandbox/windowssandbox/filesystem_overrides_test.go`

- `TestResolveWindowsSandboxFilesystemOverridesSelectsBackendLikeRust`：disabled/空/restricted-token/elevated/未知 level 的分支与 override 内容；
- `TestResolveRestrictedTokenRejectsDenyReadLikeRust`：restricted-token 拒 deny-read、elevated 接受（锁定“先选后端再校验”）；
- `TestResolveRestrictedTokenChecksSplitReadBeforeDenyReadLikeRust`：split-read 先于 deny-read 报错；
- `TestResolveElevatedRejectsRootReadDenialLikeRust`：elevated 的 `:root` 读拒绝仍被拒；
- `TestWindowsSandboxFilesystemOverridesProjectionKeepsDenyPaths`：投影字段不丢。

### 2.3 残余（诚实边界）

- Rust 的 `resolve_windows_elevated_filesystem_overrides` 会从
  `resolve_for_enforcement` 的 split 策略里推导 `read_roots_override` / `write_roots_override` /
  `additional_deny_*`；Go 的 elevated 侧仍由
  `requireLogonSandboxCredsForPermissions`（`GatherReadRoots` / `GatherWriteRootsForPermissions`）
  推导根集合，共享解析器只做“选择 + 校验 + 投影”。若要与 Rust 完全同构，需要把
  `sandboxpath.ResolveForEnforcement` 的 split 投影接进 setup/refresh，属下一批可选项。
- Go 的 `SandboxPolicy.HasFullDiskReadAccess()` 恒为 `true`（`sandbox/policy.go:282`），
  因此 restricted-token 的 split-read 分支只有在 `FileSystem` 缺失时才触发；这与 Rust
  “有 deny 条目即非 full-disk read”的判定仍有差异，属跨 lane（`sandbox/policy.go`）语义项，
  本轮不改，已在测试中用 nil `FileSystem` 锁定顺序契约。

### 3.1 已落地

`sandbox/mxc/psec_windows.go` + `psec_common.go` + `psec_other.go` + `psec_test.go`：

- 纯 `golang.org/x/sys/windows` 动态解析（`windows.NewLazySystemDLL("processmodel.dll")`，
  等价 Rust 的 `LoadLibraryExW(..., LOAD_LIBRARY_SEARCH_SYSTEM32)`），**不需要 cgo、头文件或静态库**；
- `ProbeNativeSupport()` 每进程一次缓存，返回 `Available/Major/Minor/SupportFlags/

- 非 Windows 返回 `Available=false` + `Reason`；

## 3.5 `#60034` Omit sensitive process inputs from spawn trace logs

- 上游：`738ef9f3bb4a5f17892eda6e5b52e06f11f680ea`（2026-11-07，改动 `codex-rs/core/src/spawn.rs`）。
- 所属 lane：上游改动在 core；Go 侧对应路径（核心 exec/spawn）不在 Lane W（属 L lane），**只做判定**。
- 判定：**not_applicable**（结构化差异：Go 的核心 spawn 路径没有与 `spawn_child_async` 对应的 trace 事件，
  argv/arg0/env 从不写入 trace，因此不存在需要脱敏的日志面）。
- 证据命令：

```text
# Go 全树（排除测试）搜索 spawn 相关 trace/attribute，无 argv/env 记录点
grep -rn "spawn_child_async|spawnChildAsync" --include=*.go .        # 无命中
grep -rn "process\.args|process\.command|Argv:" --include=*.go .     # 命中都是工具/审批事件载荷，不是 spawn trace
grep -rn "cmd\.Args|\.Env\b" exec/*.go                              # 无命中（exec 包不直接拼 trace）
```

- 残余 / 跨 lane 提醒：若 L lane 后续给核心 spawn 加 OTel span（`tool.AdaptUnifiedExecSpan` 一类），
  **属性里不得含 argv/env**，只能放 `arg_count`/`has_arg0_override`/`env_count`/program/cwd。
  建议账本 lane 用契约 `spawn-trace-redaction`（断言：spawn span 属性不含 argv/env 值）把这个约束冻住。

## 4. `#60041` Require explicit project trust in non-interactive runs

- 上游：`11ca3f7531866b22b07bd7ed181e814f087b7ee5`（2026-11-07）。
- 判定：**partial**（安全默认已对齐，显式 `--trust` opt-in 面缺失）。**只做判定，不跨 lane 改。**
- 所属 lane：判定落在 Windows lane 的职责范围内，但改动点全部在 `cli/`、`app/`、`config/`（非 Windows lane），故只出结论。
- Go 现状证据：
  - `config/config.go:429` 项目配置加载受 `ProjectConfigEnabled(discoveryValues, cwd)` 门控，
    即只有 `projects.<path>.trust_level = "trusted"` 才合并项目层；该门控与 sandbox 模式无关，
    所以“非交互 + `workspace-write` 自动信任”这条 Rust 回归在 Go 上不存在；
  - `config/project_config_warning.go` 已有“项目配置被禁用”的告警文案与 reason；
  - `cli/cli.go` 的 exec/review 已有 `--ignore-user-config`、`--ephemeral`、`--skip-git-repo-check`，
    **没有 `--trust`**；
  - `app/local_environments.go:65 runLocalRunnerRequest` 是 exec/review 的非交互入口，
    没有 trust 授予逻辑；Go 也还没有 Rust `LoaderOverrides.default_cwd`。
- 需要改的文件（跨 lane，交 /root 分配）：
  1. `cli/cli.go`：`ExecOptions` 增加 `Trust`，解析 `--trust`，与 `--ignore-user-config` 互斥报错；
  2. `cli/exec_help.go`、`cli/usage_clap.go`、`cli/completion.go`、`cli/subcommand_help.go`：
     帮助/补全表加入 `--trust`；
  3. `app/local_environments.go`（`runLocalRunnerRequest`）：授予前先读 trust 决策，
     显式 `untrusted` 拒绝、`--ephemeral` 仍持久化、写入 `projects.<path>.trust_level="trusted"`；
  4. `config/config.go` / `config/api.go`：增加 `LoaderOverrides.default_cwd` 等价的
     “cwd 作为配置默认值”通道，避免嵌入式 server 启动隐式授信；
  5. `--oss` provider 在配置重载后的保持（Rust 同 commit 修的另一处）。

## 11. TTY/ConPTY 下的 MXC：进程内方案被 PSEC 否掉，需改两段式启动器（2026-11-08 追加）

本轮尝试把 `SpawnLiveSession(tty=true)` 从"显式拒绝"改成"进程内挂 ConPTY"，结论是**不可行**，
已回滚到 fail-closed，未交付未验证的代码。下面是决定性的实验证据。

### 11.1 实验证据（本机 Windows 10.0.26200.9711，PSEC v1.1，`processmodel.dll` 可用）

把 `PROC_THREAD_ATTRIBUTE_SECURITY_ENVIRONMENT` 与 `PROC_THREAD_ATTRIBUTE_PSEUDOCONSOLE` 放进同一个
属性列表，按 ConPTY 文档设置标准句柄三元组：

| 属性列表 | `STARTF_USESTDHANDLES` + `INVALID_HANDLE_VALUE`×3 | `CreateProcessW` 结果 |
|---|---|---|
| PSEC only | 是 | **失败**：`The handle is invalid`（ERROR_INVALID_HANDLE，6） |
| PSEC + PSEUDOCONSOLE（PSEC 在前） | 是 | **失败**：同上 |
| PSEC + PSEUDOCONSOLE（PSEUDOCONSOLE 在前） | 是 | **失败**：同上 |
| PSEC + PSEUDOCONSOLE（两种顺序） | 否 | 成功 |

读法：拒绝来自 PSEC 对"显式标准句柄为 `INVALID_HANDLE_VALUE`"的校验，**不是** PSEUDOCONSOLE 冲突
（只放 PSEC + 三元组就已经失败，与是否挂控制台无关）。而不设三元组时子进程不会挂到伪控制台上
（输出不进控制台管道），所以"PSEC + 进程内 ConPTY"没有可用组合。

对照：`STARTF_USESTDHANDLES` 带**有效**句柄时 PSEC 正常接受 —— 这正是现有非 TTY pipe 路径
（`TestNativeLaunchSmoke`）已经跑通的形状。

### 11.2 第二个障碍：本仓库的 ConPTY 内容捕获未经验证

`sandbox/windowssandbox/conpty` 现有测试只断言"最后一个客户端退出后输出管道 EOF"
（`TestSpawnedConsoleOutputReachesEOFAfterLastClientExits`），**没有**断言控制台内容。
我按该包的句柄生命周期（`Create` → 启动 → `TakeOutputRead` → `PeekNamedPipe`/`ReadFile`，
finish 与不 finish 两种）构造进程内捕获，在**完全不加 PSEC** 的情况下也读到 0 字节。
也就是说：即使绕过 PSEC，"从伪控制台里拿到子进程输出"这一环在本仓库仍未经验证。

### 11.3 Rust 为什么能 TTY：PSEC 与 ConPTY 在**不同进程**上

- `exec-server/src/local_process.rs:441` 把 `tty: params.tty` 交给 `codex_sandboxing::spawn_process`；
- `sandboxing/src/spawn.rs` 只对 `WindowsRestrictedToken` 走专用 spawn，`SandboxType::WindowsMxc`
  落到**通用 pty 路径**：用 ConPTY 启动一个**非沙箱**进程（`codex --__codex-windows-mxc` 启动器）；
- 启动器再用 PSEC 创建真正的工作负载，并**继承启动器自己的（控制台）标准句柄** —— 有效句柄，PSEC 接受；
- `utils/pty/src/win/psuedocon.rs` 的 `STARTF_USESTDHANDLES` + `INVALID_HANDLE_VALUE` 三元组只作用在
  **启动器**那次 CreateProcess 上，从不与 PSEC 同时出现。

## 14. 时间盒结论：**不是环境限制**，是 Go 侧 ConPTY 用法缺陷（2026-11-08 追加）

按 /root 的时间盒做了官方等价最小复现。结论推翻了"宿主会话环境限制"这个假设，请**不要**把它标成
`blocked-external`。

### 14.1 独立复现（不引本仓库任何代码）

工具：`C:\msys64\ucrt64\bin\gcc.exe` 编译的独立 C 程序，严格按文档序列：
`CreatePipe(bInheritHandle=TRUE)` → `CreatePseudoConsole(80x24)` →
`InitializeProcThreadAttributeList` + `UpdateProcThreadAttribute(PROC_THREAD_ATTRIBUTE_PSEUDOCONSOLE)` →
`CreateProcessW(..., FALSE, EXTENDED_STARTUPINFO_PRESENT, NULL, NULL, &si.StartupInfo, &pi)`。

本机环境（先排除环境因素）：

```text
consoleWindow=0x0          # 本进程自己没有控制台
windowStation="WinSta0"    # 交互式窗口站
desktop="Default"
whoami: Medium Mandatory Level, NT AUTHORITY\INTERACTIVE, CONSOLE LOGON  # 非 session 0、无 AppContainer
```

C 程序实测：

```text
[c] CreatePseudoConsole hr=00000000
[c] child pid=23304
MIRROR_C_OK                                 # ← 子进程输出出现在**继承的标准句柄**上
[c] wait=0 exit=0
[c] peek available=16
[c] content=?9001h?1004h                    # ← 控制台管道里只有 conhost 的 VT 初始化序列
```

对照（同一程序，子命令 `cmd /d /c exit 5`）：`exit=5`（退出码正确透传），`peek available=16`。

读法：
1. **ConPTY 在本机是可用的**：`CreatePseudoConsole` 成功、子进程正常启动并正确透传退出码、控制台管道
   有 conhost 的初始化字节。所以"环境限制"不成立。
2. 但**子进程的 stdout 并没有走控制台**——`MIRROR_C_OK` 直接出现在继承的句柄上。原因是那次启动
   **没设** `STARTF_USESTDHANDLES` + `INVALID_HANDLE_VALUE` 三元组：不设三元组时子进程沿用父进程的
   标准句柄，控制台只被初始化不被使用。

### 14.2 Go 侧的两个配置都不工作

| 配置（Go，`conpty.Create` 生成伪控制台） | 结果 |
|---|---|
| 不设三元组（对齐 C 程序） | 子进程 exit=0，**管道 0 字节**（输出跑到继承句柄，与 C 同因） |
| 设三元组（仓库 `SpawnProcessAsUser` 的现行做法） | 子进程 exit=0，**在任何 `FinishSpawn`/`ReleasePseudoConsole` 之前**轮询 5s，管道仍 **0 字节** |
| 三元组 + 管道改 `bInheritHandle=TRUE` | 仍 0 字节 |
| 三元组 + `CreatePseudoConsole` 去掉 `PSEUDOCONSOLE_RESIZE_QUIRK` | 仍 0 字节 |

最后一行是与 C 程序最大的差异点（C 用 flag=0），即便对齐了仍无输出，所以差异还在**更底层**的 Go 调用
路径上（`x/sys/windows` 的 `CreateProcess` / `NewProcThreadAttributeList` 与直接 Win32 调用的差别），
需要把 C 程序逐句移植成一个 Go `cmd` 小程序做二分定位。

### 14.3 对计划的影响

1. `windows-mxc-tty-launch` **不要**标 `blocked-external`。正确结论是"Go 侧 ConPTY 用法/绑定缺陷，
   可在本机修复与验证"，这反而是好消息：不需要换节点。
2. 第 ① 步（内容捕获）仍然阻塞第 ② ③ 步，但阻塞原因从"环境"变成"需要在 Go 里定位 ConPTY 绑定差异"，
   工作量可控（已有可对照的 C 最小程序）。
3. 建议下一轮（或 #60041 之后）的顺序：把 C 程序逐句移植为 Go 单文件（`syscall` 裸调用），跑通后
   再回头修正 `conpty.Create`/`SpawnProcessAsUserWithToken`，最后才接两段式启动器。

### 14.4 本轮状态

- 代码：**无净改动**。所有实验（可继承管道、去 quirk、三元组探针）已回滚，
  `git diff sandbox/windowssandbox/conpty/` 为空。
- 命令：`go build ./...` EXIT=0；`go test ./sandbox/windowssandbox/conpty/ ./sandbox/mxc/ -count=1` 均 ok。
- 独立 C 程序留在 `%TEMP%\conpty_probe\`（不属项目内容），可作为下一轮移植的对照。

### 16.7 信任决策的数据来源：为什么复用 `decisionForDir` 而不是新增字段

按要求先核了你点名的两个入口：

| 候选 | 结论 | 证据 |
| --- | --- | --- |
| `config.ProjectTrustLevelForTarget(userValues, path)`（`config/config.go:3331`） | **不够**：只给 `(level, ok)`，没有可写入的 key；且它只对**单个路径**建 lookup（`ProjectTrustLookupFromNativePath`），没有 Rust `decision_for_dir` 的「目录 → 项目根 → 仓库根」顺序 | 函数体只 `return cfg.ProjectTrustLevelForLookup(ProjectTrustLookupFromNativePath(path))` |
| `(*Config).ProjectTrustLevelForLookup(lookup)`（`config/project_trust.go:190`） | **不够**：返回 `(level, found)`，命中的 key 没有出口（`ActiveProjectForLookup` 只返回 project 表）；要拿 key 得对 `lookup.Keys()` 逐个重跑 `ActiveProject`，等于把查找逻辑复制一遍 | 该函数末尾只 `return level, true` |
| `projectTrustContext.decisionForDir(dir)`（`config/project_config_warning.go:180`） | **够用，已复用**：返回 `(trustKey, level, saved)` 三件套，查找顺序就是 Rust 的目录 → 项目根 → 仓库根，key 默认值也一致（仓库根优先，其次项目根） | 同一函数就是给 `Layer.DisabledReason` 赋值的那个（`project_config_warning.go:123`），所以「读信任」和「写信任用哪个 key」共用一份来源 |

因此 **没有在 `ConfigLayerStack` 上新增 `project_trust` 字段**：Rust 加那个字段是为了把决策随 layer stack
传给 exec；Go 侧按需计算即可，加字段只会扩大结构差异。`ProjectTrustDecisionForDir` 只是这层复用的薄包装。

### 16.8 `default_cwd` 与 `--oss`：判 `not_applicable`，附证据

**（1）`LoaderOverrides.default_cwd` + 去掉 `thread_start_params_from_config` 的 cwd**

- Go 的 `codex exec` **从不启动 in-process app-server 客户端**：`exec/` 包（非测试文件）对
  `codex_go/appserver` 的 import 数是 **0**（`Get-ChildItem exec/*.go | Where-Object { $_.Name -notlike '*_test.go' } | Select-String 'codex_go/appserver'` → 无输出）。
  也就是说 Rust 里 `InProcessClientStartArgs` / `thread_start_params_from_config` 那条链在 Go 根本不存在，
  「把 `cwd: Some(config.cwd)` 去掉」没有可去掉的对象。
- 该字段要解决的「loader 级默认 cwd」在 Go **已经存在**：`appserver` 的 `RuntimeRouter.services.DefaultCWD`
  经 `effectiveThreadStartCWD(params, r.threadStartDefaultCWD())` 生效
  （`appserver/runtime_router.go:6634`、`appserver/router.go:1588`），优先级正是「请求 cwd → server 默认 → 进程 cwd」，
  生产 host 已在设置它（`app/hooks_tui.go:34`、`app/interactive_providers.go:20,40`）。
- `thread/start` 的 cwd 能授信这一点在 Go 也确实存在（`appserver/runtime_router.go:6949`
  `threadStartEffectivePermissionsTrustProject` 要求 `params.CWD` 非空才谈授信），但没有任何 Go 生产代码把
  `config.cwd` 塞进 `params.CWD`：TUI 用的是 `codextui.State.CWD`（`app/interactive.go:2018`），是客户端值。
- 结论：上游这两处改动在 Go 侧 **already satisfied by structure**，不新增 `config` 字段；
  本轮一度新增的 `LoadOptions.DefaultCWD` / `EffectiveOptions.DefaultCWD` 已撤回。

**（2）`--oss` 选中 provider 跨配置重载保持**

- 上游做法是把 `model_provider` 追加进 `cli_kv_overrides`，交给 app-server 配置重载时重放。
- Go 的 `appserver/**` 没有 `cli_overrides` / `CliOverrides` 这类透传通道：
  `Get-ChildItem appserver/*.go | Where-Object { $_.Name -notlike '*_test.go' } | Select-String 'CliOverrides|cli_overrides'` → 无输出；
  `Overrides` 的命中都是 spawn model overrides、exec env overrides 等无关物。
- 结论：`not_applicable`（Go 的 app-server 重载不从 exec 收 CLI override 列表）。若将来需要等价语义，
  应在 appserver lane 引入 override 通道，而不是在 Windows lane 造一个旁路。

### 17.3 根因与修复（一行语义）

`sandbox/windowssandbox/proc_thread_attr_windows.go` 的 `SetPseudoconsole` 原来传的是
`unsafe.Pointer(&value)`——HPCON 的**地址**。上游两处 Rust 实现传的都是**值**：

- `codex-rs/windows-sandbox-rs/src/proc_thread_attr.rs` `set_pseudoconsole`：
  `self.update(PROC_THREAD_ATTRIBUTE_PSEUDOCONSOLE, hpc as *mut c_void, size_of::<HPCON>())`
- `codex-rs/utils/pty/src/win/procthreadattr.rs` `set_pty`：`self.update(..., con, mem::size_of::<HPCON>())`

修复后（同一个 `UpdateProcThreadAttribute` 调用，只换 lpValue）：

```go
err := l.container().Update(
    windows.PROC_THREAD_ATTRIBUTE_PSEUDOCONSOLE,
    handleBitsAsPointer(handle),   // 原来是 unsafe.Pointer(&value)
    unsafe.Sizeof(handle),
)
```

`handleBitsAsPointer` 用 `*(*unsafe.Pointer)(unsafe.Pointer(&handle))` 重解释句柄位，
避免 `unsafe.Pointer(uintptr)` 触发 `go vet` 的 unsafeptr 检查（`go vet ./sandbox/windowssandbox/` 无输出）。

> 从未 attach 的控制台拆了 → 管道立刻 broken pipe，**早于子进程退出**，而且是 0 字节。

修复后原断言反而变红（`reader finished while the pseudoconsole was still open`），正是它是伪证据的证明。
新断言只看一条真实性质：**EOF 必须带着控制台字节**；0 字节的 EOF 就是「控制台从未被 attach」的签名。

### 18.2 形状：Rust 与 Go 怎么对应

Rust（`codex-rs/sandboxing/src/manager.rs`，`SandboxType::WindowsMxc` 分支）：

```rust
let args = codex_mxc_sandbox::create_command_args(...)?;   // 返回 [CODEX_WINDOWS_MXC_ARG1]
exec.command = std::iter::once(exe).chain(args).collect(); // [codex.exe, --__codex-windows-mxc]
```

载荷（permission profile / policy cwd / managed network / argv）通过环境变量传给 helper，随后**由通用 PTY spawner 启动这个命令**——所以 Rust 的 TTY 与管道走的是同一条 spawn 路径，区别只在 spawner。

Go 对应：

- `execserver/sandbox_process_windows.go` 的 MXC 分支在 `params.TTY` 时改走
  `mxc.CreateCommandArgs(params.Argv, *profile, cwd, managed, launcherEnv)` →
  `mxc.SpawnLauncherSession(os.Executable(), args, launcherEnv, cwd)`；
- 非 TTY 仍走进程内 PSEC（`mxc.SpawnLiveSession`），因为它已经能正确交付管道 stdio，且不引入一层 helper；
  这是 Go 与 Rust 的已知结构差异（Rust 两条都过 helper），行为面等价，记录在 18.7 残余 5。
- `CreateCommandArgs` 会把 `SystemDrive`/`LOCALAPPDATA`/`SystemRoot` 写进传入的 env map，
  所以 execserver 传的是本次启动的**副本**，不污染共享的 child env。

### 18.3 `SpawnLauncherSession` 的四条语义（每条都有用例）

| 语义 | 实现 | 锁住它的用例 |
| --- | --- | --- |
| 能力门在最前 | `!NativeTTYLaunchSupported()` 直接返回 `TTYUnsupportedMessage` | `TestTTYCapabilityMatchesSpawnBehaviour`、`TestTTYCapabilityGatePrecedesLaunchValidation` |
| 只放 PSEUDOCONSOLE + 标准三元组 | `SetPseudoconsole(instance.RawHandle())`，`STARTF_USESTDHANDLES` + `INVALID_HANDLE_VALUE`×3，**无** `SECURITY_ENVIRONMENT` | `TestLauncherSessionDeliversConsoleContent` |
| helper 原子入 job | 属性表 2 项：pseudoconsole + `PROC_THREAD_ATTRIBUTE_JOB_LIST`（kill-on-close）；`Close()` 关 job → 连 helper 起的沙箱子进程一起收 | `TestLauncherSessionRunsSandboxedCommandThroughHelper`（退出码 + 文件双断言） |
| stdin 归一化 | `conpty.NewInputWriteCloser`（移植 `WindowsTtyInputNormalizer`） | `TestLauncherSessionNormalizesStdinForTheConsole`、`TestInputNormalizer*` |

`SpawnLiveSession` 的 `tty bool` 参数**删掉了**：两段式落地后，这条入口只服务管道会话。
保留参数会让“请求 TTY 但走管道”成为静默降级，正是 §13 说的契约地雷；删掉之后

## 19. `--ignore-user-config` 在 exec 路径上没有落到配置加载（Go 侧既有缺口）— 2026-11-08 追加

### 19.1 结论

| 项 | 判定 | 说明 |
| --- | --- | --- |
| `exec-ignore-user-config-skips-user-layer` | **ported（Go 侧缺口已补）** | loader 级开关 + exec 接线 + warning 口径三处一起收；用例见 19.4 |
| `#60041` | 维持 **ported** | §16 的判定不变，§16.6 第 1 项已作废并指向本节 |

这不是某条上游提交的移植，而是 Go 侧一直存在的"宣称不读却读了"的语义问题：
`--ignore-user-config` 只影响 worktree 冲突判断和本地 runner 的环境选择，配置层照读用户文件。

### 19.2 上游语义（Rust，照抄不改）

`codex-rs/config/src/loader/mod.rs::load_user_config_layer`：`ignore_user_config` 为真时**不读文件**，
直接返回一个**空值的 `ConfigLayerSource::User` 层**——所以

- 语法坏掉的 `config.toml` 也不会让加载失败；
- 层还在（优先级序列不变），只是没有值，于是"信任判决"自然回落到 untrusted；
- 只有 `config.toml` 受影响：用户的 exec policy 规则文件由 `ignore_user_and_project_exec_policy_rules`
  控制，本 flag 不动（`core/src/exec_policy_tests.rs::ignore_user_config_keeps_user_policy_files`）。

这也是 `--trust --ignore-user-config` 互斥的原因：saved 信任决定就存在被忽略的那个文件里。

### 20.2 `#60038`：启动错误要变成工具结果，不是回合失败

上游语义（`codex-mcp/src/connection_manager/tool_catalog.rs` + `core/src/mcp_tool_call.rs`）：

- `prepare_call_for_tool` 从 `Option<PreparedMcpCall>` 改成 `Result`；连接失败时用
  `with_context(|| format!("Could not start MCP server `{server_name}`"))` 保留原因链；
- 仍然返回「not available to the model」的只有**缺失 / 被过滤 / 已不可见**的三种情况；
- `handle_mcp_tool_call` 把准备失败渲染成 `format!("{error:#}")` 的**工具结果**（`notify_mcp_tool_call_skip`），并且 `McpHandler` 的 `recorded` 分支同样改成把错误带出去。

Go 侧对照与落地：

| 层 | 改动 |
| --- | --- |
| `mcp/api.go` | `WaitForServerStartup` 不再 `_ =` 丢弃 `inventoryStatusForConfig` 的结果：启动失败返回 `*MCPServerStartupError`（`ctx` 已取消时仍返回 `ctx.Err()`，避免把取消当启动失败） |

| `turn/tool_dispatcher.go` | 就绪阶段失败时，若错误实现 `ModelVisibleError`，转成 `rejectedInvocationResult`（`Success=false` 的工具结果）并 `completeDirectCall` 收口，回合继续；其余错误（取消、基础设施）照旧中止回合。单调用与批量两条路径都覆盖 |

### 21.5 `#60039` 后半段（批次事件）成本评估：不做

Rust `af9a98b074` 的后半段是：先把整批 `eager_starts` 以 `Starting` 播报一遍，再发终态汇总；dormant 服务器不进初始摘要；
TUI 侧（`chatwidget/mcp_startup.rs`）让 defer 的服务器在后续轮次独立上报。

Go 侧现状：`MCPStartupObserver` 是**逐服务器回调**（`mcp/api.go` 12 处），唯一的消费方是 `app/interactive.go`，
没有「批次」这个类型，也没有初始启动摘要的结构。要做等于：

1. 新造一个批次/摘要事件类型并让它与逐条通知共存（观察者签名变更 → `mcp` + `app` 两头改）；
2. `app/interactive.go` 的启动展示按新类型重排（用户可见的 UX 变化，属 `app/**` 车道）；

### 22.6 与 `/root` 措辞的一处差异（请复核）

`/root` 写的子用例是"现代协商后 **legacy 客户端拿不到新目录**、modern 能"。本包实现的方向与 §21 一致、也与 Go 既有用例一致，是**反过来的**：

- 现代握手记录后，**发现式（modern）客户端**不得复用早于该握手的目录；
- **legacy 客户端**仍可复用；
- 握手之后发布的目录两边都能用。

用例把两种方向都显式命名了：
`TestToolCatalogCacheGenerationOrderingLikeRust/{modern discovery rules out the older catalog for discovery clients, legacy publish does not advance the modern generation}`。
