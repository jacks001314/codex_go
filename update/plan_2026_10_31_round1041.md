## Goal

Keep target-native paths on command approvals and launches.

## Findings

- Rust #42577 stops deriving a host-native path (`guardian_cwd`) for the user
  command approval request and passes the selected executor's `PathUri`
  straight through, so the approval reports the executor's own working
  directory and execution resumes on the same path. It also renames the
  native-path permission helpers to `*_local_path_with_cwd` and makes
  executor-aware policy transforms require a
  `FileSystemSandboxPolicyContext`.
- Go passed `ShellRequest.CWD` straight into
  `CommandExecutionRequestApprovalParams.CWD`, but the shell request itself was
  still resolved with `filepath.Abs`: a POSIX executor driven from a Windows
  host turned `/srv/project` into `D:\srv\project`, and `PathConvention`
  stayed empty. The mangled path reached both the approval request and
  `unifiedExecPathURI` for the remote launch.
- Go has no `can_*_path_with_cwd` helpers to rename; the executor-aware
  equivalents already exist from the #42391/#42314 work
  (`safety.FileSystemPolicyContext`/`CanWritePathInContext`,
  `sandbox.PermissionProfileWithAdditionalPermissionsForConvention`), and the
  shell request's `PathConvention` is what feeds them.

## Implementation

- `tool.resolveShellRequestCWDForConvention` resolves the launch directory in
  the selected executor's path grammar: a foreign convention is cleaned/joined
  lexically (`resolveRemoteUnifiedExecCWD`) instead of being absolutized
  against the host; the native convention keeps the existing host resolution.
- `prepareExecCommand` records the remote executor's inferred `PathConvention`
  on the validation options, so the request, its sandbox permission
  materialization, and the approval all use the target grammar.
- Tests pin the remote request cwd (`/srv/project`, relative and absolute
  workdir joins) and the unchanged local behaviour, plus the app-server
  approval request carrying `/srv/project` and `environmentId: remote` and
  resuming after acceptance.
