### sync151: the environments.toml provider and the stdio client transport

The executor environment configuration layer now exists in Go, mirroring
Rust's `environment_toml.rs` / `environment_provider.rs`:

- `execserver.ParseEnvironmentsTOML` / `LoadEnvironmentsTOML` decode
  `environments.toml` (top-level `default` and `include_local`, one
  `[[environments]]` table per environment with `id`, exactly one of `url` or
  `program`, optional `auth_bearer_token`, `args`, `env`, `cwd`,
  `connect_timeout_sec`, `initialize_timeout_sec`), reject unknown fields, and
  never echo configuration values in failures — syntax errors report a line and
  column, unknown fields report the field name.
- `NewEnvironmentProviderSnapshot` reproduces Rust's validation messages
  verbatim: reserved/whitespace/invalid-character/overlong ids, duplicate ids,
  `must set exactly one of url or program`, empty program, `args/env/cwd
  require program`, `auth_bearer_token requires url`, `connect_timeout_sec
  requires url`, non-websocket and malformed urls, config-dir-relative stdio
  cwd resolution, `default = "none"` disabling the default, and a local default
  rejected when local is disabled.
- `DefaultEnvironmentProviderSnapshot` mirrors the `CODEX_EXEC_SERVER_URL`
  fallback (`remote` environment, or `none` disabling the provider), and
  `EnvironmentProviderFromCodexHome` selects the file when present.
- The stdio transport is implemented: `execserver.DialClientOptions.StdioCommand`
  spawns the configured program and speaks line-delimited JSON-RPC over its
  stdin/stdout (reusing the shared initialize/session machinery). Mirroring
  Rust, a stdio connection registers no reconnect strategy, so a dropped
  connection fails instead of resuming a session the child cannot know about,
  and a stdio command conflicts with an exec-server URL.

Remaining for this program: the host-side wiring — `appserver`'s environment
manager still learns about environments only from RPC registrations, so the
app-server must pre-register the provider snapshot (remote entries with their
bearer headers, stdio entries with their command threaded through the
unified-exec and remote-skills dial paths).

### sync152: the app-server serves the configured executor environments

- `EnvironmentManager.ApplyProviderSnapshot` pre-registers a provider snapshot:
  remote entries become records with their URL, bearer headers and connect
  timeout, stdio entries become records carrying the program command, and the
  provider's default selection is retained. The local environment stays
  implicit.
- The app-server startup loads the provider from CODEX_HOME, so a malformed
  `environments.toml` fails startup with the parse error and never echoes the
  configuration values.
- Stdio records are reachable through every executor path: environment
  info/status, remote skill discovery/reads, the OpenAI-file executor client and
  unified exec all select the stdio transport (`execServerClientOptions`,
  `tool.UnifiedExecEnvironment.ExecServerStdioCommand` →
  `ShellRequest.UnifiedExecRemoteStdioCommand` → `execserver.DialClientOptions`),
  and the "remote environment" decisions in the shell executor treat a stdio
  command as remote so the local sandbox path is not used.
- A turn that selects no environment now uses the provider default
  (`DefaultEnvironmentID` → `unifiedExecEnvironmentsForTurn`), replacing the
  implicit local environment when `environments.toml` points `default` at a
  configured executor; `default = "none"` or a local default keeps tools local.

Remaining for full fidelity: Rust builds the same environment manager from
CODEX_HOME in `codex exec`, the TUI and the worktree paths, while Go's
non-app-server hosts still run turns locally without consulting
`environments.toml`.

### sync150: the portable project trust lookup (#47620)

- `config.ProjectTrustLookup` mirrors Rust's `ProjectTrustLookup`: the ordered
  project-map keys for one working directory, with cwd keys before the
  repository root's and each executor-normalized canonical spelling before its
  original spelling. It matches the merged projects map exactly first, then
  case-insensitively on Windows with a deterministic (lowest-key) tie-break, and
  an entry that omits `trust_level` still wins — which is the precedence the

- `ProjectTrustLevelForTarget` now resolves through the lookup, so trust entries
  written with either the canonical or the original spelling are honored, and
  `ProjectConfigEnabled`'s ancestor walk stays as the separate onboarding
  (`directory_trust_persisted`) check.

### Triage: preempting model responses (#48141)

The follow-on to #48135 (which sync206 landed) reaches the model request itself:

- **Rust**: `ModelClientSession::drop_connection` resets the cached WebSocket

### sync202: early yielding for code-mode observations (#48123)

Rust adds an optional `preempt` signal to `CodeModeSession::execute` and
`wait`: firing it ends the foreground observation early while the cell keeps
running and stays available to later waits. The signal crosses both remote
transports - `operation/yield` guarded by the negotiated `yield-observation`
capability on the stdio/WebSocket wire, and a native `YieldObservation` RPC on
gRPC - and the in-process runtime races it against the yield timer.

Go already had the whole cell machinery (`tool`'s exec/wait executors run the
script off the caller's goroutine and select on the cell, a caller `yield`
channel and the yield timer), so the port threads the signal end to end:

- **`tool/code_mode_yield.go`**: `YieldSignal` (the preempt token, nil = never
  preempt) plus `CodeModePreemptContextKey`, which carries the host's per-request
  signal into the exec/wait executors.
- **`tool.CodeModeRemoteSession`**: `Execute`/`Wait` gained the trailing preempt
  signal (Rust's trait change), with the production sessions and test doubles
  updated.
- **`tool/code_mode_exec.go`**: a request carrying a preempt signal no longer
  takes the inline fast path, so it always runs as an observable cell; the exec
  and wait selects gained the preempt branch, which returns the running
  observation while the cell keeps running; both remote paths forward the
  caller's signal.
- **`codemode/protocol_host.go`**: `YieldObservationCapability` and the
  `operation/yield` frame (`YieldRequest`) in the client-to-host codec.
- **`codemode/stdio_host.go`**: the host advertises `yield-observation` only when
  the client asked for it (required or optional) and now rejects a required
  capability it cannot provide, mirroring Rust's filter-based capability set;
  every request carries a `tool.YieldSignal`, which `operation/yield` cancels for
  execute and wait requests only, and which reaches the executors through the
  invocation context.
- **`codemode/session_runtime.go` / `session_host.go`**: `Execute`/`Wait` accept
  the signal - the engine now runs off the caller's goroutine so the yield timer
  and the preempt signal both end the observation while the cell completes later
  (`finishCellFromEngine`), and the host threads the request's signal in.
- **`codemode/remote_provider.go`**: the client hello asks for
  `session-cell-execution-resource-limits` and `yield-observation` as optional
  capabilities; `supportedYieldSignal` drops a caller signal for a host that did
  not negotiate the capability (an older host keeps its normal timeout), the
  connection stores the negotiated set, and a per-observation watcher writes
  `operation/yield` when the signal fires.
- **`codemode/grpc`**: the vendored proto is merged with upstream's (it also
  picks up the missing `ToolCall.traceparent` field, Rust #41017) and the
  generated Go code is regenerated, so the schema carries `YieldObservation`;
  Go's gRPC client speaks the framed transport, so its yield path is the
  `operation/yield` frame over the same negotiated handshake.

The core still passes no signal (Rust passes `None` too), so production behavior
is unchanged until a caller supplies one - exactly the upstream end state.
