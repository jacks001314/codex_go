## Goal

Register the creating client connection before thread startup prewarms the
Responses socket, so that handshake can request attestation for the new
thread (persistent and ephemeral).

## Findings

- Rust reserves the thread id, registers the creating connection with the
  thread state manager, and only then calls `start_thread`; startup can prewarm
  before `thread/start` returns. Failure removes the thread state.
- Go already installs the creating connection subscription
  (`installThreadSubscription`) before `scheduleStartupPrewarm`, and
  `markResponseThreadLoaded` subscribes the response connection; attestation
  selects the first subscribed connection that opted into
  `requestAttestation`.
- Gap: neither startup prewarm nor idle-thread history prewarm carried a
  thread id or attestation provider, so `addAttestationHeader` never ran for
  those handshakes. History prewarm had the thread id but no provider.

## Implementation

- `appserver/session_startup_prewarm.go`: both prewarm requests now set
  `ThreadID` and `AttestationProvider: r.appServerAttestationProvider()`, so
  the prewarm handshake requests attestation through the registered
  connection, matching the Rust #47912 outcome.
- `appserver/startup_prewarm_attestation_like_rust_test.go`: subscribes an
  attestation-capable connection, schedules a startup prewarm, and asserts the
  captured request carries the thread id and provider, that the provider
  resolves the injected token through that connection, and that the request
  targets it.

## Residuals

- Go schedules the prewarm strictly after thread/start installs the
  subscription, rather than concurrently with `start_thread` as Rust does.
  The observable attestation ordering is therefore satisfied without moving
  thread creation off the request path.
