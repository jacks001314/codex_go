## Goal

Attribute plugin measurement analytics to the turn originator.

## Findings

- Rust #42445 adds `originator` to `PluginMeasurementsInput` and
  `CodexPluginMeasurementEventParams`, threads it through the reducer, and fills
  it from `turn.originator` in `finish_and_track_measurements`, which already
  labelled the event with `item_id` set to the tool call id.
- Go already carried the `originator` field from the #45445 model-attribution
  work, but sourced it from the thread record metadata, never filled `ItemID`
  (so the emitted event always reported an empty `item_id`), and omitted the
  field entirely when empty (`json:"originator,omitempty"`), unlike Rust's
  always-serialized string.
- `tool.ShellExecutor` had the tool call id available at the measurement
  callback (`invocation.CallID`) but did not forward it, and
  `toolRouterForTurnContext` already resolves the turn originator from
  `params.Originator` (with the thread record as its fallback) before building
  the registry.

## Implementation

- `plugin.PluginMeasurementBatch` gains `ItemID`; the shell executor fills it
  from the invocation call id.
- `appserver.emitPluginMeasurements` takes the turn originator, prefers it, and
  keeps the thread record metadata as the fallback; it forwards `batch.ItemID`
  into the analytics input.
- The turn registry's measurement tracker passes the resolved turn originator.
- `telemetry` always serializes `originator` (an empty string when absent) on
  both the input and the event params, matching Rust's payload shape.
