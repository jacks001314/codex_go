## Goal

Report the managed filesystem policy source and configuration scope in
`codex doctor` without exposing denied paths.

## Findings

- Rust #42821 loads doctor configuration through the cloud-aware CLI path and
  adds `configuration load ms`, `configuration scope: invocation config,
  including cloud-managed policy`, `active thread overrides: not inspected`,
  denied-read rule/glob counts, glob scan depth, and the managed filesystem
  source (`none`, `cloud`, `multiple layers`, `system`, `MDM`, legacy variants,
  or `unknown`).
- Go already emitted the filesystem kind, denied-read rule/glob counts, glob
  depth, and denied-read restrictions, but labeled any permissions requirement
  as `managed requirements` and did not report the scope or load-time details.

## Implementation

- `config`: `Config` now records whether the local `requirements.toml`
  (`system`), a cloud enterprise-managed fragment (`cloud`), or both
  (`multiple layers`) supplied `[permissions.filesystem]`.
  `FilesystemRequirementsSource` renders those values (plus `none` and
  `unknown`) using Rust's labels. `applyCloudConfigBundleWithFilesystemSource`
  reports the cloud contribution; `applyCloudConfigBundle` remains as a wrapper.
- `doctor`: the sandbox check uses `FilesystemRequirementsSource`, and the
  config check reports the invocation scope, active-thread limitation, and
  measured configuration load time.
- Tests: `config/filesystem_requirements_source_like_rust_test.go` covers
  none/system/cloud/composite/unknown, and
  `doctor/filesystem_requirements_source_like_rust_test.go` covers the source
  label (without path leakage), scope details, and load-time detail.
