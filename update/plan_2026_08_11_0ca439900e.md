## Upstream audit

### Commit `0ca439900e` - "Cache tool catalogs for streamable HTTP MCP servers (#37970)"

#### Why

Subagents should be able to use known HTTP MCP tool definitions without opening a
connection until a tool is actually called.

#### What changed (Rust)

1. `codex-rs/codex-mcp/src/connection_manager.rs`
   - When a connection is being built, the tool catalog cache context is now
     created with `Some((&connection_identity, protocol_mode, server.is_agent_plugin()))`
     instead of nothing. This makes HTTP (streamable) configs eligible for the
     shared tool-catalog cache when their auth identity can be derived safely.
2. `codex-rs/codex-mcp/src/tool_catalog_cache.rs`
   - `ToolCatalogTransportIdentity` gains a `StreamableHttp { fingerprint: [u8; 20] }`
     variant alongside `Stdio`.
   - HTTP configs are cached only when the auth identity is safe:
     - excluded when `oauth`, `scopes`, or `oauth_resource` are configured;
     - excluded when `auth == ChatGpt` and there is no explicit HTTP authorization;
     - excluded when there is no explicit HTTP authorization and the connection
       identity has dynamically resolved OAuth credentials;
     - otherwise fingerprint: `url`, `bearer_token_env_var`, sorted
       `http_headers`, sorted `env_http_headers`, `config.auth`,
       `environment_id`, `agent_plugin`, `protocol_mode` preferred version,
       `client_elicitation_capability`, sorted `client_mcp_extensions`, plus the
       resolved values of referenced environment variables (bearer token env var
       and `env_http_headers` values).
3. Tests
   - `connection_manager_tests.rs`: call sites updated to the new
     `client_context` tuple + optional `connection_identity` parameters.
   - Removed the assertion that an HTTP server's `tool_catalog_cache_context`
     is `None` (HTTP servers are now cache-eligible with safe auth).
   - `core/tests/suite/mcp_tool_cache.rs`: new integration test
     `cached_http_mcp_starts_lazily_for_subagents` proving a subagent receives
     cached HTTP tool definitions without reinitializing the server, and opens
     its own connection only when it calls a tool.

### Go mapping / equivalence analysis

Go mirrors this feature at two layers:

1. `mcp/api.go` - `sharedOptionalMCPStartupGrace` (process-wide shared optional
   startup deadline map) + `optionalStartupGraceKey(name, config)` keyed by
   `name + "\x00" + mcpConnectionCacheKey(&config, false)`.
   - Go already fingerprints the whole config in `mcpConnectionCacheKey`
     (JSON of the config incl. URL, headers, auth, env vars, environment id,
     protocol mode, openAI form). This is the Go analog of the Rust tool-catalog
     identity.
2. `mcp/http_client.go` / `mcp/stdio_client.go` - connection-level identity
   (`mcpConnectionCacheKey`, `mcpHTTPConnectionCacheKey`).

What Go still needs to mirror from `0ca439900e`:

1. **HTTP cache eligibility gate**: Go currently treats HTTP configs like stdio
   configs in the shared optional-startup grace (`sharedOptionalStartupDeadline`
   is applied uniformly). Rust now excludes OAuth / ChatGpt-without-explicit-auth
   / dynamic-OAuth-credential HTTP configs from the shared tool-catalog cache.
   Go needs an eligibility check (`hasExplicitHTTPAuthorization` +
   `mcpToolCatalogCacheEligible`) so only safely-identified HTTP servers share
   the cached tool catalog.
2. **HTTP-specific fingerprint**: Go's `mcpConnectionCacheKey` already hashes the
   config but does not include:
   - resolved values of `bearer_token_env_var` / `env_http_headers`
     environment variables (Rust hashes their values);
   - `agent_plugin` status;
   - protocol mode preferred version + client capabilities (Go includes
     `protocolMode` + `openAIForm`, which is the Go equivalent of the Rust
     protocol mode + client elicitation capability; client MCP extensions map
     to `openAIForm` in the Go architecture).
   Add these to the HTTP fingerprint inside the shared-identity helper.
3. **Tests**: add Go unit tests proving:
   - stdio configs remain cache-eligible;
   - HTTP configs with explicit authorization (e.g. `http_headers` with
     `Authorization`, `bearer_token_env_var`) are cache-eligible;
   - HTTP configs with OAuth/scopes/oauth_resource, ChatGpt auth without
     explicit authorization, or dynamically resolved OAuth credentials are
     excluded from the shared cache;
   - fingerprint changes when env var values / agent plugin status change.

## Implementation plan (Go)

### Files

- `mcp/api.go`:
  - add `hasExplicitHTTPAuthorization(config *ServerConfig) bool` (mirrors Rust
    `has_explicit_http_authorization`; checks `http_headers` for a non-empty,
    printable `Authorization` value and requires no `bearer_token_env_var` /
    `env_http_headers`);
  - add `mcpToolCatalogCacheEligible(config *ServerConfig, oauthCredentialsResolved bool) bool`;
  - extend `optionalStartupGraceKey` / a new HTTP fingerprint helper so the
    shared identity includes resolved env var values and agent plugin status;
  - apply the eligibility gate in `populateStatusInventories` where
    `sharedOptionalStartupDeadline` is computed for optional servers (only
    eligible servers may share the process-wide catalog identity; ineligible
    HTTP servers keep a per-call identity so each connection set warms its own
    catalog).
- `mcp/api_test.go`:
  - unit tests for `hasExplicitHTTPAuthorization` and
    `mcpToolCatalogCacheEligible`;
  - fingerprint-difference tests (env var value change, agent plugin change);
  - shared-grace test: eligible HTTP config shares deadline across calls;
    ineligible OAuth HTTP config does not reuse the shared catalog identity.
