### `1715e55076` #45185 - direct tool-call metadata (port)

Rust attaches a recorded direct call to the invocation's own output before it
enters history (`prepare_direct_call` + `attach_direct_call_to_output`), marks
`tool_calls_complete` when the arguments were fully recorded, bounds retained
direct metadata (1 MiB) with a clear order (tool-result metadata first, then the
executed calls), ties prepared records to a recorder-lifetime token so disabling
capture invalidates them, strips direct metadata from prompt/compaction inputs
when capture is disabled, and records call IDs that bypass local dispatch so
their reuse cannot establish Code Mode completeness. Go still uses the older
pending-then-attach-at-prompt model (`AttachPendingToPrompt` +
`CommitAttachment`), has no `tool_calls_complete` for direct outputs, no retained
budget, and no non-dispatched observation.

Go-side surface: `turn/executed_tool_calls.go` (recorder),
`turn/tool_dispatcher.go` (dispatch/attach), `turn/agent_loop.go` and
`turn/runtime.go` (prompt attach/strip), `turn/compaction` (history strip).

While auditing the last banner residual (`update_luna_reserve_reasoning`) the

  `UpdateReasoningEffort` / `PersistModelSelection` (and
  `UpdateLunaReserveReasoning` for the temporary Reserve model). The app then

  `sync_active_thread_reasoning_setting`), and (b) writes `model` /
  `model_reasoning_effort` through config persistence
  (`app/config_persistence.rs` `persist_model_selection`). The Reserve model is
  the exception: it updates the active task's effort without persisting a model
  default (`app/backend_banner_fallback.rs::update_luna_reserve_reasoning`).
- Go has the picker UI and the plan-mode-scope prompt, and
  `tui/tea/model.go::resolveModelPickerModal` updates `m.State` as well as
  returning a `PickerDecision`; but no production code consumes
  `ModalResponse.Picker` (both `OnModalResponse` handlers only forward to the
  approval/elicitation/user-input brokers), no code writes a `model` /
  `model_reasoning_effort` config key (the settings writers cover theme, pet,
  service tier, experimental features, and memories), and no callback updates
  the server thread's settings for a picked model/effort.

turns; it does not persist across restarts and does not update the remote

has no Go counterpart to fix until the base application path exists - so the
recorded `update_luna_reserve_reasoning` residual is folded into this lane.

## `#44341` residual: remote-control connections reject a retired owner's work

Rust binds every transport connection to the authentication owner that opened
it (`ConnectionAuth`, captured at `ConnectionOpened`); once the owner changes the
connection's RPC gate closes, so incoming messages are dropped and queued RPC
handlers never acquire a permit. Only remote-control connections carry auth
(`stdio`/`websocket` pass `None`), which is exactly Go's
`RemoteControlTransportServer`. Go tracked no owner on those connections.

- `appserver/remote_control_transport.go`: each remote-control connection
  captures `connectionAuthOwner(router)` (the login-lifetime generation) at open;
  `handleIncomingMessage` drops a message whose connection owner is no longer
  current, and the queued RPC goroutine re-checks before dispatching so a change
  detected after admission cannot run the handler under the previous owner.
- Tests: a connection initialized under owner A stops responding once the owner
  changes, and a connection opened under the new owner is admitted normally
  (verified to fail when both gates are removed).

Still open from `#44341` (recorded): cancelling in-flight remote-control
operations (Go's `RemoteControlConnectionAuth` carries the account id but no
owner generation for a call-time `ensure_current`), a replacement session
starting from a fresh replay cursor, and enrollment/preference persistence

## `#44341` residual: a live relay connection ends on an authentication change

Rust's remote-control websocket loop ends a live connection with
`ConnectionEndReason::AuthOwnerChanged` when the auth owner changes and retires
the session. Go only observed the revision during reconnect backoff, so a
connected relay kept serving the previous owner until something else stopped it.

- `remotecontrol/websocket_loop.go`: `runConnection` polls the owner revision
  alongside the enabled/status check (`connectionPollReason`) and ends with the
  new `remoteControlConnectionEndedAuthChanged` reason; `Run` retires the
  session there (retires the manager state, resets the relay's replay state,
  disables until the user enables remote control again), matching Rust's
  retire-on-identity-change and its fresh-state replacement session.
- Test: a live connection with a real websocket pair is retired to
  `disabled` (its enrollment cleared, its subscription cursor dropped, and the
  replacement connection started with no cursor) when the owner revision changes
  (verified to fail when the retire branch or the state reset is removed; run
  20x for flake resistance).

Still open from `#44341` (recorded): the reconnect-backoff path reconnects
instead of retiring when an owner change is observed during a drop (the
app-server's logout/switch handlers already retire, so this only differs for an
