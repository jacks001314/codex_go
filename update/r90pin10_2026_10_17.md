## 2. 可达性复核 (V 的论断, 我保留并加固)

- 到 `toolItemAnalyticsBase` / 四个专属 emitter 的调用点只有两处(全仓非测试 grep):
  `appserver/turn_runtime.go:1838-1844`(item 来自 `BuildThreadItem` -> **秒**) 与 `turn_runtime.go:3131`(`unifiedExecThreadItem` 终态 item -> ms, 且 `turn_runtime.go:3368-3374` 在 `status != InProgress` 时**必写** `completedAtMs`).
- `BuildThreadItem` 把 Metadata 合并进 Data(`protocol.go:3914-3920`), 而 `appTimingMetadata` 写的正是 ms 键 => 主流已完成路径**不缺 key, 不进回退**;
  回退只在「Data+Metadata 都没有时间键但 `CreatedAt > 0`」(旧 rollout / 无 metadata 条目, 例如从 Rust 侧写出的 rollout 读回)时命中. **修正 V 的一处措辞**: 命中时 `startedAtMs` 也为 0(同一来源缺 key), 故 `DurationMS` 等于 `completedAtMS`, 不是"时长被截断".
- 结论: 回退分支**只可能**收到秒值(所有 ms 生产者都自己带 ms 键) => `* 1000` 是**保守且不触碰主流路径**的修法; 我另加一条反向守卫断言(下方测试第 2 段)防止有人把转换做大(对已带 ms 键的 item 再乘 1000).

## 6. `thread_shell_command.go` 双单位: 只读判定

- `appserver/thread_shell_command.go:233` `StartedAt: active.StartedAtMS` — **毫秒**(`activeRuntimeTurn.StartedAtMS`, `runtime_router_test.go:10484` 以 `UnixMilli` 构造).
- `appserver/thread_shell_command.go:257` `StartedAt: response.Turn.StartedAt` — **秒**(`turn/api.go:582/665` = `s.now().UTC().Unix()`).
- 同结构体字段 `threadShellCommandRun.StartedAt int64`(`:32`) 因此**一名两单位**.
- 但它**只有一个消费点**: `:326` `completedTurnNotificationTurn(..., &run.StartedAt, ...)` -> `Turn.StartedAt`(`*int64`, wire `startedAt`), 且该行在 `if run.Standalone`(`:321`) 分支内; 而 `Standalone` 为真的分支恰好就是 `:257` 写**秒**的那条 -> **单位与 wire 一致, 当前无 live 断链**; `:233` 写的毫秒值**从未被读**.
- 另: `:323 duration := completedAtMS - startedAtMS` 用的是函数内局部毫秒变量, 不经 `run.StartedAt`.

**建议: 记 backlog(低危, 非 live 缺陷), 不本批修.** 理由: (1) 修 `:233` 是纯粹防未来的名字/单位陷阱, 当前可观察行为 0 变化, 属于"为绿而改"的邻域; (2) 更干净的做法是让 `threadShellCommandRun.StartedAt` 带单位后缀(如 `StartedAtMS`)并把 `:326` 处的秒值显式命名(如 `startedAtSec`), 这是一次小重构, 建议在碰这个文件的下一批里顺手做; (3) 若坚持现在改, 最小改动是 `:233` 改成 `active.StartedAtMS / 1000`(或该 turn 的秒值来源), 但那会引入一个当前无人读的"凑单位"赋值, 不如等重构.
