# Round 1215: Provisioning worker and settings-aware setup completion (2026-11-01)

Target: Rust main at 67f0994b532b8740f14b5b738af7b7b2a915b1d6 (#42342, crate
windows-sandbox-service; `provisioning.rs`).

## Context

Round 1213 dispatched requests to an injected handler but had no worker, and the
Go readiness check ignored the requested proxy settings, so a provisioned sandbox
with different listeners was reported complete. This round adds both halves.

## Setup completion

`windowssandbox.SandboxSetupIsCompleteWithSettings` ports Rust
`sandbox_setup_is_complete_with_settings`: the setup marker must match the setup
version, its proxy ports compared after sorting must equal the requested
listeners, the local-binding mode must match, and the credentials file must match
the version. A missing or malformed marker or credentials file is "not
complete", not an error.

## Provisioning worker

`windowsandboxservice/provisioning_windows.go` ports Rust `provisioning::run`:

- a `register_installation_request` only records the authenticated owner and
  returns `ok`;
- a legacy request duplicates the impersonated token, records the owner, checks
  completion as that owner (`ImpersonateLoggedOnUser` on a locked OS thread,
  revert required or the process exits), and returns `ok` when the recorded
  setup already matches;
- otherwise the packaged `codex-windows-sandbox-setup.exe` next to the service
  binary must exist as a regular non-reparse entry, and the injected
  `SetupRunner` performs the elevated provisioning; success logs
  `EVENT_PROVISIONING_SUCCEEDED` and failure logs `EVENT_PROVISIONING_FAILED`
  before the error becomes a bounded error response;
- a missing setup runner reports `ServiceUnavailable` so the client falls back to
  its interactive helper, matching the service's fallback contract.

The owner registrar and setup runner are injected, so the package-lifecycle and
retained-handle launch can land without reshaping this worker.
