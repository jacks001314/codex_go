# Round 1225: The registered provisioning transaction reaches the service (2026-11-01)

Target: Rust main at 67f0994b532b8740f14b5b738af7b7b2a915b1d6 (#42342,
`windows-sandbox-service/src/provisioning/registered.rs::run`; #45550).

## Context

Round 1224 could register both accounts, but nothing called it: a registered
Core request still answered "not available in this build". The service now runs
the whole registered transaction under one setup lock, from admission through
readiness, and reports readiness only after both accounts hold the package.

## Transaction

`RunRegisteredProvisioning` ports `provisioning/registered.rs::run`:

- Acquires the machine-wide sandbox setup lock for the whole transaction and
  refuses a request whose authenticated sandbox group no longer matches the
  live `CodexSandboxUsers` (`sandbox group changed before authentication`),
  before any owner is admitted.
- A refresh-only request may only resume the same owner, home, current package
  family, resumable record and complete setup, with both accounts enabled,
  unexpired and still owning their recorded SIDs; anything else is refused as
  "registration refresh requires unchanged sandbox ownership and settings" or
  "registration refresh cannot repair or replace a sandbox account".
- Records the authenticated owner, seeds the runtime record with the running
  package family and persists it before setup can rotate credentials.
- Re-inspects both managed accounts, asks `CredentialsNeedRepair` whether a
  credential mismatch needs full setup, and refuses a refresh that would repair
  setup or a setup owner that no longer matches the authenticated user.
- Registers both accounts through `ProvisionRegisteredRuntime` and logs the
  provisioning outcome like the legacy arm.

Go keeps legacy behaviour for the account-provisioning step: instead of Rust's
in-process `provision_sandbox_in_process`, it launches the packaged setup
helper (already the production `SetupRunner`) with the registered runtime, so
the resulting machine state is the same without moving the helper's account,
ACL and firewall work into the service library.

`HandleRequest` now returns the interruption as an error and
`RunProvisioningPipe` returns it instead of writing a response, so a
registration that is still running when shutdown arrives is never answered and
its objects survive until the process exits.

## Known gaps

cleanup (`package_lifecycle/cleanup.rs`), uninstall observation
(`package_lifecycle/registered.rs`), owner-aware cleanup and the
`OwnerRemoved` stop reason remain open, as does the installer/MSIX wiring for
the new service binary.
