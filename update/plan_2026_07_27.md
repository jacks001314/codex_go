# Codex Go 对齐计划（2026-07-27）

## 1. 目标与结论

本轮最大的缺口不是某一个 RPC 或工具，而是 Go 版缺少与 Rust `ThreadManager` +
`LiveThread` 对应的统一在线线程状态模型。当前线程记录、rollout、writer ownership、active
turn、订阅、状态和 terminal notification 分散在多个 map 与 service 中，单点功能虽然大多可用，
但 resume、fork、interrupt、shutdown、错误恢复和并发操作容易产生重复事件、漏事件或所有权漂移。

实施优先级如下：

| 优先级 | 工作域 | 目标 |
| --- | --- | --- |
| P0 | Live thread 状态模型 | 建立单一线程生命周期和资源所有权边界 |
| P0 | Paginated fork | 对齐 Rust 的分页 fork、ephemeral fork、边界和 replay 契约 |
| P1 | Remote code mode | 对齐远程 host、WebSocket、fallback 和 Responses metadata |
| P1 | MCP runtime | 对齐跨线程 refresh、auth 变化、authority 和重连语义 |
| P1 | Network / exec-server | 对齐 approval 取消与并发、network policy request 和 hook 输出 |
| P2 | Skills / plugins | 补齐 executor skill、Agent Plugin 和 publish 协议 |
| P2 | macOS release | 从“能在 macOS 测试”提升到“原生产物可发布” |
| P3 | TUI / analytics / Rust-only | 独立吸收用户可见改动，内部重构不机械移植 |

本计划采用渐进迁移，不一次性重写 `appserver.RuntimeRouter`。先引入统一对象和契约测试，再按
handler 逐条迁移；旧字段只能作为短期适配层，迁移完成后删除。

## 3. 当前架构诊断

### 3.1 Go 当前状态分散点

- `appserver/runtime_router.go`
  - `active`：active turn 和 cancel handle
  - `diffs`：线程 diff tracker
  - `ephemeralThreads`：额外的内存线程记录
  - `threadSubscriptions`：连接订阅关系
  - approval、MCP、selected skills、pending exec 等线程相关旁路状态
- `appserver/thread_status_manager.go`：线程状态单独维护
- `session/writer_lock.go`：跨进程单 writer ownership 已存在，但未成为在线线程对象生命周期的一部分
- `session.Store` / rollout recorder：记录、路径和 recorder 分别获取及释放
- `appserver/turn_runtime.go`：active turn 注册、取消、完成和 notification terminal path

这些组件各自加锁不能保证跨组件原子性。例如“占有 writer -> 注册 live thread -> 启动 turn ->
发送 terminal event -> 释放 recorder/writer”不是一个可审计的状态转换。

### 3.2 Rust 对齐方法

参考以下实现，不照搬 Rust 类型系统，但保持职责和状态转换一致：

- `codex-rs/core/src/thread_manager.rs`
  - `ThreadManager` 维护在线线程 registry 和共享服务
  - thread start/resume/fork 统一进入 manager
- `codex-rs/thread-store/src/live_thread.rs`
  - `LiveThread` 绑定线程存储、初始化、append、metadata 和关闭生命周期
- `codex-rs/core/src/session/session.rs`
  - session 创建/恢复时初始化 `LiveThread`
- `codex-rs/app-server/src/request_processors/thread_processor.rs`
  - paginated fork 先 `prepare_fork`，再按 boundary 创建目标线程

Go 的目标不是复制 Rust crate 边界，而是复制以下行为：单一 registry、单一资源 owner、初始化失败原子
回滚、terminal event 幂等、关闭顺序确定、持久化策略由线程来源和 history mode 决定。

## 4. 不可回归契约

以下契约在 Phase 0 先固化，之后每个阶段都必须通过：

1. fresh thread 在首次 user message 前不创建 rollout 或 persisted `thread/list` 记录。
2. `ThreadStartParams.Prompt` 只影响启动配置，不伪造成 user item。
3. ephemeral 或 non-local thread 不落入本地持久化列表。
4. 每个 command item 的 `started` 和 `completed` 各出现一次。
5. 每个 turn 的 final agent message 和 `turn/completed` 各出现一次。
6. final agent message 必须先于对应 `turn/completed`。
7. shell/tool rejection 必须以 JavaScript Promise rejection 返回，可被 `try/catch` 捕获。
8. JavaScript runtime 不得派发空 `exec`，也不得把失败调用静默重试成重复命令。
9. writer ownership 冲突必须在任何 rollout、DB、registry 副作用之前原子失败。
10. resume/fork 不重复 replay tool output、command completion 或 final message。
11. paginated cursor 与 non-paginated cursor 不混用；fork lineage 禁止错误的增量游标读取。
12. interrupt、disconnect 和 shutdown 竞争时，只能产生一个 terminal outcome。
13. hook 子进程在读取 stdin 前退出时，已经产生的 stdout/stderr 仍被保留。
14. item completion 的 start time 必须来自原始 started event，不能在 completion 时重新生成。

## 6. Phase 1：引入统一 LiveThread / ThreadManager（P0）

### 目标结构

建议先增加以下最小对象，命名可在实现时按 Go 包边界微调：

```text
appserver.ThreadManager
  registry[ThreadID] -> ManagedThread

appserver.ManagedThread
  session.LiveThread
  ActiveTurn
  Subscribers
  DiffTracker
  Status
  TerminalLedger

session.LiveThread
  Record / HistoryMode / Source
  RolloutPath / Recorder
  WriterLock
  Persisted / Ephemeral / NonLocal
  Init / Append / UpdateMetadata / Close
```

### 迁移规则

- `ThreadManager` 是在线线程 registry 的唯一入口；禁止 handler 直接写多个 router map。
- `session.LiveThread` 是 writer lock、recorder、rollout path 和持久化 record 的唯一 owner。
- 使用 init guard：任一步初始化失败，逆序释放 recorder、writer、registry 和临时状态。
- `ManagedThread` 内部用一个 mutex 保护跨字段状态转换；耗时 I/O 不在锁内执行。
- `TerminalLedger` 以 `(threadID, turnID)` 记录 terminal outcome，notification sink 重试不能重复发送。
- `RuntimeRouter` 第一阶段保留同名 helper，但内部转发到 manager；禁止同时双写旧 map 和新 registry。
- close 顺序固定为：阻止新 turn -> cancel/wait active turn -> flush terminal -> close recorder -> release writer ->
  remove registry -> notify status。

### 第一批迁移

1. `thread/start` 和首次 user message 的 lazy persistence。
2. `thread/resume` 的 writer ownership、record load 和 replay。
3. `turn/start`、`turn/interrupt`、turn completion。
4. router/connection shutdown。

### 退出条件

- 旧的 `active`、`diffs`、`ephemeralThreads`、`threadSubscriptions` 至少不再被首批 handler 直接修改。
- start/resume/turn/interrupt/shutdown 全部通过 race test。
- 注入每个初始化步骤失败时，无残留 lock file、rollout、registry entry 或 terminal notification。

## 7. Phase 2：迁移完整线程生命周期（P0）

### 工作项

- 迁移 `thread/read`、`thread/list`、`thread/turns/list`、`thread/items/list`。
- 迁移 `thread/fork`、archive/unarchive/delete/rollback 的资源预占和释放。
- archive/delete 对 descendant tree 按稳定顺序批量获取 writer ownership；任一冲突则整批无副作用失败。
- 统一 fresh、persisted、ephemeral、non-local、imported thread 的 persistence policy。
- hook transcript 不为 non-local thread 创建本地 session。
- metadata update、name update 和 item append 通过 `LiveThread` 排序，不直接改 record 后另行落盘。
- item start time 在 started 时进入 turn timing state，在 completion projection 中读取。

### 退出条件

- 所有 thread handler 只通过 manager 获取 live state。
- list/read 不会暴露 fresh、ephemeral 或 non-local 本地记录。
- concurrent resume/fork/archive/delete 的成功/冲突行为与 Rust raw JSON-RPC 对齐。

## 8. Phase 3：Paginated fork 与 replay 对齐（P0）

### Rust 参考

- `05f000263b`：paginated thread fork
- `1811b67a84`：ephemeral fork of paginated thread
- `codex-rs/thread-store/src/local/paginated_fork.rs`
- `codex-rs/app-server/tests/suite/v2/thread_fork.rs`

### 工作项

- 在 Go thread store 增加 `PrepareFork`，输入 boundary：
  `Latest`、`ThroughTurn(turnID)`、`BeforeTurn(turnID)`。
- `PrepareFork` 返回已验证的 model context、terminal prefix、source metadata 和 rollout lineage；handler
  不自行拼接 JSONL。
- active paginated turn 被 fork 时，source snapshot 只能落为一个 interrupted terminal state。
- paginated fork 使用 reference-backed lineage，禁止伪装成普通 rollout 后继续使用 incremental cursor。
- ephemeral paginated fork 要求 `excludeTurns=true`，保持 pathless、不进入 list，并可继续 turn。
- 保留 approval reviewer、thread name、CWD、model context、config snapshot 和合法父子关系。
- fork replay 以 `(turnID, itemID)` 去重，保留 creation ordinal，仅推进 update ordinal。

### 必测边界

- latest、through named turn、before named turn。
- compacted history、缺失 boundary、active turn、空 history。
- persisted 与 ephemeral 目标。
- source writer 冲突、target 初始化失败、fork 后 resume。
- paginated/non-paginated cursor 误用必须返回明确 invalid request。

### 退出条件

- Rust `thread_fork.rs` 中可映射的行为测试在 Go 有对应 table cases。
- SDK/raw app-server 场景中无重复 user/tool/final item，fork 后工作区副作用只发生一次。

## 10. Phase 5：MCP runtime refresh 与 authority（P1）

### 当前判断

Go 已有单 service 的 `Refresh()`、健康连接复用和 catalog 保留；缺口是 Rust 的线程级 runtime refresh
协调、启动期 prewarm、auth/requirements 触发、显式 refresh 重连和 current authority 传播。

### 工作项

- 在 `ThreadManager` 建立 MCP refresh coordinator，对活跃线程快照后逐线程更新，不持有 registry 锁做网络 I/O。
- thread startup 期间的 refresh 与新 thread 初始化协调，不能漏更新或重复发布 catalog。
- auth revision 变化、managed MCP requirements 变化、独立 thread config 变化均触发正确范围的 refresh。
- background prewarm 完成后原子替换 runtime；失败保留旧健康 runtime 并报告 warning。
- 显式 `mcpServer/refresh` 强制 reconnect；普通无身份变化 refresh 继续复用健康连接。
- elicitation review 在决策时读取 current MCP authority，不使用 turn start 时的过期 snapshot。
- OAuth discovery 和 token 操作使用 runtime 最终 HTTP client，继承 proxy、CA、timeout 和 policy。
- 无 allowlist 时不执行 plugin MCP filtering；有 allowlist 时维持现有 fail-closed 行为。
- 将 MCP server recursion limit 对齐 Rust，并增加深度边界测试。

### 退出条件

- 多线程同时 start、auth change、explicit refresh 时，每个 runtime 只发布一次最终 catalog。
- Apps catalog、资源和工具在可复用连接 refresh 后不回退。
- 本地 MCP fixture 覆盖 stdio/HTTP、断线、auth revision 和递归边界。

## 11. Phase 6：Network approval、exec-server 与 hooks（P1）

### 工作项

- 对齐 network approval state machine：pending、resolved、cancelled、turn terminal，只有一个状态可获胜。
- 同一 turn 的并发 network denials 可独立等待，不复用错误的 request/response channel。
- interrupt/disconnect 时取消所有未决 approval，late response 被忽略且不改变 terminal outcome。
- exec-server client 接收 network policy server request，并把 decision 返回原连接；恢复/重连不能丢 pending request。
- 保持 network policy amendment 的 Rust snake_case wire shape。
- hook runner 同时 drain stdout/stderr 和写 stdin；子进程先退出时仍保存已输出内容。
- `09241ae4db` 的 reqwest 解耦属于 Rust 内部边界，Go 只审计外部 HTTP/policy 行为，不复制 crate 重构。

### 退出条件

- `go test -race` 覆盖 approval cancel/resolve/interrupt/shutdown 交错。
- raw events 中 approval request、resolution、command completion 和 turn terminal 均不重复。

## 12. Phase 7：Skills、plugins 与 deferred tools（P2）

### 工作项

- 支持 Agent Plugin manifest，并与现有 plugin manifest 明确版本和 namespace 规则。
- executor skills 通过 skill tools 暴露，显式 skill 可读取授权范围内 resource。
- resource read 保持 provider authority，不允许将任意 host path 当作 skill resource。
- 暴露 workspace plugin publish capability 和 app-server wire fields。
- remote plugin ID 贯穿 skill metadata、script attribution 和 analytics，但不得泄漏本地绝对路径。
- skills watcher 忽略生成的 system skills，避免 self-trigger refresh loop。
- extension warnings 按所属 thread 发送一次，并进入 terminal ledger 去重路径。
- host skill path 在 metadata 压力下按 Rust 策略压缩，引用仍可解析。
- deferred tool search 记录 namespace，合并 sources 时去重。
- host 可自定义 `wait_for_environment` description，默认描述保持兼容。

### 退出条件

- manifest、authority、resource traversal、warning duplication 和 remote ID 都有负向测试。
- app-server schema snapshot 与 Rust 对应字段一致。

## 17. 推荐实施切片

为控制 review 和回滚范围，按以下顺序提交独立变更；每个切片必须自行通过第 14 节门禁：

1. Contract fixtures、raw audit、JS runtime deterministic scenarios。
2. `session.LiveThread` + init guard，不迁移 handler。
3. `ThreadManager` registry + start/resume/turn/interrupt/shutdown 迁移。
4. read/list/archive/delete/fork handler 迁移，删除相应旧 map 直写。
5. paginated `PrepareFork`、lineage、ephemeral fork。
6. remote code-mode WebSocket、fallback、metadata。
7. MCP refresh coordinator、triggers、authority、HTTP client。
8. network approval/exec-server/hook race fixes。
9. skills/plugins/deferred tools 协议。
10. macOS release artifact/signing gate和 P3 用户可见同步。

禁止把 2-5 合成一次大提交。统一状态对象只有在实际 handler 迁移并删除旧旁路后才算完成，单纯增加一个
wrapper 不算解决缺口。
