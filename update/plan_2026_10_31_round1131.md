## Findings

- #42773 (Rust `c9fac4dd5a`) releases the global `thread_list_state_permit`
  while a cold `thread/resume` loads configuration, then reacquires it, reloads
  configuration when persisted metadata/settings/history-cwd changed during the
  unlocked interval, rejoins threads resumed concurrently, and skips threads
  archived or deleted in that window.
- The Go app server has no global metadata permit to release. Cold resume takes
  per-thread writer ownership in `ThreadManager.AcquireLiveThreadRetention`
  (`appserver/thread_manager.go:197`); its `liveThreadsMu` is released when the
  call returns. Configuration for the resumed thread is loaded afterwards by
  `RuntimeRouter.effectiveConfigForTurn` via `config.LoadWithOptions`
  (`appserver/turn_runtime.go:10363`) with no shared lock held, so unrelated
  thread metadata updates and MCP requests are never serialized behind resume
  config loading — the regression the Rust commit fixes cannot occur.
- Go already re-reads the stored snapshot under the acquired retention
  (`refreshedResumeRecord`, Rust #49599), and rejects archived threads before
  ownership is taken (`threadResumeArchivedError`). No permit-scoped reload loop
  or rejoin path is needed.
- Decision: #42773 is `not_applicable` for the Go implementation.
