# Round 1216: Service-side owner persistence and lifecycle pinning (2026-11-01)

Target: Rust main at 67f0994b532b8740f14b5b738af7b7b2a915b1d6 (#42342, crate
windows-sandbox-service; `package_lifecycle.rs`).

## Context

Round 1215 wired the provisioning worker to an injected owner registrar, but the
registrar itself had no carrier: nothing persisted the authenticated owner, and
nothing retained the owner token or pinned home that uninstall cleanup needs.
This round adds that carrier.

## Installation record writes

`sandbox/windowssandbox/installation_record_service.go` adds
`LoadRuntimeInstallation`, and the Windows-only
`installation_record_service_windows.go` adds:

- `SaveInstallationRecord`: takes the `Global\\CodexSandboxSetup` lock (5 s
  budget), drops the caller's runtime receipts so a client cannot smuggle its
  own journal in, loads the current runtime as the service, runs
  `AdmitOwner` against the current package family (refusing a different owner
  or home, a retiring installation, or pending cleanup), then restores the
  loaded runtime receipts and flushes the record.
- `InstallationIsCurrentPackage`: case-insensitive package-family comparison,
  treating a missing runtime as an error instead of a match.

## Package lifecycle

`windowsandboxservice/lifecycle_windows.go` ports
`PackageLifecycle::register_authenticated_user`:

- previous ownership (retained or loaded) must match the new owner and home, and
  a refused mismatch surfaces as `ServiceUnavailable`;
- desktop ownership recorded earlier is merged forward;
- the record is saved under the setup lock, so a concurrent client cannot
  interleave;
- the first registered owner impersonates the owner, pins every existing
  ancestor, guards the home with `CreateDirectoryGuard`, re-probes the final
  path and retains the duplicated token and handles;
- a home that cannot be pinned is logged as `EVENT_SERVICE_FAILED` and left
  unpinned, so cleanup skips file removal rather than acting on an unverified
  path;
- a retained installation keeps its pins but adopts the newly saved record, and
  a duplicate token is closed rather than leaked.

`Lifecycle.ServeProvisioningRequest` composes the lifecycle with
`RunProvisioning` so provisioning and registration share one owner registrar.

## Known gaps

`provisioning/registered.rs` refresh under the setup lock with
unchanged-settings verification, managed-policy load as the impersonated owner,
`run_elevated_provisioning_setup_with_retained_handles`, package uninstall
observation and cleanup (`PackageCatalog` + `PackageUninstalling`,
`package_lifecycle/cleanup.rs`), `ServiceStopReason` diagnostics, WTS session
restore, `service/runtime_lifecycle.rs` and the registered-runtime transactions
remain open.
