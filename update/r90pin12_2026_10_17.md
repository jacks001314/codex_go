## 6. 未决 / 未覆盖

### 6.1 load arm reachability from account/read (observation, not a code gap)
Go's `handleGetAccount` resolves the forced-login restrictions before workspace routing, and `loginRestrictionViolation` (`appserver/runtime_router.go:1224`) reads the effective configuration - so with a malformed `config.toml` the *raw* `config.ConfigLoadError` is returned first:
`workspace_routing_test.go`-side probe: `error message = "failed to load configuration from <home>\config.toml: toml: array is incomplete"` (no `failed to load workspace requirements` prefix).
Rust has no such pre-read on this path (`enforce_login_restrictions` takes an already-loaded `AuthConfig` and is only called from `exec`/`tui`, not from the app-server: `login/src/auth/manager.rs:1317`). So Rust's `RequirementsLoad` arm is the one reached by the Rust v2 test, while in Go the same malformed file is reported by the login-restriction step.
Consequence: the load arm was therefore tested through the routing entry (Rust's own unit-test entry, `read_account_for_background_workspace_routing`), and the *reload* arm is the one reached through `Handle`. Left as a finding for the captain: making the account-read config failure safe (same #53805 reasoning, different carrier) would be a separate, un-scoped change to `runtime_router.go` - not done here.

### 6.2 blast radius of the signature change
`workspaceRoutingConfigIdentity` is referenced only at `workspace_routing.go:92/124` (grep, whole repo). Neither the load nor the reload message is asserted anywhere else and no `errors.Is(err, model.ErrWorkspaceRoutingRequirementsReload)` consumer exists (grep: only `model/workspace_routing.go:35` plus the two changed sites), so the signature/message change cannot alter another package's expectations.

### 6.3 cloud arm is unit-only
Go's routing config read (`ConfigService.Read` -> `loadConfigFile`) never loads a cloud bundle (`CloudConfigBundle` is consumed by `config/managed_requirements.go:28` and `config/config.go:373` under `IncludeManagedConfig` + an explicit bundle). So `workspaceConfigLoadReasonFromCloudError` has no live producer on the routing path yet; it is implemented for Rust parity and pinned by unit tests only. The Rust v2 expectation `failed to load workspace requirements: cloud config: invalid bundle` therefore has no Go end-to-end analogue today.

### 6.4 fallback platform caveat
Rust's tail prints `io::Error::from_raw_os_error(code).to_string()` (`"<strerror> (os error N)"`); Go prints `syscall.Errno.Error()` (`"<strerror>"`, no code suffix, Go's own strerror casing). Both are OS text and neither carries a path or a config value, so the safety property holds; the exact byte string does not match Rust on a raw OS error. Go also has no `io::ErrorKind::InvalidData` equivalent, so a raw TOML decode error would report `other` instead of Rust's `invalid data` - the loader types every TOML failure as `config.ConfigLoadError` before this point, so it is unreachable in practice.
