# Rust #48272: Windows daemon launcher stdio inheritance

Upstream commit: `dfdb40cd0b72dfba3293db5c7c441232e8ef1a60`

## Result

Equivalent end state with a different Windows carrier.

- Rust clears `HANDLE_FLAG_INHERIT` on the launcher's stdin/stdout/stderr
  before spawning a detached managed process and tolerates missing or
  already-closed handles.
- Go's `syscall.StartProcess` always passes an explicit
  `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` containing exactly the child's configured
  stdio handles plus `SysProcAttr.AdditionalInheritedHandles`. Unrelated
  inheritable handles, including the launcher's captured output pipes, are
  therefore never propagated to the detached child, without mutating the
  launcher's own handles.
- The detached child uses its own `NUL` stdin/stdout and configured stderr log,
  matching Rust's child stdio configuration.

## Verification

```text
go test ./appserverdaemon -run 'TestDaemonLaunchDoesNotRetainLauncherStdio' -count=1
go test ./appserverdaemon -count=1
```

The regression test makes the launcher's stdout/stderr inheritable, starts the
detached child, and requires the launcher's captured output to reach EOF while
the child stays alive and writes only to its configured log.

Passed on 2026-10-18.
