# Round 1185: preserve PowerShell relative paths in the elevated sandbox (2026-10-31)

Target: Rust `main` at `cbe16d525c2d7362fc3d4726143288e932905daa`.

## Gap

- #49690 (`7e8878f6`) found that an inaccessible user profile makes sandboxed
  PowerShell lose its working directory and fail to resolve `.\relative` paths
  when the project sits beneath `USERPROFILE`.
- Go's elevated payload did not carry `USERPROFILE`, and the helper never
  granted the sandbox group even read-attributes access to the profile root.

## Evidence

- `sandbox/windowssandbox/setup_windows.go`: `setupElevationPayload` carries
  `user_profile`; `runElevatedSetup`, `runSetupRefresh` and
  `runSetupRefreshForRequest` forward the trimmed `USERPROFILE`, and the
  provisioning payload does the same like Rust's retained-handle provisioning
  path.
- `sandbox/windowssandbox/bin/setup_main/win/run_windows.go`:
  `setupPayload.UserProfile` feeds `grantUserProfileReadAttributes`, which
  requires an absolute profile containing `CommandCWD` and grants the sandbox
  group non-inheriting `FILE_READ_ATTRIBUTES`. Grant failures are logged and
  never fail setup.
- Non-inheriting grants preserve existing permissions and deny ACEs; the
  generic deny check already maps `GENERIC_*` bits through
  `mapFileGenericMask`, so a generic deny blocks a conflicting allow.
- Tests: `TestSetupPayloadCarriesUserProfileLikeRust`,
  `TestSetupPayloadFromEnvironmentTransportLikeRust`,
  `TestGrantUserProfileReadAttributesIsNonInheritingLikeRust` (an unprotected
  child's security descriptor is unchanged),
  `TestGrantUserProfileReadAttributesSkipsCommandOutsideProfile`, and
  `TestDACLHasDeniedMaskExpandsGenericMaskLikeRust`.
