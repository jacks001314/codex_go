real data-loss bug in the config write API, not a network flake.

## What changed

- `ConfigService.BatchWrite` splices `mcp_servers` replace edits into the
  existing document so comments and unrelated sections keep their bytes
  (Rust `ConfigDocument::apply` / `replace_mcp_servers`). It fetched the table
  with `values["mcp_servers"].(*OrderedTable)`, but parsed and just-edited
  values are plain maps, so the type assertion always failed and the splicer
  received nil.
- Consequences on `origin/main`: replacing `mcp_servers` on a config with no
  servers wrote an empty file; replacing it on a config that already had
  servers deleted every `[mcp_servers.*]` table and wrote nothing. Skill MCP
  dependency auto-install and `codex mcp add`-shaped writes both hit this.
- `orderedMCPTable` converts the plain map into the ordered table the splicer
  expects (sorted keys, matching `renderTOML`), so the in-place splice runs.
- Regression tests: `TestBatchWriteReplacesMCPServersTableLikeRust` (comments,
  unrelated keys and old servers survive correctly) and
  `TestBatchWriteReplacesMCPServersOnFreshConfigLikeRust`.
