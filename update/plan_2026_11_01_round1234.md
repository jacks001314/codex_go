## #49067 policy rejection events

`windowsandboxservice/policy_rejection_windows.go` ports
`ipc::policy_rejection_diagnostic` and the two decisions
`ipc::handle_request` makes around a failed policy check:

- `policyRejectionStage` maps the loader labels to `runtime`, `bootstrap`,
  `resolve_auth`, `initialize_auth`, `managed` and `enforce`, and reports
  `unknown` otherwise. Rust compares the whole anyhow message; Go's wrappers
  append their cause, so a label also matches as a prefix.
- `policyRejectionDetail` reports the first typed cause: `cloud=<Code>
  http=<Some(n)|None>` for a bundle failure, `io=<Kind> win32=<Some(n)|None>`
  for an OS failure (named the way Rust's `io::ErrorKind` Debug is),
  `io=InvalidData win32=None` for a configuration failure, and
  `cause=unavailable` when nothing typed is in the chain. Parser text never
  reaches the event, so a configuration line with credentials cannot be logged.
- `policyViolationResponse` answers `Unavailable` when the failure is a TOML
  parse error (`isConfigParseError`), otherwise records
  `EVENT_REQUEST_REJECTED` and returns the bounded `Error` whose message
  starts with `requested sandbox settings violate administrator-controlled
  machine policy`.

Two supporting corrections: `HandleRequest` now routes the policy failure
through that helper, and `ValidateProvisioningRequest` returns Rust's bare
`configuration runtime worker failed to impersonate the provisioning client`
message (the sentinel `errOwnerImpersonation` keeps the cause out only for that
failure, so a loader failure still keeps its own chain).

`policy_rejection_like_rust_test.go` covers every stage, the cloud and io
detail forms, the credential-free event text, the parse/IO distinction and the
single logged event with the `Error` response.
