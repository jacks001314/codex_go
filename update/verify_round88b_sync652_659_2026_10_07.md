### ① sync656 `interruptThread`：单槽被别的线程占用时是否**静默跳过**而不误 cancel ⇒ **CONFIRMED（best-effort，不误伤）**

生产代码（`app/interactive.go:473-503`：`:482-485` 线程守卫，`:501` cancel）：

```go
c.mu.Lock()
if c.threadID != threadID {
    c.mu.Unlock()
    return false          // ← 槽位属于别的线程：静默 no-op，不动 cancel
}
cancel := c.cancel
...
c.mu.Unlock()
...
if cancel == nil { return false }
cancel()                  // ← 只在记录线程匹配时才 cancel
```

Rust 同态：`App::active_turn_id_for_thread`（`tui/src/app/thread_routing.rs:159-163`）按 **per-thread event channel** 取该线程自己的 active turn；取不到返回 `None`（`tui/src/app/side.rs:450-459` 的 `discard_side_thread_in_background` 用 `unwrap_or_default()`）。**Rust 侧天然按线程隔离，Go 用「单槽 + threadID 守卫」达成同一「不误伤」性质。**

独立证据（仓内，全部实跑 PASS）：

```
=== RUN   TestInteractiveLocalSideCloseKeepsOtherRunningTurn
--- PASS: TestInteractiveLocalSideCloseKeepsOtherRunningTurn (0.38s)
=== RUN   TestInteractiveInterruptControllerInterruptThreadScopesToThread
--- PASS: TestInteractiveInterruptControllerInterruptThreadScopesToThread (0.00s)
```
（后者逐条断言：空 threadID→false；未跟踪→false；**其它线程→false 且该线程 turn 未被 cancel**；本线程→true 且被 cancel；调用后跟踪态清空。）

Rust 对照原文（`C:\rw` HEAD）：`tui/src/app/side.rs:549-558`

```rust
let interrupt_result =
    if let Some(turn_id) = self.active_turn_id_for_thread(thread_id).await {
        app_server.turn_interrupt(thread_id, turn_id).await
    } else {
        app_server.startup_interrupt(thread_id).await
    };
```

**观察 6-a（非阻断，建议登记）**：Go 的 `interruptThread` 在「本线程无在飞 turn」时直接返回 false，**没有** Rust 的 `startup_interrupt(thread_id)` 回退臂（Rust 注释：`Replay-only sides may still be running after reconnect, so always interrupt.`）。远程/daemon 侧 `app/remote_tui.go:1259-1306` 同样只在跟踪到该线程时发 `turn/interrupt`，也无 startup 回退。⇒ Go 的 side-close 中断是 Rust 的**真子集**（少一条 startup-interrupt 兜底），语义方向一致（仍不误伤他线程），非安全漏洞。

**观察 6-b（覆盖缺口，建议登记）**：`runInteractiveTUI` 里那行**生产接线**
`OnCloseSide: interactiveLocalSideClose(interrupts, sideCoordinator)`（`app/interactive.go:1290`）**无任何测试覆盖**——我把该行单独回退成 `sideCoordinator.Close` 后：

```

```

⇒ 仓内测试只覆盖 handler **内部行为**（直接调用 `interactiveLocalSideClose(...)`），不校验它被装进 `Options.OnCloseSide`。要闭合该缺口需一个走 `runInteractiveTUI` 的装配级断言（本轮只读，不落补丁）。

### ② sync659 `GitDirPointerTarget` 三边界 vs Rust `resolve_gitdir_from_file` ⇒ **CONFIRMED（三边界同态）**

Rust 权威原文（`C:\rw` = `5b0b253035`，`codex-rs/protocol/src/permissions.rs:2573-2629`）：读文件失败→`None`；`split_once(':')` 且 `prefix.trim()=="gitdir"` 否则 `None`；`gitdir_raw.trim()` 空→`None`；`base = dot_git.parent()`；`resolve_path_against_base(gitdir_raw, base)`（`utils/absolute-path/src/lib.rs:46-57`，词法归一）；`!exists()`→`None`；否则 `Some(path)`。另 `is_git_pointer_file`（`:2568-2571`）= `is_file()` 且 `file_name()==".git"`。

| 边界 | Go（`sandboxpath.go:157-182`） | Rust | 结论 |
|---|---|---|---|
| 相对 `gitdir:` 路径 | `Clean(raw)`；`!IsAbs` 时 `Join(Dir(dotGit), target)` | `resolve_path_against_base(raw, parent)` | **同态**（Go 实跑 PASS，探针 B） |
| 目标不存在 | `os.Stat(target)` 出错 → `("",false)` | `!exists()` → `None` | **同态**（探针 C PASS） |
| 目标为目录 | `Stat` 成功（不判 `IsDir`）→ `(target,true)` | 只判 `exists()` → `Some` | **同态**：目录目标被**接受**（探针 D PASS） |
| 指针本身是目录 | `info.IsDir()` → false | `is_file()` 为假 → 非指针 | **同态**（探针 D PASS） |
| 非 `gitdir:` 内容 / 空目标 | `prefix!="gitdir"` / `raw==""` → false | 同上 → `None` | **同态**（探针 D PASS） |

**注意文档措辞**：`sandboxpath.go:155-156` 注释写「reports false for a directory」——该「directory」指的是**指针文件本身**（对应 Rust `is_git_pointer_file` 的 `is_file()`），**不是**目标。目标为目录时两边都返回 true/Some，探针 D 已钉死；建议后续把注释写清以免误读（只读建议，不落补丁）。

**自查后已证伪的怀疑（留档）**：Rust `#47974` 把 carveout 纳入条件写成 `WritableRootPathResolution::Effective => cfg!(target_os="linux")` / `PreserveMutableComponents => cfg!(target_os="macos")`（`permissions.rs:1590-1594`），而 Go 的 `addResolvedGitDirCarveouts` 无 GOOS 门。我据此怀疑 Windows 行为分歧，**核查后证伪**：
