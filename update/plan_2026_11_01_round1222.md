# Round 1222: Registered runtime ownership, retention and package queries (2026-11-01)

Target: Rust main at 67f0994b532b8740f14b5b738af7b7b2a915b1d6 (#45550,
`windows-sandbox-service/src/registered_runtime.rs`; #42342, #42375 for the
cleanup-ownership preconditions).

## Context

The service could already record a registered-Core owner and receipt, but it
could not answer the questions the registered-runtime lifecycle depends on:
whether a record is coherent, whether cleanup still owns its accounts, whether
an account's logon is the account the record names, and whether any account
still has a package from the record's family. Those answers decide when cleanup
may release resources, so they must be exact rather than best-effort.

## Runtime ownership

`windowsandboxservice/registered_runtime_windows.go` ports
`registered_runtime.rs`:

- `ValidateRuntimeRecord` refuses more than two accounts and a record that
  names the same managed account twice.
- `PrepareRuntimeCleanup` validates the record, then re-resolves every account
  that still exists locally (`NetUserGetInfo` level 1 flags) and refuses a
  replaced account, an unfinished retiring journal, or a pending cleanup logon.
  A removed local account is skipped, matching Rust.
- `ValidateRuntimeTarget` reads the logon token's SID, refuses a changed SID,
  a replaced account, an account holding `S-1-5-32-544` (even disabled) and a
  token without an enabled `CodexSandboxUsers` membership.
- `RuntimeAccountProfile` loads the account profile with `LoadUserProfileW`
  and `PI_NOUI`, unloads it before the account is re-disabled and closes the
  logon token on `Close`, mirroring Rust's `AccountProfile` drop ordering.
- `ErrRuntimeSetupInterrupted` carries the Rust `RegistrationInterrupted`
  message so a future registration transaction can escape request handling
  without answering the client.

## Package queries

`windowsandboxservice/winrt_windows.go` adds the minimal Windows Runtime ABI
the service needs (HSTRING lifetime, apartment initialization, activation and
vtable dispatch), and `registered_packages_windows.go` ports
`registered_packages`/`has_retaining_registration` on top of it:
`PackageManager.FindPackagesByUserSecurityIdPackageFamilyName` followed by
IIterable/IIterator iteration and `IPackage.Id().FullName()`. Iteration errors
propagate, because an authoritative empty answer is what allows cleanup to
release ownership; `RuntimeHasRetainingRegistration` stops at the first
account that still holds a package.

## Known gaps

Package registration (`RegisterPackageByFullNameAsync` plus the async status
loop and `RegistrationResult`), `provisioning/registered.rs`, metadata
grants/removal, `registered_runtime/removal.rs`, native packaged cleanup,
uninstall observation and the `OwnerRemoved`/`RegistrationInterrupted` stop
reasons remain open. Logging on an existing sandbox account is still
unported, so the transaction that consumes these seams cannot run yet.
