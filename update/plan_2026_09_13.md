### `1715e55076` #45185 - direct tool-call metadata (port)

Rust attaches a recorded direct call to the invocation's own output before it
enters history (`prepare_direct_call` + `attach_direct_call_to_output`), marks
`tool_calls_complete` when the arguments were fully recorded, bounds retained
direct metadata (1 MiB) with a clear order (tool-result metadata first, then the
executed calls), ties prepared records to a recorder-lifetime token so disabling
capture invalidates them, strips direct metadata from prompt/compaction inputs
when capture is disabled, and records call IDs that bypass local dispatch so
their reuse cannot establish Code Mode completeness. Go still uses the older
pending-then-attach-at-prompt model (`AttachPendingToPrompt` +
`CommitAttachment`), has no `tool_calls_complete` for direct outputs, no retained
budget, and no non-dispatched observation.

Go-side surface: `turn/executed_tool_calls.go` (recorder),
`turn/tool_dispatcher.go` (dispatch/attach), `turn/agent_loop.go` and
`turn/runtime.go` (prompt attach/strip), `turn/compaction` (history strip).

### `e61f381900` #45182 - N/A

Rust hand-walks the TOKEN_GROUPS buffer and copies SIDs into owned values, so it
now validates the layout, SID bounds, revision, and length with a shared
size-limited helper. Go delegates to `golang.org/x/sys/windows`
(`Token.GetTokenGroups()`) and only reads the returned `SIDAndAttributes`
(`sandbox/windowssandbox/token_windows.go` `scanTokenGroupsForLogonSID`), so
there is no raw buffer walk to harden and no owned group list to build. No Go
change; the equivalent robustness comes from x/sys's own sizing/validation.

### `cfde11a24c` #45180 - N/A

The commit extracts `PreparedNetworkConfig` from the loader
(`build_network_proxy_spec`) preserving behavior, and adds helpers for
*per-environment* network policy (`project_environment_profile_network`,
`validate_environment_network_policy`, `build_environment_policy`). Go's loader
already applies managed network requirements after permission fallback
(`appserver/managed_network_constraints.go`), and Go does not model a
per-environment `network` table at all (`appserver/environment_config.go` has no
network field; `network.EnvironmentNetworkPolicy` has no production caller), so
the new helpers have no Go consumer. Recorded as a prerequisite for the
environments-network feature, not as a change in this range.

### `a4c61afff2` #45178 and `dfaf451426` #45169 - N/A

Both are Rust-internal extractions of the Windows sandbox service/library
(package-lifecycle cleanup phases; setup provisioning and installation-record
storage moved into the library while preserving the registry key, size limit, and
serialization). Go's elevated sandbox is structured differently (helper
materialization plus setup-completion polling) and has no installation-record
storage or service provisioning module to split, so there is nothing to
restructure and no behavior change to land.

### `c379459bba` #45176 - lane (blocked on native MXC)

Adds the `WindowsSandboxLevel::Mxc` backend, the `windows_mxc` sandbox tag, the
`WindowsMxc` violation backend, and MXC execution through the codex executable
with the effective permission profile. Porting needs (1) the enum/tag/violation
values, which are portable, and (2) the native MXC launcher
(`codex-rs/mxc-sandbox/src/native`, `is_available`, `run_main`) which requires
binding the native process-security API and cannot be exercised here (Rust skips
its native tests when MXC is unavailable). Recorded as a Windows-native lane.

### `1715e55076` #45185 - done (Go side), commit `e637a56e`

- `turn/executed_tool_calls.go`: `PrepareDirectCall` reserves a pending slot and
  snapshots the invocation; `AttachDirectCallToOutput` appends the record to the
  invocation's own output, sets `tool_calls_complete` when the arguments were
  fully recorded, and applies the 1 MiB retention budget in Rust's clear order
  (tool-result metadata first, then the record). The pending-direct map is
  replaced by a non-zero-sized `executedToolCallLifetime` token, so a record
  prepared before capture was disabled can no longer attach (Go may give
  distinct zero-sized allocations the same address, so the token carries a
  generation). `ObserveNonDispatchedCall`, `StripDirectCallMetadata`, and
  `StripDirectMetadataWhenDisabled` mirror the Rust helpers, and
  `RecordToolResultSources`/`RecordToolResultMetadata` are now Code Mode-only.
- `turn/tool_dispatcher.go`: prepares each direct record before dispatch and
  attaches it to that invocation's response item afterwards (releasing the permit
  on completion, cancellation, or a fatal error), observes calls that did not
  resolve to a dispatchable tool, and guards the prepared-call maps for parallel
  execution.
- `turn/agent_loop.go`, `turn/runtime.go`: non-dispatched items are observed, and
  a turn with capture disabled strips direct metadata from the prompt.
- N/A parts (with evidence): Go's compaction history is a summarized `Item` list
  with no response-item metadata, so Rust's compaction strip has no target; the
  app-server raw-response notification forwards the untouched wire item from the
  model stream, so there is no host metadata to strip; Go's Guardian review has
  no byte-budgeted transcript-history machinery. MCP result-metadata capture is

  `handlers/mcp.rs`), and Go already matches that: `tool.Output` carries no
  `_meta` and the recorder's result-capture methods stay Code Mode-only.

### `24664a59` - exec-server MXC gate (#45176 residual)

Rust's exec-server validates the sandbox context's kebab-case
`windows_sandbox_level` and, for MXC, rejects TTY/arg0 requests
("MXC currently supports ordinary pipe launches only"), managed networking
("MXC managed networking is not supported yet"), and hosts without native MXC
("native MXC is unavailable on this executor"). Go accepted any level string and
silently mapped "mxc" to the restricted-token backend.

- `execserver/sandbox_process_windows.go`: the level is validated against Rust's
  wire values and the MXC gate runs in Rust's order before any sandbox work.
- `execserver/server.go`: the shared non-Windows sandbox path applies the same
  level validation (Rust's enum deserialization).
- Tests: the MXC gate matrix and the unknown-level rejection message.

Investigated while porting (no change needed): Go's `disabled` -> legacy
(restricted-token) mapping is faithful, because Rust's
`executor_windows_sandbox_level` (#38043) upgrades a Disabled level to
RestrictedToken for Windows-convention cwds, and Go's `executorWindowsSandboxLevel`
mirrors it. Native MXC execution itself is not portable: `codex-rs/mxc-sandbox`
launches through Microsoft's `mxc` crates (`BaseContainerRunner`,
`SecurityEnvironmentApi`) rather than public Win32 APIs Go could bind.
