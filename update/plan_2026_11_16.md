## 2026-11-17 侧聊上下文预算核查（用户报 `/side` 400）

现象：Go TUI 从长线程打开 `/side` 后首轮报
`unexpected status 400 Bad Request: litellm.BadRequestError: Hosted_vllmException`
→ `LiteLLM: model group 'deepseek-v4-flash' failed with the error above`。
查 LiteLLM 服务端日志（2026-11-16 07:01:20Z，即本地 15:01，与截图同刻）确认为
`ContextWindowExceededError`：prompt 524,289 tokens 超过模型上限 524,288。

结论与对齐状态：

- 侧聊是父线程的 fork，首轮必须把继承的全部历史发给新线程；父线程平时走服务端
  响应链，只发增量，所以历史在存储里可远超单次请求可承载的窗口。
- Rust 的 fork 同样继承 `InitialHistory::Forked` 与源线程的
  `TokenUsageInfo`（#57839 `TestForkKeepsReasoningAccountingLikeRust`），重放历史后
  `History::reset_last_usage_boundary` 把用量边界对齐到重放末尾，因此也不会在
  首轮前自动压缩。即：Rust 在这个场景下做出相同行为，超长线程同样会撞 provider
  上限，不是 Go 的请求字段差异。
- Go 侧已核对并对齐的部分：`#57839` 的用量会计继承、fork 恢复用量通知先于
  thread started、以及分页父线程经 `history_base` 引用时按物化后的历史估算
  （新增 `appserver/side_fork_context_budget_like_rust_test.go`）。合成模型元数据
  的窗口为 Rust 的 272000 回退值，auto-compact 上限 244800，压缩请求历史预算
  226100（窗口 95% × 7/8），与 Rust 的 `ModelInfo::auto_compact_token_limit` /
  `compactionHistoryTokenBudget` 一致。
- 可行动项（不属于 Rust 行为对齐）：父线程超过 provider 窗口时，fork 首轮必然
  超限；需要先在父线程压缩（或用更大窗口的模型/部署）再开侧聊。
