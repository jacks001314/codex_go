### `#55969` - drain WebSocket responses on mailbox preemption

The Rust change refines the Responses Lite **WebSocket** stream: on mailbox
preemption it sends `ResponseInterrupt::Drain` instead of abandoning the
connection, keeps completed items and the response id for incremental
continuation, suppresses partial items until `OutputItemDone`, cancels buffered
tool calls before dispatch, and treats stream errors during the drain as
`needs_follow_up`.

Go has no corresponding consumer: `model.AgentRunner` only exposes `Run`
(HTTP/SSE), `ResponsesAgentRunner.Run` never selects the WebSocket transport,
and `RunWebSocket` is called only by the prewarmed Guardian reviewer
(`appserver/guardian_reviewer.go`) and tests, where no request carries a
`Preempt` channel. There is therefore no Go path that can send a WS interrupt
and no drain state to thread through `turn/agent_loop.go`; a faithful port would
first require the main turn to run over WebSockets, which is a separate
transport project (same structural class as `#56000`/`#55994`).

The transport-independent guarantees the PR relies on are already true for the
HTTP turn path and are now pinned by regression assertions in
`turn/mailbox_preemption_test.go`:

- a mailbox boundary continues the turn instead of discarding it, retaining the
  completed non-tool items in the next request's input;
- the preempted response id is carried into the follow-up request
  (`previous_response_id`) so the model continues from what it already
  produced;
- a buffered tool call in the preempted response is never dispatched and never
  reaches the follow-up request;
- queued inter-agent mail is included in the follow-up request.

### `#55954` - separate retained instruction collection from budget policy

`state/guardian_retained_context.go` had fused the two concerns in
`RetainedInstructionFragment.Required`. Collection now records only the
semantic family and source, and retention is assigned when the context is
composed:

- `RetainedInstructionItem` carries `Content`, `Kind` and `Source`;
  `RetainedInstructionKind` distinguishes user instructions, assistant
  context, host notices and framing.
- `RenderRetainedInstructions` tags each collected fragment with its kind
  instead of a required flag; the two host omission notices are `HostNotice`
  and the section markers composed by the section builders are `Framing`.
- `RetainedInstructionPolicy` mirrors Rust's composition mapping: user
  instructions, host notices and framing compose to required evidence, and
  assistant context composes to optional at `commentary` priority.
- The async/sync section split derives from that policy (plus the exact
  assistant omission notice), and both section builders frame their content
  through `Framing` items exactly like Rust's section contributor.
- Tests assert the per-kind policy table and the kinds produced by collection;
  the split-signature helper now derives `required` from the policy.

### `#55689` - owner-locked marketplace staging directories

Rust replaced the age-based "is this staging directory abandoned?" heuristic
with owner locks so concurrent installs cannot delete each other's in-progress
checkouts, and so a crashed process is reclaimed immediately instead of after
a timeout.

- `plugin/marketplace_staging.go` now models the layout from Rust:
  `.staging` (parent), `.staging.lock` (coordination), `.staging-cleanup.lock`
  (cleanup pass), `.lock` (per-directory owner) and `checkout` inside each
  staging directory.
- `MarketplaceStagingDir` takes the coordination lock, creates
  `marketplace-<goos>-*`, creates and locks the owner `.lock`, and exposes
  `checkout` as the clone destination. `Close` releases both locks and removes
  the staging directory, so installation and rollback both happen while the
  owner lock is held.
- `cleanupMarketplaceStaging` keeps the legacy age-based sweep (24h for
  `marketplace-add-`, 10m for `marketplace-upgrade-`) and then runs the
  owner-lock sweep: take the cleanup and coordination locks, inspect at most
  four platform-prefixed entries, treat a missing owner lock as abandoned, keep
  anything whose owner lock is non-regular or still held, and reclaim
  acquirable ones. Symlinks are skipped and the coordination lock is released
  before deleting.
- `materializeGitMarketplace` drops the `keepStaged` bookkeeping and relies on
  `Close` for the non-installed path.

Verification: `go test ./plugin/ -count=1`, `go vet ./plugin/`,
`gofmt -l plugin/marketplace_staging.go plugin/marketplace_install.go
plugin/marketplace_staging_test.go`.

### `#56302` - carry managed hook configuration on environment attachments

Rust added `environment_hooks` to `protocol::EnvironmentConfig` so an
environment attachment can carry the hooks from its effective managed
requirements, and summarized the table as a handler count in `Debug`.

- `appserver/hook_events.go` introduces `HookEvents`, the Go counterpart of
  `codex_protocol::hooks::HookEventsToml`: the fourteen event lists, the
  `IsEmpty`/`HandlerCount` helpers, `matcherGroups` ordering, deep cloning and
  JSON helpers. `hookEventsFromManagedRequirements` adapts
  `config.ManagedHooksRequirements` (the managed directory fields stay on the
  config type).
- `appserver.EnvironmentConfig` gains `EnvironmentHooks`, parsed from the
  `environment_hooks`/`environmentHooks` selection key, cloned with the rest of
  the config, and serialized back only when non-empty. Inferred thread configs
  inherit the zero value, matching Rust's `Default::default()`.
- Parsing rejects the same values Rust's tagged enum and
  `deserialize_mcp_tool_input` reject: unknown handler types, and MCP inputs
  that contain `null` or unsigned integers above `i64::MAX` at any nesting
  depth.
- `EnvironmentConfig.String` mirrors the Rust `Debug` implementation: the hook
  table is reported as `N handlers` and `shell_environment_policy` is redacted.
- `appendManagedRequirementHooks` now iterates the shared `HookEvents` shape so
  managed discovery and environment attachments use one event order.

### `#56304` - environment-scoped managed hooks: validation, discovery, execution

Rust's environment-scoped managed hooks PR has four parts: per-environment
discovery/listing, execution routed to the owning environment, per-environment
hook input scoping, and fail-closed validation of required hooks when an
environment configuration is accepted.

Validation, on top of the `EnvironmentHooks` field from `#56302`:

- `validateEnvironmentHooks` reports the Rust-equivalent required-load
  failures for an attachment's hook table: invalid matchers (event-scoped,
  after matcher normalization) and empty command handlers (after the
  Windows `command_windows` substitution).
- `validateEnvironmentConfigForSelection` rejects a ready attachment whose
  hooks cannot load with
  ``failed to load required managed hooks for environment `id`: ...``, matching
  Rust's `ensure_required_hooks_loaded`.
- Handler kinds Go's engine cannot run yet (`mcp_tool`, `prompt`, `agent`)
  stay accepted because Rust loads them; rejecting them here would make Go
  refuse configurations Rust accepts.

Discovery and execution (`appserver/hook_environment.go`,
`appserver/hook_environment_executor.go`, `appserver/hook_environment_turn.go`):

- `discoverEnvironmentHooks` mirrors `discover_environment_hooks`: one
  required, managed, `system` source per environment under the synthetic path
  `<environment:{id}>/requirements.toml`; `command_windows` resolves against the
  environment cwd's path convention; every load failure (invalid matcher, empty
  command, unsupported kind) is recorded as a required load error so readiness
  and startup stay fail-closed.
- `environmentHookSourcesForTurn` resolves each ready attachment's
  `EnvironmentHooks` from its resolved `EnvironmentConfig`, skipping pending and
  failed attachments, mirroring Rust `environment_hook_sources`.
- `hooksForTurn`/`hooksForThreadTurn` extend the cwd inventory; the turn tool
  hooks, session start, compact, model request, interrupt and session end paths
  all use them.
- Environment handlers carry the environment cwd and withhold the
  controller-owned transcript paths (`environmentHookInputJSON`). Local
  environments keep the in-process runner with the environment cwd; remote ones
  run through `HookEnvironmentExecutor`, which dials the environment's
  exec-server and applies Rust's one-line stdin wrapper (POSIX and PowerShell;
  `cmd` is rejected).
- Environment `PermissionRequest` verdicts can deny but never allow, matching
  Rust's "authority may restrict, never grant" rule.
- `hooks/list` thread mode merges the active turn's per-environment entries.

Round 9 closed both divergences:

- `tool.HookEnvironmentSelector` exposes the tool call's target environment
  IDs; `PreToolUse`/`PostToolUse` payloads carry `TargetEnvironments`, captured
  once before the pre-hooks run so an input rewrite cannot change the scope.
  Shell, apply_patch, view_image, request_permissions, write_stdin and MCP tools
  implement it; no selector or no id means "all environments", matching Rust's
  `ToolEnvironments::All`.
- `PermissionRequest` hooks are filtered by that same target set in the
  appserver adapter, and shell/apply_patch/MCP approval requests carry the
  resolved environment id (implicit local calls use
  `execserver.LocalEnvironmentID`).
- Threads persist the environment selections resolved during a turn.
  `threadEnvironmentHookParams` prefers the active turn and otherwise falls
  back to the persisted snapshot, so `hooks/list` thread mode, turn-scoped
  hooks and session-end hooks keep seeing environment declarations after the
  turn finishes.

### `#56036` - OAuth session logout on the gateway manager

`#56036` added request-scoped OAuth credentials and explicit session lifecycle
APIs. Go already had the request-scoped half: `GatewayCredentials`,
`RefreshAccessToken` (rejected-token recovery), `CredentialID`,
`AuthorizationID`, `ResolveAccessTokenWithoutLogin`, and the
`device_authorization_url` config field. The missing piece was explicit logout.

- `gatewayAuthStorage.delete` removes the stored grant and reports whether one
  existed.
- `GatewayAuthManager.Logout` takes the credential lock, deletes the persisted
  credential, clears both the cached token and any pending save, publishes
  `NotReady`, and returns whether a grant was removed. A cancelled context
  leaves credentials untouched, matching Rust's storage-first ordering.

Verification: `go test ./auth/ -count=1`.

## Remaining gaps and next-round priority

1. `#55994` + `#56000` (Windows proxy `CONNECT` authentication) stay blocked on
   a Go architectural gap, not on effort. Rust does not implement the handshake:
   `connect_windows_proxy` drives libcurl with `Auth::gssnegotiate/ntlm` so
   Windows SSPI produces the `Negotiate`/`NTLM` tokens on a socket curl owns,
   then hands the tunnel back to a purpose-built route-aware pool that bridges
   it through destination-specific named pipes (`reqwest`'s
   `windows_named_pipe`). Go has none of the three pieces: `net/http` offers no
   hook to replace or retry its internal `CONNECT`, the tree has no SSPI/NTLM
   binding, and `network.NewHTTPClient` only swaps `Transport.Proxy` on
   `net/http` rather than owning a route-aware pool. The whole path is
   `#[cfg(windows)]` and can only be exercised against a proxy that requires
   integrated Windows authentication.
   The transport-independent half is now pinned instead: `#56000` states that
   only a failed `CONNECT` is a proxy challenge while an origin `407` is an
   ordinary response. `network/http_client_test.go` asserts both directions
   (`TestHTTPClientTreatsOriginProxyAuthStatusAsResponseLikeRust`,
   `TestHTTPClientReportsProxyConnectChallengeAsErrorLikeRust`), and
   `doctor.isProxyAuthenticationProbeError` already maps the resulting
   "proxy authentication required" error onto Rust's
   `RouteFailureClass::ProxyAuthenticationRequired`.
2. Rust `origin/main` is `7ac6081623`; no newer commits to audit.
