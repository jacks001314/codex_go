## Findings

- #44202 hands every world-state and turn-context contributor the `ModelInfo`
  captured for the sampling step. In Rust the skill catalog budget and usage
  instructions previously read a thread-scoped `ModelInfo`, so a model switch
  mid-turn could budget the catalog with the previous model's window.
- #44242 makes the step's captured settings drive tool planning and execution:
  image support and detail, command/MCP output truncation, extension metadata,
  tool telemetry, and delayed completion events.

## Implementation

- `model/catalog.go`: exported `ModelInfo.ResolvedContextWindow` (Rust
  `resolved_context_window`: `context_window`, else `max_context_window`).
- `appserver/turn_runtime.go`: `skillContextWindowForTurn` now resolves the step
  model through `modelInfoForRuntimeWithConfig` plus `ResolvedContextWindow`, so
  the skill catalog budget follows the captured step model and a model that
  declares only `max_context_window` keeps its 2%-of-window budget.
- `tool/view_image.go`: `ViewImageOptions.StepSettings` plus call-time checks
  that reject a step model without image input using Rust's
  `VIEW_IMAGE_UNSUPPORTED_MESSAGE` and downgrade `detail: original` when the step
  model cannot request original detail.
- `appserver/runtime_router.go`: `viewImageOptionsForTurn` installs that
  resolver from the active turn's captured model.
- `appserver/turn_runtime.go`: `stepTurnClientMetadata` rewrites
  `node_repl_disabled`/`node_repl_auto_review_required` from the step model, and
  `activeTurnClientMetadata` prefers the captured `RunConfig.Model` over the
  configured default.
- Tests: `appserver/step_model_extension_context_like_rust_test.go`,
  `appserver/step_tool_settings_like_rust_test.go`.
