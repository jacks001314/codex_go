### 2. `codex tcp-tunnel` (the hidden HTTP/3 CONNECT tunnel, #45900)

Rust added `codex-rs/tcp-tunnel` plus the hidden `codex tcp-tunnel` subcommand:
a loopback TCP listener forwarded through an HTTP/3 (MASQUE-style) CONNECT
proxy, with the bearer and optional extension headers supplied only on stdin,
`LISTENING <addr>` readiness on stdout, `AUTH_UPDATED` acknowledgements, and a
listener that survives transport loss without replaying TCP streams.

Go now implements the same surface in the new `tcptunnel` package:

- `args.go`: clap-shaped argument parsing and the policy surface -
  `ParseTrustedOrigins` (exact HTTPS origins only) and `ParseProxyTarget`
  (trusted origin, credential-free authority, nonzero port), mirroring Rust's
  `parse_trusted_origins` / `ProxyTarget::parse` rules and error texts.
- `control.go`: the bounded stdin protocol (`ReadConnectHeaders` /
  `ReadAuthToken`) with Rust's limits (64 KiB tokens, 16 KiB metadata, 16
  headers, 4 KiB values), the `x-` non-forwarding header rule, duplicate
  rejection, and failures that never echo a secret.
- `tunnel.go`: the transport - a cached QUIC connection to the proxy, one
  authenticated CONNECT per local connection, `LISTENING`/`AUTH_UPDATED`
  readiness, the draining/reconnect loop with Rust's 1s->15s backoff while
  dropping (never queueing) local connections, and stream bridging with
  half-close on local EOF.
- `cli`/`app` wiring: `codex tcp-tunnel ...` reaches `tcptunnel.Run`.

Tests: the policy/admission matrix and the clap requirement matrix mirror
Rust's `proxy_policy_and_target_admission`; the control-input tests mirror
`control_input_acknowledges_bearer_renewal_with_or_without_metadata`,
`closed_parent_pipe_finishes_even_before_proxy_readiness` and
`invalid_control_input_stops_credentials_without_exposing_secrets`; and two
end-to-end tests run against a local HTTP/3 CONNECT proxy built with
`quic-go` + `http3` in the test itself - one drives the full transport
(authenticated CONNECT, bearer renewal, transport loss, reconnect, no replay)
and one drives `Run`'s whole command surface (stdin control, `LISTENING`,
`AUTH_UPDATED`, per-connection CONNECT headers).

This is the first new third-party dependency in a while
(`github.com/quic-go/quic-go` + `qpack`); it is pure Go, so the cgo-free release
path is unaffected (`go build ./...` and the existing cross-build script).

### 4. Experimental `rollout/compress` RPC (#46020)

Rust added `rollout/compress`: no parameters, requires the `experimentalApi`
capability, rejects non-local thread stores, immediately acknowledges the
trigger with `{}`, and schedules a best-effort background pass that compresses
cold local rollouts even when `features.local_thread_store_compression` is off.

- `rollout/compression.go`: `SpawnRolloutCompressionWorker` /
  `RunRolloutCompression` mirror Rust's worker - the process-scoped rollout
  maintenance lock (skip when another maintenance job holds it), the
  `rollout-compression.lock` run marker under `.tmp` with its 6-hour stale
  window, the 7-day cold-file age gate, the archived-then-active scan order, the
  sibling temp file + zstd encode + decode verification, the source-state
  recheck before publishing, the no-clobber publish that keeps the source's
  mtime, and removal of the plain file only after the compressed copy is
  published.
- `appserver`: `MethodRolloutCompress` is a top-level experimental method
  (dispatch + result type + schema signature), and the runtime router forwards
  it to the thread router's handler, so the capability gate
  (`rollout/compress requires experimentalApi capability`) and the response
  shape match.
- `appserver/rollout_migration_startup.go` +
  `RuntimeRouter` startup: `MaybeSpawnRolloutCompressionOnStartup` starts the
  startup-triggered pass when `local_thread_store_compression` is enabled,
  mirroring `thread_manager.rs`.

Tests: `rollout.TestRolloutCompressionWorker*` (cold compression + lossless
readback + mtime preservation, run-marker skip, already-compressed no-clobber),
`appserver.TestRuntimeRouterRolloutCompressSchedulesBackgroundPass` (the RPC
acknowledges and the background pass compresses a cold rollout), and
`appserver.TestRolloutCompressRequiresExperimentalCapability`.

Recorded nuance: Go has no per-rollout writer lock
(`WriterLockCoordinator`), so the worker's "skipped busy" branch has no Go
caller; the maintenance lock still excludes compression from migration and
other compression runs. Go also has no non-local thread store, so Rust's
`unsupported_thread_store_operation("rollout/compress")` rejection has no Go
counterpart (`experimental_thread_store` is not modelled at all).

### Effective collaboration mode on resume (#45519)

Rust resumed a thread with `Default`, losing a saved Plan mode, and had no
server-reported mode for reconnecting clients. Go now:

- records the collaboration mode on the persisted thread-settings snapshot
  (`rollout.AppendThreadSettingsAppliedWithSnapshot` writes
  `thread_settings.collaboration_mode`, and the runtime router passes the
  thread's saved mode when it persists a settings update),
- restores it the way Rust does: the latest thread-owned snapshot first
  (fork-copied snapshots owned by another thread are skipped), then the legacy
  `TurnContext.collaboration_mode`, then Go's compact world-state section
  (`rollout.LatestPersistedCollaborationMode`,
  `Router.latestPersistedCollaborationMode`),
- reports it as `thread/resume.collaborationMode` (absent when nothing was
  saved), and
- seeds the resumed session's settings from the restored mode so the first turn
  after a cold resume keeps using the saved Plan mode
  (`RuntimeRouter.applyThreadResumeCollaborationMode`).

Evidence: `rollout.TestLatestPersistedCollaborationModeRestoresSavedMode` (owner
matching plus the fork-copy skip),
`rollout.TestLatestPersistedCollaborationModeFallsBackToTurnContext`,
`appserver.TestThreadResumeReportsLiveCollaborationMode` (including the
serialized `collaborationMode` document),
`appserver.TestThreadResumeRestoresPersistedCollaborationMode`, and
`appserver.TestLatestPersistedCollaborationModeReadsWorldState`.

### An accepted exec-server replacement retries the attach (found while running the suite)

Running `go test ./...` twice surfaced a real, load-sensitive failure that is
not part of the upstream range but is a Go/Rust behaviour gap:
`execserver.TestConnectAcceptedClientInitializesAndReplacesLikeRust` failed with
`accepted exec-server replacement failed: exec-server initialize failed
(-32010): session <id> is already attached to another connection` (reproduced
on demand by running six concurrent copies of the package under load).

Rust classifies `SESSION_ALREADY_ATTACHED_ERROR_CODE` as a *retryable* recovery
error (`exec-server/src/client_recovery.rs::is_retryable_recovery_error`)
because retiring a transport is asynchronous on the server, and its accepted
replacement returns after handing the socket to the recovery task, which
re-dials/re-handshakes. Go's `ReplaceAcceptedConnection` closed the old transport
and then ran a single initialize, so the handshake could race the server's
detach and fail the host's handoff (losing the host-supplied socket).

Go now mirrors the classification: `execserver.rpcServerError` carries the
JSON-RPC code (text unchanged), `isSessionAlreadyAttachedError` matches -32010,
and `attachAcceptedReplacement` retries the handshake on the same socket for
that code only, bounded by a 2 s window with 10 ms steps, while every other
failure still releases the socket. Evidence:
`execserver.TestAcceptedReplacementRetriesAlreadyAttachedLikeRust` (a scripted
first attach rejected with -32010, then a successful resume, socket kept) and
`execserver.TestAcceptedReplacementSurfacesNonRetryableAttachErrorsLikeRust`
(another code still fails the handoff and closes), plus 330 clean runs of the
previously failing test under the six-job stress harness that reproduced it.
