## Goal

Audit the diagnostic report upload hardening stack and record whether Go can
carry it.

## Findings

- #41569 splits a report into a core event envelope plus one gzip envelope per
  attachment, bounds encoded and decoded payload sizes with format-aware
  truncation, retries transient attachment failures within a shared budget, and
  honors Sentry rate-limit/retry headers without replaying the core event.
- #42096 gives the whole report one five-minute deadline, stops reading or
  sending attachments once the deadline or a rate limit is hit, and limits the
  app server to three concurrent uploads with an overloaded JSON-RPC error.
- Go's feedback path stops at local preparation. `appserver/feedback.go`
  (`PrepareUpload`, `SaveFeedback`, attachment archives and size bounds) and
  `app/remote_tui.go` build the report and its attachments, but no Sentry
  envelope client, HTTP/gzip sender, retry/rate-limit handling, delivery outcome
  type, or upload concurrency gate exists anywhere in the tree.
- The earlier `complete` entries in this stack (`13d75cd1c3`, `0df1daf526`) are
  attachment-preparation contracts, which Go does implement. The upload
  transport itself has never had a Go carrier.

## Implementation

- No product code this round: both commits describe behavior of a network
  transport Go does not have.

## Decision

- `aaa7ed042e` and `a17ee5705c` -> `blocked_precondition`, with the missing
  diagnostic report (Sentry envelope) transport recorded as the precondition.

## Residuals

- Diagnostic report network uploads (event/attachment envelopes, retry and
  rate-limit handling, shared deadline, three-slot concurrency gate) remain
  unimplemented in Go; the whole stack reopens once a transport exists.
