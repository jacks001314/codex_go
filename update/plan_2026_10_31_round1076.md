## Goal

Bound the app-server's native user-verification work: one operation per
service and a 120-second worker timeout.

## Findings

- Go already dispatches `userVerification/status|enroll|delete|verify` through
  the installable `UserVerificationProvider`, gates enroll/delete/verify to
  local transports before parameter validation, and exposes device-gated
  activation; unsupported providers report `providerUnavailable`.
- It did not yet mirror Rust's native worker: Rust keeps a one-permit semaphore
  per service, rejects a concurrent operation with
  `failed/providerError` and the message "Another user verification operation
  is still running.", bounds the work to 120 seconds with
  `failed/timeout` ("User verification timed out."), and holds the permit in
  the worker until the provider actually returns.
- Rust also re-checks connection, cancellation and account identity after the
  worker finishes and before delivering the response; Go's synchronous handler
  has no per-request cancellation token or connection gate to re-check.

## Implementation

- `appserver/runtime_router.go`: add `userVerificationWorkMu` /
  `userVerificationWork`, the router-owned single worker slot.
- `appserver/user_verification_runtime.go`: `userVerificationService` gains
  `acquire`/`release`/`timeout`; every native branch (status included) runs
  through `runNativeWork`, which rejects a second concurrent operation with
  `failed/providerError`, runs the provider on its own goroutine, returns
  `failed/timeout` after 120 seconds, and releases the slot from the worker
  when the provider returns (also after a timeout).
- `appserver/user_verification_worker_like_rust_test.go`: cover concurrent
  rejection, timeout, the slot staying busy after a timeout, and reuse once the
  provider returns.

## Residuals

- Post-worker re-checks of connection closure, in-process cancellation and
  account revision are not implemented: Go's user-verification handler is
  synchronous and the provider interface carries no request guard. The worker
  slot and timeout, which are the observable bounds of this commit, are covered.
- Rust's in-process TUI activation wiring is out of scope here; Go's
  device-gated activation predicate already exists.
