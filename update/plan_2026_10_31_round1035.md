## Goal

Audit #42391 (`Authorize apply_patch in the executor path context`) and close
the path-convention misclassification in Go's apply_patch authorization gate.

## Findings

- Rust moved patch authorization onto `PathUri` values evaluated with a
  filesystem policy context (`FileSystemSandboxPolicyContext`), because a patch
  target can use a different path convention from the Codex host.
- Go's authorization gate (`tool/apply_patch_executor.go`
  `applyPatchDeniedPath`) classified targets with host `filepath` operations
  against the *Codex host* cwd, not the selected environment cwd that the patch
  itself resolves against:
  - a Windows executor on a POSIX host had `C:\workspace\file` treated as a
    relative path below the host cwd (work inside the executor workspace was
    refused);
  - a POSIX executor on a Windows host had `/srv/outside/file` treated as a
    relative path (writes outside the executor workspace were allowed).
- Go already resolves the environment filesystem and merges granted permissions
  with `PathConventionForPath(cwd)`, so only the authorization gate and the
  safety helpers still used host semantics.

## Implementation

- `safety/safety.go`: added `FileSystemPolicyContext` (executor cwd as a
  `utils.PathURI`, extra resolved roots, protected metadata names) with
  `ResolvePath`, `CanWritePath`, and `HasConfiguredWritableRoots`, plus
  `CanWritePathInContext`, `WritePatchConstrainedToWritablePathsInContext`, and
  `AssessPatchSafetyWithContext`. Roots are resolved through `PathURI.Join`, so
  relative and foreign-convention roots follow the executor convention;
  protected workspace metadata names (`.git`, `.agents`, `.gcode`, `.aws`) stay
  read-only and are matched case-insensitively only under the Windows
  convention.
- `tool/apply_patch_executor.go`: the denial gate now receives the resolved
  environment cwd instead of `e.cwd()`. When that cwd is a path URI or uses a
  foreign convention, classification goes through the executor context: the cwd,
  the policy's writable roots, and the symbolic POSIX `/tmp` root are resolved
  under the executor convention, while the host temp directory is never used for
  a foreign executor.
- Tests:
  - `safety/apply_patch_path_context_like_rust_test.go`: Windows executor URIs,
    parent traversal, drive/case handling, protected metadata and its case alias,
    move targets, full-disk policy, and the read-only versus outside-project
    rejection reasons.
  - `tool/apply_patch_executor_path_context_like_rust_test.go`: a Windows
    executor addressed from another convention, a POSIX executor addressed from
    a Windows host, and protected metadata under the executor convention. Both
    direction tests were confirmed to fail against the pre-fix gate.

## Decision

- Mark `fe140d4c8e` as `partial`:
  - the misclassification and the context-aware containment/rejection-reason
    contract are implemented and covered;
  - residuals: Rust's `write_permissions_for_paths` derives and requests parent
    write permissions for executor-managed out-of-root targets, and
    `PatchSandboxRoute` distinguishes executor-managed from platform sandboxing
    when auto-approving. Go's executor has no automatic patch permission request
    (grants come from the turn/session) and no sandbox-route enum, so those parts
    remain unimplemented;
  - Rust's entry-list special-path narrowing (`has_write_narrowing_entries`,
    `has_same_target_write_override`, `has_full_disk_write_access_with_context`)
    has no Go counterpart because Go's workspace policy is the legacy
    `SandboxPolicy` rather than a restricted entry list; the convention split for
    `:slash_tmp` is applied where Go does model it (the extra `/tmp` root).
