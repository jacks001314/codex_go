## Advanced this round

While covering the client half of #58125 the stdio host turned out to report a
failed script as a **successful** observation: the wire frame carried
`"error_text": null` and only the text the script had already written. A TUI
or app-server talking to the in-process host therefore rendered the failure as
"Script completed" with no `Script error:` block.

Three defects stacked up:

1. `tool/codeModeExecExecutor.consumeCell` overwrote the settled output's
   `content_items` with the cell delta (only what `text()`/media wrote), which
   discarded the trailing `Script error:` item the failure response had built.
2. The executors truncated inside the execution layer even when serving a
   code-mode host, so a server-truncated observation was budgeted twice (a
   second `Warning: truncated output` header inside the first one).
3. `hostRuntimeResponse` ignored `Output.Success` and never set `error_text`,
   so a finished failure looked like a plain successful `Result`.

## What changed

- `tool/code_mode_exec.go`: failure responses expose `Data["error_text"]`;
  `consumeCell` keeps the trailing labeled item and appends it to the cell
  delta body; `CodeModeHostObservationContextKey` tells the executors that a
  host owns the observation policy, and the four execution-layer truncation
  sites skip budgeting for such invocations.
- `codemode/stdio_host.go`: the host marks its invocations, reports
  `Result{content_items, error_text}` for an unsuccessful output, and drops the
  executor's own labeled block so the observation policy adds it exactly once
  (client mode hands it to the caller, server mode charges it to the budget).
- Tests: `codemode/stdio_host_failure_like_rust_test.go` drives a real
  `RunStdioHost` session in both truncation modes over the wire protocol;
  `tool/code_mode_server_truncation_like_rust_test.go` covers the cell delta and
  the client half of #58125.
