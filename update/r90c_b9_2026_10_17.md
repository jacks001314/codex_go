## 7. 未覆盖 / 说明（如实）

1. **Go 的 core 单载体 vs Rust 的双载体**：Rust 把独立图片生成放在 `TurnItem::Extension(ExtensionItem::ImageGeneration(..))`（camelCase，带 fileId/inputImages），而把 hosted 变体放 `TurnItem::ImageGeneration`（`protocol/src/items.rs:405-415`，只有 id/status/revised_prompt/result/saved_path）。Go 只有**一个**合并的 core `ImageGeneration` 项（还额外带 `transparent_background`），因此本批按 Go 既有约定把两个字段并入该 core 项，而**没有**把 core 类型改成 `Extension{kind:"image_gen.generation"}`——那是会牵动 appserver 协议/schema/state 投影的大改动，超出 G10 范围，且与 Go 现网 rollout 的记录形状不兼容。此差异作为**已知形状偏差**登记，未做近似改动。
2. **legacy 事件的写侧**：Rust 的 legacy 事件（`ImageGenerationEnd`）是 fileRef/inputImages 的正式载体之一。Go 的 `AppendSessionItemEvent`（`rollout/session_items.go:136`）在 **paginated 模式下直接 return nil**，且只处理 user/agent 消息 —— 即 Go 的 paginated rollout 从不写图片生成 legacy 事件，也没有 `EnsureRustCompatibleSessionHistory` 的图片分支。本批**未**新增 legacy 事件分支：Go 的等价载体就是 core 项（本批已补齐），新增事件流会改变 rollout 行数/回放语义，属另一项工作（如需要可另立项）。
3. **`fileId` 与 `result` 同时存在时**：Go 读取端偏好 fileRef（core 写入时也只在 `fileId` 非空时写 `file_id`，但会保留空 `result`，与 Rust 迁移期记录一致）；公开面按 Rust untagged 语义只发其中一个。此取舍已由探针第 (3) 段断言钉住。
4. **`failure` 字段**：Rust 的 ext item 有 `failure`（`ImageGenerationFailure`），Go 的 core/公开投影都没有该键（Go 用 `status`/`savedPath` 表示失败），属**既有**形状差异，不在 G10 的两个字段范围内，未动。
